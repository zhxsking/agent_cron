大模型经典论文精读系列 #034

Toolformer: Language Models Can Teach Themselves to Use Tools Toolformer：语言模型自己教自己用工具——把 Self-RAG 的"反思 token 训进权重"拓成"任意工具调用训进权重"，让模型学会按需调计算器、搜索引擎、日历、问答系统

作者：Timo Schick, Jane Dwivedi-Yu, Roberto Dessì, Roberta Raileanu, Maria Lomeli, Luke Zettlemoyer, Nicola Cancedda, Thomas Scialom 机构：Meta AI Research · Universitat Pompeu Fabra 发表：2023-02 / arXiv:2302.04761 · NeurIPS 2023
arXiv GitHub（非官方实现）

想象一位博学的图书馆员：他能跟你聊三个小时康德的二律背反，能背出整本《神曲》的段落，却在你问"23 乘以 47 等于几"时，一脸诚恳地告诉你"大概是 1001 吧"——然后在你提醒今天是星期几时，又茫然地摇了摇头。这不是夸张的笑话，这就是 2022 年底所有大语言模型的真实写照。

更尴尬的是，一个只有几兆参数、连"理解语言"都算不上的小计算器，在算术上能把 1750 亿参数的 GPT-3 按在地上摩擦。这篇论文要回答的，就是一个近乎哲学的问题：能不能让这位博学的"笨蛋"自己学会，在算不动账的时候悄悄掏出计算器、在记不起日期时悄悄瞄一眼日历？而且——关键来了——不需要人手把手地教，让它自己教自己。

一句话总结 Toolformer 让一个 67 亿参数的语言模型，靠"自采样 + 损失过滤"的自监督流程，自己学会在什么时候、用什么参数、调用哪一类外部工具（计算器、问答、搜索、翻译、日历），并把它"焊"进权重，零样本下追平甚至超过 1750 亿参数的 GPT-3，而原来的语言能力一丝不减。

01领域定位

把上一篇 Self-RAG 想成"把调检索器验证这一种动作训进权重"，那么 Toolformer 就是把这条思路从一种工具拓展到任意工具：计算器、问答系统、搜索引擎、机器翻译、日历，统统按同一种"工具调用 token"格式训进权重。它承接了"工具使用进权重"的范式，又为后来真正意义上的 agent（智能体）时代铺下了第一块砖——只不过，它自己也老老实实地承认：我还不会把一个工具的输出喂给另一个工具（不能链式调用），所以这块砖还只是"最小学步车"。

在大模型发展脉络上，它正好卡在一个奇妙的转折点：训练期把工具调用内化，而非 few-shot 那样每次推理时临时拼提示。这一步，让"会用工具"从"提示工程技巧"升级成了"模型自身的能力"。

02研究背景

2022 年底的大模型有一个被反复调侃的"悖论"：它们能写诗、能编程、能讨论哲学，却在四件"小学生都会"的事上频频翻车——算不准账、记不住今天星期几、查不到最新新闻、翻译不好小语种。作者把这四类毛病归因于一个根本原因：这些能力无法靠单纯扩大参数来解决。算术是符号精确运算，知识有截止日期，时间是动态变量——再大的模型，也只是把训练语料里的统计模式背得更熟，本质上学不会"算"和"查"。

解决办法看起来很简单：给模型一把"瑞士军刀"——外挂计算器、搜索引擎、日历。但当时已有的做法都有硬伤：

  • 重人工派（如 Google 的 LaMDA、Internet-Augmented Dialogue）：靠海量人工标注的"何时调工具"样例训练，成本高得吓人，而且人觉得有用的，未必是模型觉得有用的。
  • 硬编码派（如各种 retrieval-augmented 流水线）：把工具调用写死在某个任务的某个步骤里，换个任务就失效，模型完全丧失通用性。
  • 纯提示派（few-shot 演示工具用法）：推理时管用，但没进权重，换个措辞的提示就可能懵掉，且每次都要占用宝贵的上下文窗口。
类比 旧方法像是给一个新员工配了一位"秘书"：秘书（人工标注/硬编码流程）在他耳边不停念叨"这个该查日历、那个该用计算器"。员工确实能把活干了，但离了秘书就抓瞎，而且秘书还贵得离谱。Toolformer 想做的，是让这位员工自己摸索出"什么时候该翻哪本工具书"，摸索的过程全靠他自己干活时的得失反馈，不请任何秘书。

03核心问题

把上面的背景压成一句话，Toolformer 要解的是：如何让语言模型在不需要大量人工标注的前提下，自己学会"何时调、调哪个、传什么参数、怎么把结果接回文本"，而且学了工具之后，原有的通用语言能力一点都不能掉。

注意这里有两个看似矛盾的要求被绑在了一起——要会调工具（领域特定能力）和不能丢通用性（跨领域能力）。前者容易让人想到"为每个任务单独训一个模型"，后者又恰恰反对这么做。作者给出的破局思路是：用同一个语言建模损失来当裁判，让"对预测未来文本有用"的工具调用自己浮出来。

思考一下 如果让你判断"模型在这里调一次计算器到底有没有用"，你会怎么衡量？是看模型最后答得对不对？还是看别的什么？先别往下看——这个问题的答案，正是 Toolformer 最巧妙的那一步。

04方法详解

整个方法可以浓缩成四个字：采样、执行、过滤、微调。它巧妙地借用了当时刚火起来的一个思路——"用大模型的上下文学习能力，自己生成训练数据"（这条思路的早期代表正是同一作者 Timo Schick 的 Self-Instruct 雏形）。下面逐步拆解。

步骤一：把工具调用变成"文本"

要做这一切，第一步得让"调工具"这件事能写进文本里。作者把每次 API 调用定义成一个元组 $c = (e_{api}, e_{in})$，其中 $e_{api}$ 是工具名（如 Calculator），$e_{in}$ 是输入参数。然后用一对外层特殊 token 把它"包"起来，把调用、返回结果都线性化成普通文本序列：

Pittsburgh is also known as <API>QA("What other name is Pittsburgh known by?")</API> Steel City the Steel City.

这里 <API> ... </API> 包住的是"调用本身"，紧跟其后的 Steel City 是工具返回的结果 $r$，再往后接原文。一旦调用、返回都被写成 token，模型就能像预测任何普通词一样去预测它们——这就是"把工具调用训进权重"的字面含义。

步骤二：让模型自己"提议"该在哪调什么

现在语料里还没有这些调用，得有人去"种"。作者只给模型每个工具一小撮人工写的示范（论文里说是 a handful of demonstrations，每种工具就几条），然后把大段纯文本喂给模型，让它用上下文学习的方式，在文本的各个位置上采样出可能的 API 调用——调什么工具、传什么参数，全由模型自己猜。这一步会产出海量候选，绝大多数都是噪音。

步骤三：用损失当裁判，过滤出"真有用"的调用

这是全篇最巧妙的一步，也是回答前面那个思考题的答案。作者没有去看"模型最终答得对不对"（那是结果监督，需要标准答案），而是看把工具结果塞进上下文后，模型预测后续文本是不是更容易了。具体地，对位置 $i$ 上的候选调用 $c_i$ 及其返回 $r_i$，定义一个加权交叉熵损失：

$$ L_i(z) = -\sum_{j \geq i} w_{j-i} \log p_M\!\left(x_j \mid z,\, x_{1:j-1}\right) $$ (1)

这里 $z$ 是塞到位置 $i$ 的"前缀"，权重 $w$ 让越靠后的 token 影响越小（贴近调用位置的 token 更受影响）。然后比较两种情形：

  • 有结果：$L_i^{+} = L_i\!\big(e(c_i, r_i)\big)$，把"调用+返回"都塞进去；
  • 无结果：$L_i^{-} = \min\!\big(L_i(\varepsilon),\; L_i(e(c_i, \varepsilon))\big)$，取"完全不调"和"调了但不给返回"两者中损失更小的那个。

过滤规则只有一行：当且仅当有了结果后损失下降得够多，这个调用才被留下——

$$ L_i^{-} - L_i^{+} \geq \tau_f $$ (2)

这个设计妙在三点：第一，不需要标准答案，监督信号完全来自模型自己的损失，真正做到自监督；第二，它衡量的是"对模型有用"而非"对人有用"，正好避开前人"人工标注与模型需求错位"的坑；第三，阈值 $\tau_f$ 一刀切，调高了样本少而精，调低了样本多而噪，一个超参就能在数据量与质量间拨杆。

步骤四：在过滤后的数据上微调，并改造推理

把通过过滤的调用连同返回结果，原样交错插回原始文本，得到增强语料 $C^*$。注意原文本一字未改，只是间或插入了带返回的工具调用——这保证了模型在学"调工具"的同时，原始语言建模分布没被破坏。然后用标准语言建模目标微调原模型（论文用的是 GPT-J，6.7B 参数）。

推理时也做了配套改造：模型正常自回归生成，一旦吐出代表"请求返回"的特殊 token，解码立刻暂停，系统去真正调用对应 API，把返回结果和闭合 token 插回序列，再让模型继续往下写。对外部世界而言，模型就像中途"停笔查了一下资料"又接着写。

工具清单 论文实证了五种工具，全部是"文本进、文本出"的 API：计算器（算术）、QA 系统（基于 Atlas 的事实问答）、BM25 维基百科检索、机器翻译模型、日历（返回当前日期）。选这五样不是随便挑的——它们正好覆盖了开篇列出的那四类"再大模型也学不会"的毛病。

05实验结果

实验在 GPT-J（6.7B）上做，用 CCNet 子集构造增强数据，8 块 A100 + DeepSpeed ZeRO-3 微调。基线很有意思：原始 GPT-J（看原生能力）、GPT-J + CC（在同样纯文本上微调，用来证明"增益不是来自多看了一遍语料"）、OPT-66B 和 GPT-3 175B（看"参数大十倍、二十多倍"能不能碾压）。全部在零样本设置下评估。

几个最让人眼前一亮的发现：第一，触发率本身就说明问题——在算术任务上模型 97.9% 的时候主动掏出计算器，在事实问答上 98.1% 主动调 QA，说明它真的"内化"了"这种题该用这个工具"的判断，而不是瞎调。第二，6.7B 在它该用工具的领域，硬是把 175B 的 GPT-3 甩在身后——参数不再是唯一解，"小模型 + 外挂精确工具"在这几类任务上性价比碾压。第三，也是最让作者欣慰的：WikiText 困惑度几乎纹丝不动，证明"学调工具"和"保持通用语言能力"这对矛盾，被这套设计真的调和了。

消融实验还挖出一条很有意思的规模规律：利用工具的能力，要到参数量大约 775M 之后才开始显现，更小的模型即使照搬这套流程也学不会。换句话说，"自己教自己用工具"这件事本身，是一种涌现能力。

06影响与意义

Toolformer 的最大贡献，是把"模型该不该调工具、调哪个、怎么用结果"这三件事的决策权，从人和流水线手里夺过来，交还给模型自己，并且用一种优雅到近乎朴素的方式——"对你预测下文有没有帮助"——来当唯一裁判。它证明了：不需要海量人工标注，模型也能自己长出工具使用能力。

它的思路直接启发了后来一系列工作：把"工具调用"作为一种特殊 token 训进权重，几乎成了 function calling（函数调用）范式的原型；"用模型自己的损失当裁判、自生成训练数据"这一招，也被后续很多 agent 训练工作继承。可以说，它是从"会聊天的模型"走向"会动手的 agent"路上，最早的一块路标。

07局限性与未来方向

作者相当坦诚地列了几条硬伤，而这些硬伤恰好划出了后来 agent 研究的主战场：

  • 不能链式调用：一个工具的输出不能直接当另一个工具的输入，无法做"先搜再算再翻译"这种多步流水线。
  • 没有多轮交互：比如搜索结果只能拿第一段，不能"翻下一页""换关键词再搜"。
  • 对指令措辞敏感：训练时的措辞分布会迁移到推理，换个问法就可能不触发工具。
  • 不计调用成本：模型决策时完全不考虑调一次 API 要花多少时间或钱。
  • 工具必须文本进文本出：图像、音频这类非文本 API 没法直接套这套流程。

这些局限几乎预言了接下来两年的研究方向：链式调用催生了各种"思考-行动-观察"循环的 agent 框架，多轮交互催生了带反馈的 agent 训练，非文本工具则被多模态模型逐步消化。

08领域演进脉络

把镜头拉远看整条大模型脉络：2017 年 Transformer 打下架构地基；2018–2020 年 BERT、GPT-2/3 让"预训练"成为范式；2020–2022 年 Chinchilla 摸清"算力最优"配比，InstructGPT 用人类反馈教模型听懂人话；2022–2023 年进入"对齐与应用"期，CoT 系列点燃推理，Self-Refine/Reflexion/CRITIC/Self-RAG 一路把"自我纠正"从提示技巧推进到训练进权重。

Toolformer 正处在这条线的转折点：它把 Self-RAG 的"反思 token 进权重"思路，从"一种检索器"拓成"任意工具"，让模型第一次具备了自主使用外部世界的能力。再往后，就要解决它留下的"不能链式、不能多轮"——那正是下一篇 ReAct 要登场的地方，agent 时代就此拉开帷幕。

09趣味延伸

一作 Timo Schick 在这一年前后简直是"自监督数据生成"的狂热信徒：他的另一篇 Self-Instruct 雏形工作，和 Toolformer 共享同一种哲学——"与其求人标注，不如让模型自己生成、自己筛"。有趣的是，Toolformer 论文里模型从未被告知"算术题该用计算器"，它是看着文本里"400 人里有 29% 通过"这种句子，自己琢磨出"在这儿塞个 [Calculator(400/1400)] 会让后面更好预测"的。这种"模型自己发现什么时候工具帮得上忙"的涌现，比人工教它规则要迷人得多。

还有个容易被忽略的彩蛋：Toolformer 发表在 2023 年 2 月，几乎和 ChatGPT 函数调用、各种 plugin 生态同一波涌现。而它选择 GPT-J 这个相对小的 6.7B 模型做实验，本身就是一种宣言——"会调工具的小模型，能在特定领域咬住参数大二十多倍的巨兽"。这个判断在两年后被开源小模型 + 工具调用的浪潮反复验证。至于"模型越界的幽默"也不少：早期版本里，模型有时会在完全不需要工具的地方也硬塞一个调用，活像个刚学会用锤子的孩子，看什么都像钉子。

10个人解读与延伸思考

读完整篇，我最受触动的不是它做了多少工具，而是它背后那个极简的裁判原则：判断一个动作该不该被模型学会，就看"它让模型预测未来更容易了吗"。这个原则之所以深刻，是因为它把"什么是有用的工具调用"这个本来需要人来定义的主观问题，转换成了一个模型自己能量化的客观指标。人觉得有用的，模型未必觉得有用；模型自己损失下降了的，才是真的对它有用。这套哲学今天回头看，几乎就是"用模型自身的损失当奖励信号"的雏形——和后来大行其道的 RL 训练，在精神上是同源的。

从工程现实看，Toolformer 也是"小模型 + 外挂能力"路线的早期实证：在算术、事实、时间这些符号精确的领域，与其把模型堆到天文参数去硬背，不如让一个 6.7B 学会按需调精确工具。这条性价比路线，和今天开源小模型靠工具调用与 agent 框架"以小博大"的趋势，一脉相承。

留个问题给你 Toolformer 用"损失下降"来当裁判，可损失下降≠最终答案正确。一个调用可能让模型"更自信地预测错答案"而被留下。你觉得，这种"以模型自身损失为裁判"的做法，在什么任务上会失灵？又该怎么补上这道"自信但错误"的缝隙？带着这个问题，我们下篇见。

ReAct: Synergizing Reasoning and Acting in Language Models

Toolformer 把工具调用训进了权重，却老老实实承认"我还不会把一个工具的输出喂给下一个工具"。下一篇我们讲 ReAct：它不靠训练，只在推理时把"思考"和"行动"交织成 Thought→Action→Observation 的循环，让模型一边想一边调工具、一边观察一边再想，正好补上 Toolformer 留下的链式调用与多轮交互缺口——agent 时代真正的奠基之作，即将登场。
