大模型经典论文精读系列 #050

MASAI: Modular Architecture for Software-engineering AI Agents MASAI：把一个 agent 拆成五个子智能体——微软研究院的“分而治之”，在 SWE-bench Lite 上拿下 28.33%

作者：Daman Arora*, Atharv Sonwane*, Nalin Wadhwa*, Abhav Mehrotra, Saiteja Utpala, Ramakrishna Bairi, Aditya Kanade, Nagarajan Natarajan（*同等贡献） 机构：Microsoft Research India（微软研究院印度） 发表：2024-06 / arXiv v1
arXiv SWE-bench

上篇我们讲完 OpenHands——它把 agent 做成一套开放平台，谁都能往里塞自己的 agent。可在它之前一个多月，微软研究院印度（MSR India）的一支团队已经悄悄抛出另一个问题：通用平台是有了，可“一个 SE agent 到底该怎么设计”？是把 LLM 扔进一个长循环里让它自己想、自己改、自己试，还是该像真正的工程师那样——先把活拆开，再分工？

2024 年 6 月 17 日，Daman Arora、Atharv Sonwane、Nalin Wadhwa 等八人把答案挂上 arXiv。他们的结论很反直觉：别让一个 agent 从头到尾“一条道走到黑”，那样轨迹又长又贵、上下文还塞满无关信息；把它拆成五个目标明确、策略各异的子智能体——有人负责摸清测试设施、有人负责复现 bug、有人负责定位、有人负责改、有人负责用测试排序——反而更准、更省。在 SWE-bench Lite 上，这套“分而治之”拿下 28.33%，成为当时开源 SOTA。当“通用平台派”和“无 agent 流水线派”吵得不可开交，MASAI 选了第三条路：不是不要 agent，而是把 agent 拆成模块。

一句话总结 MASAI 把“修一个 GitHub issue”这件复杂事，拆给五个目标明确、策略各异的子智能体——Test Template Generator、Issue Reproducer、Edit Localizer、Fixer、Ranker——用 ReAct 做导航、CoT 做补丁采样、复现的测试做排序，在 SWE-bench Lite 上以 28.33% 登顶开源 SOTA。

01领域定位

顺着这个系列的脉络，第 47 篇 SWE-agent 把 ReAct 的“思考-行动”循环落到真实仓库上，给出 ACI 接口设计，证明“接口比堆 agent 重要”；第 48 篇 Agentless 反手抽走“自主决策”，用一条死板流水线也能 SOTA；第 49 篇 OpenHands 把 agent 做成开放平台。三篇走完，SE agent 圈形成了两条主线：通用平台派和无 agent 流水线派。

MASAI 站在两条线中间，给出第三种解法。它既不否定“agent”这个主体（这点和 Agentless 划清界限），也不把所有事压给一个“长循环 agent”（这点和 SWE-agent 划清界限）。它的主张是：agent 该用，但要按软件工程师的方式用——先分而治之，再各司其职。这篇论文在脉络里的位置，是“模块化派”的奠基之作——它之后，把一个大 agent 拆成定位/修复/验证子模块，几乎成了 SE agent 设计的默认范式。

02研究背景

2024 年上半年，SWE-bench Lite 成了 SE agent 圈最热闹的角斗场——300 个真实 GitHub issue，来自 11 个 Python 仓库，谁能在最少的提示下修好最多 issue，谁就是王者。SWE-agent、AutoCodeRover、Aider、OpenDevin……一批工作轮番上阵，思路却惊人地一致：把 LLM 塞进一个长 ReAct 循环，让它自己想、自己调工具、自己改、自己再试。

可这条路有三个绕不开的坑，论文开篇就点破了：

  • 单一策略难以通吃：导航仓库要用“边想边调工具”的 ReAct，可生成补丁时连续推理（CoT）往往更稳。一个长循环从头到尾只能用一种策略，等于用一把锤子拧所有螺丝。
  • 长轨迹又贵又脏：一个循环跑下来，上下文塞满了沿途所有命令输出、文件片段、失败重试。这些“无关上下文”既烧推理成本，又会让模型分心、性能下滑（论文专门引用了 lost-in-the-middle 现象）。
  • 信息散落各处：修一个 bug，可能要去 README 找测试怎么跑、去 test 文件找用法、去源码找根因。一个 agent 在同一根上下文里来回翻，很容易捡了芝麻丢了西瓜。

更有意思的是，作者们注意到一个反直觉的事实：软件工程师自己面对复杂 bug 时，从不一上来就埋头改。他们先复现、再定位、再改、再用测试验——每个阶段用的策略还不一样。MASAI 的灵感正来源于此：既然人这么干活更靠谱，agent 为什么不能学？

类比 想象一家小修车铺。一种修法是雇一个“全能师傅”，从接车、诊断、拆件、换件、试车全包——他确实什么都懂，但活一多就容易顾此失彼，工具摊一地，前面拆的螺丝转眼就忘了在哪儿。另一种修法是按工位分工：前台只管复现故障、诊断师傅只管找病根、维修师傅只管换件、质检员只管跑测试出报告——每个工位只盯一件事，策略各不相同。MASAI 选的是后一种，把“修一个 issue”拆成五个工位，每个工位是一个目标单一、策略定制的子智能体。

03核心问题

论文要回答的问题，可以浓缩成一句：能不能把“修一个仓库级 issue”这件复杂事，模块化拆给多个目标明确的子智能体，让每个子智能体用最适合它的策略，既绕开长循环的贵与脏，又比无 agent 流水线更准？

这个问题里藏着 MASAI 最关键的两个设计取舍。第一，“模块化”不等于“多智能体对话”——它刻意不要 AutoGen、MetaGPT 那种 agent 之间互相聊天的协作，而是把输出从一个子智能体直接喂给下一个，像流水线一样单向传递。第二，不同子智能体可以用不同策略——这是它和“一个长循环用同一种策略”最大的分野。论文用一句话点题：“当问题复杂度上升，很难再设计一个能横扫所有情况的单一策略。”

思考一下 如果你要把“修 bug”拆成五个子智能体，你会怎么分？先别往下看，自己在心里列五条：谁负责什么、用什么策略。读完下面的架构，对比你想的分法差在哪。

04方法详解

MASAI 的核心抽象很简洁。一个 MASAI agent 是若干 MASAI sub-agent 的组合；每个子智能体用一个三元组定义：⟨Input, Strategy, Output⟩——输入是什么、用什么策略解题、产出什么。子智能体之间不聊天，只靠“把上一个的输出当成下一个的输入”串成流水线。为了和真实仓库交互，所有子智能体共享一套七动作的动作空间。

基础动作空间：七个动作

所有子智能体共享一套极简动作空间，和 SWE-agent 的 ACI 思路一脉相承——动作少而精，让模型不至于在动作选择上犯晕：

  • READ(file, class, function)：读取文件/类/函数。读文件只给顶层定义签名，读函数才给完整函数体——懒表示，避免一上来就灌满上下文。
  • EDIT(file, class, function)：标记一段要改的代码（只在唯一匹配时才标记，否则返回候选列表让模型细化查询）。
  • ADD(file)：标记一个文件要新增代码（文件必须已存在）。
  • WRITE(file, contents)：写入指定内容到文件。
  • LIST(folder)：列目录。
  • COMMAND(command)：在 shell 执行命令（带超时和长输出截断）。
  • DONE：声明本子智能体目标完成。

注意一个细节：不是每个子智能体都拿全部动作。Fixer 干脆“无动作可用”——它只读 Edit Localizer 给的代码片段，闭门生成补丁；Ranker 也只跑测试做排序。这种“按需分配动作”正是模块化的好处：每个子智能体的动作空间被剪到刚好够用，上下文不会被无关动作污染。

子智能体一：Test Template Generator——先搞清楚怎么跑测试

它只干一件事：摸清这个仓库的测试基础设施。策略用 ReAct，动作是 READ/LIST/COMMAND/WRITE/DONE。它读 README、翻现有测试、自己试着跑命令，直到生成一个“和 issue 无关”的模板测试用例，外加一条能跑通的执行命令。它会反复重试到模板能无异常通过为止。这一步看起来琐碎，却是后面一切的地基——连测试怎么跑都不知道，谈何复现和验证。

子智能体二：Issue Reproducer——先把 bug 真正复现出来

它拿到上一步的模板和命令，再读 issue 描述，写一个能复现 issue 行为的测试——而且这个测试在 bug 修好后，状态会从 fail 翻成 pass。策略仍是 ReAct。这一步是 MASAI 区别于大多数同类工作的灵魂：先复现，再修。复现测试不是摆设，它将在最后成为 Ranker 给补丁排序的“裁判”。

子智能体三：Edit Localizer——别盲改，先定位

它用 ReAct 在仓库里导航，READ/LIST/EDIT/ADD/COMMAND/DONE 全开，找出该改的文件、类、函数，用 EDIT/ADD 把这些位置标记出来。如果 ReAct 跑完没标记任何位置，它就退而求其次，从自己读过的位置里挑一组。论文 RQ3 专门对比了它和朴素的 RAG 检索定位——结果很说明问题（见实验结果）。

子智能体四：Fixer——闭门采样，多出几个候选

这是策略切换最妙的一环。Fixer 拿到 issue 描述和 Edit Localizer 标出的代码片段，没有动作可用，策略换成 CoT，连续采样生成多个候选补丁。为什么用 CoT 不用 ReAct？因为生成补丁是个“想清楚再写”的活，不需要边写边调工具——而且采样多个给后面留出排序空间。这一步是 MASAI 摆脱“一条道走到黑”的关键：与其让 LLM 改一次失败就陷在长循环里反复重试，不如一次性多采几个、最后一起挑。

子智能体五：Ranker——用复现测试当裁判

Ranker 拿到 Fixer 的多个候选补丁和 Issue Reproducer 写的复现测试，把这些补丁逐个跑测试，看哪个能让测试从 fail 翻 pass。能翻的排前面，最终输出排第一的那个补丁。这一步把“复现→修复→验证”真正闭成了环：同一个测试，先复现 bug，后验证修复。论文 RQ4 的数据证明，这个“带测试的排序”比“让 LLM 凭感觉排序”或“随机挑”都强得多。

类比 传统长循环 agent 像一个“从头包到尾”的全能师傅——接车、诊断、拆件、换件、试车全他一个人干，活一多就顾此失彼，工具摊一地，前面拆的螺丝转眼忘在哪儿。MASAI 像一家按工位分工的修车铺：前台只管复现故障、诊断师傅只管找病根、维修师傅只管换件、质检员只管跑测试出报告。每个工位只盯一件事、用最顺手的工具，师傅之间不闲聊，只递交接车单。少说话、多干活，正是 MASAI 刻意避开“多智能体对话”的原因。

05实验结果

MASAI 在 SWE-bench Lite 上用 GPT-4o 当底座，拿到 28.33% 的解决率——当时开源 SOTA，压过 SWE-agent、AutoCodeRover、Aider、OpenDevin 等一众同期工作。但论文最有价值的不是这个总分，而是它把每个设计决策都拆开做了消融，告诉你到底是哪一步在起作用。

发现一：ReAct 定位，远胜朴素 RAG

RQ3 对比 Edit Localizer 的 ReAct 导航和朴素的 RAG 检索定位。结果是：RAG 能定位到 126 个相关位置却只修好 12 个；MASAI 的 ReAct 定位修好 52 个，相对提升 31.7%。结论很直白：定位这步，得让模型主动在仓库里“逛”起来，光靠嵌入相似度检索不够。

发现二：采样+排序，碾压迭代修复

这是全文最漂亮的对照实验（RQ4）。Fixer 一次性采样 5 个候选补丁，再由 Ranker 用复现测试排序——这套打法能恢复“上帝视角”潜能的多少？

选择策略1 个样本5 个样本
Oracle（上帝视角，理论天花板）23.33%35.00%
Random（随机挑）—22.28%
LLM 无测试（让模型凭感觉排序）—23.33%
LLM 带测试（Ranker，本文方法）—28.33%

读这张表要看三个对比。第一，采样多比采样少强：上帝视角下 1 个样本 23.33%、5 个样本 35.00%，多采样把天花板抬高了 12 个百分点。第二，光采样不排序没用：随机挑只有 22.28%，比单采样还低——候选多了反而容易挑错。第三，也是最关键的——复现测试是排序的灵魂：让 LLM 不带测试排序只有 23.33%，几乎没比随机好；可一旦像 MASAI 那样用复现测试当裁判（Ranker），直接飙到 28.33%，吃下了上帝视角 35% 里的一大半。

这张表还顺带戳破了当时一个流行迷信：很多人相信“让 agent 在长循环里反复自我修复”是最强打法。MASAI 用数据反驳了它——与其让模型改一次失败就在循环里反复重试，不如一次性多采几个、最后用测试一起挑。迭代修复会把模型困在失败的上下文里越陷越深，采样+排序则给它一次“重新开始”的机会。

06影响与意义

MASAI 的影响是范式级的，它给 SE agent 圈立了一根新的设计坐标系。

第一，把“模块化”立成默认范式。在它之前，SE agent 主流是“一个长循环 agent”；在它之后，把一个大 agent 拆成定位/修复/验证子模块，几乎成了新工作的默认起点。后续无论是 HyperAgent 的 Planner/Navigator/Editor/Executor，还是各类“定位-修复-验证”三段式工作，都能看到 MASAI 的影子。论文那句“当问题复杂度上升，很难再设计一个能横扫所有情况的单一策略”，成了这个圈子的共识。

第二，把“复现测试”抬到一等公民。在它之前，很多 agent 只在最后被动跑 held-out 测试判输赢；MASAI 把“先复现、再用复现测试排序补丁”做成显式环节，证明了“测试不只是判官，更是排序信号”。这个思路后来被 DEI、Kozuchi 等一众工作继承——测试驱动的候选排序成了 SWE-bench 上的标准操作。

第三，把“分而治之”带进 agent 设计。它和 SWE-agent 的“接口派”、Agentless 的“流水线派”、OpenHands 的“平台派”一起，把 SE agent 的设计空间划出了四个正交维度：接口、流水线、模块、平台。后来者要造新 agent，几乎都得先回答“我站哪个维度、和 MASAI 的模块化差在哪”。

07局限性与未来方向

论文第 7 节标题就叫 Limitations，作者自己也坦承短板。

第一，强依赖复现测试。Ranker 的全部威力来自“能复现 bug 的测试”。可不是每个 issue 都能写出干净的复现测试——有些是性能退化、有些是 UI 行为、有些要复杂环境才能触发。一旦复现写不出来，排序信号就没了，整套打法的红利大幅缩水。论文承认这点，把“弱复现场景下的鲁棒性”列为开放问题。

第二，模块边界是手工设计的。五个子智能体、各自的目标和策略，都是人凭工程直觉定的。这套划分在 SWE-bench Lite 上好用，换到别的任务形态（比如写新功能、做重构）未必最优。如何自动学到“最优模块划分”，论文没回答，留给了后续的动态编排路线（第 44、45 篇的 puppeteer、MAS-Orchestra 正是在接这棒）。

第三，子智能体之间不对话，信息只单向传递。这是优点（省、不跑偏），也是局限——当定位错了，Fixer 只能在错误位置上盲改，Ranker 也只能在错补丁里挑“最不烂的”，没有“回头让 Localizer 重定位”的反馈回路。后来 Reflexion、CRITIC 那条“自我纠正”线，正是补这个缺口。

第四，SOTA 红利短命。28.33% 的开源 SOTA 只守了很短一段时间——Agentless、OpenHands、DEI 等紧随其后。但这恰恰说明模块化思路被迅速吸收和超越了，而不是被否定。MASAI 的价值不在某个分数，而在它立的坐标系。

08领域演进脉络

把 MASAI 放回整个 LLM agent 发展的脉络里看，它的位置是“模块化派”的开山之作。

起步期，ReAct（第 35 篇）确立了“思考-行动-观察”循环范式，那时大家调调搜索引擎、跑跑计算器就心满意足。Toolformer、Voyager 把工具调用焊进模型权重，但场景仍是单文件级的代码生成。真实仓库级这个战场，长期是空白。

2023 年底 SWE-bench 一出，这块空白被显式化——3.8% 的成绩等于在喊“现有 agent 范式不够”。SWE-agent（第 47 篇）接住这棒，把 ReAct 循环落到软件工程环境里，给出 ACI 接口设计框架。Devin（闭源引爆）把“AI 软件工程师”这个词炒热。Agentless（第 48 篇）反手说“别用 agent 也能 SOTA”。OpenHands（第 49 篇）把 agent 做成开放平台。

MASAI 在这条时间线上的位置，是第三条路的开端。它不否定 SWE-agent 的“接口设计”结论，也不否定 Agentless 的“分阶段”结论——它回答的是：“agent 该用，但要按工程师的方式用——先分而治之，再各司其职”。它之后，整个 SE agent 圈形成了四足鼎立的格局：接口派、流水线派、模块派、平台派。下一篇要讲的 DEI，则是从“多样性”这个全新角度，给模块派和流水线派都补了一记重拳——它发现不同的 agent 解的题竟然不一样，组队反而更强。

09趣味延伸

MASAI 这篇论文，背后细节比代码有意思。

第一，名字是个巧妙的双关。MASAI 既是 Modular Architecture for Software-engineering AI 的首字母缩写，又恰好拼成“Maasai”——东非草原上那个以勇敢和集体协作著称的游牧民族“马赛人”。团队有没有意借用这层意思，论文没说，但“分工协作、各司其职”的画面感，和论文的主张惊人地契合。一个缩写同时喊出了“模块化”和“集体协作”，算是起名界的彩蛋。

第二，微软研究院印度的“软件工程 + AI”老牌据点。这篇八位作者全来自 MSR India，通讯作者是 Aditya Kanade 和 Nagarajan Natarajan。MSR India 长期在程序分析、自动推理、软件工程 AI 上深耕，这篇不是孤例——它和后面一连串 SE agent 工作形成了微软在这个方向上的持续投入。值得注意的是，三位一作 Daman Arora、Atharv Sonwane、Nalin Wadhwa 标注“同等贡献、按字母序排列”——这种把功劳平摊给学生作者的标注，在工业研究院里算相当厚道。

第三，示例选得很有戏。论文 Figure 2 用的示例是 scikit-learn 的 issue #13142——两个 GaussianMixture 相关函数行为不一致。选这个当例子有讲究：它不是那种“一眼能看出哪儿错”的简单 bug，但也不至于复杂到看不懂——刚好能让人跟着五个子智能体的流程走一遍，体会“先复现、再定位、再采样、再排序”是怎么一步步收敛的。挑示例的水平，往往比挑方法更能看出一个团队会不会讲故事。

第四，SOTA 只守了一小会儿。28.33% 登顶开源 SOTA 的时候，论文还特意老实写了一句：“这个领域很新、变得很快，图 1 里所有方法都是过去三个月内做出来的。”果不其然，Agentless、OpenHands、DEI 紧随其后就把分数刷上去了。但 MASAI 没有被“分数被超”这件事困住——因为后来者几乎都在用它立的“模块化”坐标系里说话。这或许是论文最体面的结局：SOTA 会被刷掉，坐标系不会被刷掉。

10个人解读与延伸思考

放长视角看，MASAI 的真正贡献不在于 28.33% 这个分数，而在于它给 SE agent 圈立了一根新的设计坐标轴：模块化。

第 47 篇 SWE-agent 证明“接口比 agent 重要”，第 48 篇 Agentless 证明“无 agent 也能 SOTA”，第 49 篇 OpenHands 证明“这个领域要公共地基”。MASAI 证明的是第四件事：agent 该用，但要按工程师的方式用——先分而治之，再各司其职。这四篇合起来，把 SE agent 的设计空间划出了四个正交维度。后来者要造新 agent，几乎都得先回答“我站哪个维度、和别人差在哪”——这种“坐标系”层面的贡献，远比单项跑分值钱。

更深一层，MASAI 和 Agentless 的“对垒”其实不是谁对谁错，而是两个层面的互补。Agentless 回答的是“修 bug 这件具体事，能不能不靠自主决策”——能。MASAI 回答的是“agent 该怎么组织才更高效”——按模块拆、各用各的策略、最后用测试排序。一个在质疑“要不要 agent”，一个在优化“agent 怎么搭”。产业落地的 coding agent（Cursor、Cline、Devin）大多是 Agentless 式的分阶段流水线 + 局部 agent 决策的混合体，但流水线里的每个 agent，几乎都是 MASAI 式的目标单一、策略定制的子模块。换句话说，Agentless 赢了“要不要 agent”这一仗，MASAI 赢了“agent 内部怎么组织”那一仗——它们不冲突，甚至合在一起才是产业最优解。

放到今天看，MASAI 最经得起时间检验的设计，是“复现测试当排序裁判”这一招。在模型还不够强时，靠测试信号从一堆候选里挑最优，是性价比最高的打法。可当模型强到某个临界点——能一次性生成正确补丁、能自己跑测试自我纠正——这套“采样+排序”的红利会不会收窄？这或许是它和 Agentless 共同的“保质期”问题。

留个问题给你 MASAI 的 Ranker 全靠“能复现 bug 的测试”当裁判。可如果一个 issue 根本写不出干净的复现测试（比如“某个图表渲染颜色偏了”），整套排序信号就失效。你觉得这种“弱复现”场景，是该换个排序信号（比如让 LLM 当裁判），还是干脆回到“一个长循环 agent 自己试”？换句话说，当测试信号不可靠时，模块化派还剩什么？

Diversity Empowers Intelligence: Integrating Expertise of Software Engineering Agents

MASAI 把一个 agent 拆成五个子智能体，可 Salesforce AI Research 偏要问另一个问题：如果不同的 agent 解的题根本不一样——Aider 解的、Moatless 解的、Agentless 解的、OpenDevin 解的，解集几乎不重叠——那把它们组队，会不会反杀最强单 agent？他们用 DEI 框架给出答案：一组开源 agent 单兵最高 27.3%，组队后 34.3%，最强组合冲到 55%。论文里那句“一座花园的美，从不只在一朵花”成了点睛之笔。当“模块化派”讲分而治之，“多样性集成派”讲百花齐放——下一篇，看 SE agent 怎么从“分治”走向“集成”。
