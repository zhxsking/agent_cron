大模型经典论文精读系列 #043

Scaling Large Language Model-based Multi-Agent Collaboration MacNet：把 ChatDev 的链式协作升级成有向无环图——支持上千个 agent 的多智能体协作网络，并发现"协作缩放定律"

作者：Chen Qian, Zihao Xie, Yifei Wang, Wei Liu, Kunlun Zhu, Hanchen Xia, Yufan Dang, Zhuoyun Du, Weize Chen, Cheng Yang, Zhiyuan Liu, Maosong Sun 机构：清华大学 / 鹏城实验室 / 北京邮电大学 发表：2024-06 / ICLR 2025
arXiv GitHub OpenReview

2024 年的某天，清华大学自然语言处理实验室里，一个问题被摆上了桌面：神经网络里"加神经元能变强"早已是共识——那如果给一群大模型智能体不断"加同事"，它们会不会也越聊越聪明？

听起来像个职场段子，但这正是 MacNet 要认真回答的问题。在此之前，多智能体研究大多停留在"三五成群"的小打小闹——十个 agent 就算多了，几十个已是极限。ChatDev 用链式对话让 LLM 自己开公司，可一旦 agent 数量上千，对话上下文就会像滚雪球一样撑爆模型窗口。这篇论文要做的，是把这条"单链"拆掉，换成一个能容纳上千节点的有向无环图，并追问：协作，也有缩放定律吗？

一句话总结 MacNet 用有向无环图（DAG）把多智能体协作从"一条链"升级成"一张网"，在拓扑排序的编排下让上千个 agent 有序协作，并发现了一条"协作缩放定律"——性能随 agent 数量呈 S 型增长，且"协作涌现"远早于传统的"神经涌现"。

01领域定位

在前面几篇里，我们已经走过了一条完整的多智能体协作脉络：CAMEL 用角色扮演点燃了两个 agent 的自主对话，ChatDev 把对话焊成了软件开发流水线，Experiential Co-Learning 又给流水线装上了"经验记忆"。但这些工作的协作结构都是"链式"的——A 告诉 B，B 告诉 C，一条路走到黑。

MacNet 站在这条脉络的"瓶颈口"上：它承接了 ChatDev 的 instructor-assistant 双角色范式，但要解决的核心矛盾是——链式结构无法扩展。一旦 agent 超过几十个，要么上下文爆炸，要么信息在长链中层层损耗。MacNet 的回答是：用图论里的有向无环图替代链，让协作从"一条线"变成"一张网"。同时，它把"缩放定律"这个大模型训练阶段的黄金法则，第一次搬到了推理阶段的多智能体协作上。

02研究背景

要理解 MacNet 为何出现，得先回到一个更根本的问题：为什么需要多个 agent 协作？

单个大语言模型虽然强大，但有三个绕不开的短板：一是上下文窗口有限，长任务塞不进去；二是"一个人做所有事"容易顾此失彼，写代码时还要兼顾测试、文档，注意力被摊薄；三是缺乏外部反馈，闭门造车容易跑偏。多智能体协作正是为了解决这些：让不同的 agent 扮演不同角色，通过对话互相提点、分工、纠错。

但问题也随之而来。早期的多智能体框架（如 ChatDev、AutoGen）几乎都采用"链式"结构——agent A 把结果交给 B，B 交给 C，像工厂流水线一样单向推进。这种结构在小规模下很好用，但一旦你想"加人手"，就会遇到三道墙：

  • 上下文爆炸：每经过一个 agent，对话历史就越滚越长，几十轮下来 token 数就突破模型窗口上限。
  • 信息损耗：在长链末端，最初 agent 产出的细节早已在层层转述中被稀释。
  • 结构僵化：一条链只能走一条路，无法并行探索多个方案，也无法让中间结果"回流"做交叉验证。
类比 想象一个 50 人的公司，但所有人只能排成一列纵队传话——CEO 跟 CTO 说，CTO 跟架构师说，架构师跟前端说……传到最后一个实习生时，CEO 最初的需求早就面目全非了。而且任何一个人请假，整条线就断了。MacNet 要做的，就是把这个"纵队"打散重组，变成一张有明确汇报关系但能并行运作的协作网络。

与此同时，论文的灵感来源也值得一提。大模型领域有一条著名的"neural scaling law"（神经缩放定律）：模型的损失（loss）与参数量、数据量、训练算力呈幂律关系——参数越多、数据越多，模型越强。Kaplan 等人在 2020 年提出的这条定律，直接推动了 GPT-3 到 GPT-4 的军备竞赛。MacNet 的作者们提出了一个大胆的类比：如果把"增加神经元"换成"增加协作 agent"，会不会也有类似的缩放规律？在训练阶段靠堆参数，在推理阶段靠堆 agent——这条路走得通吗？

03核心问题

把上面的背景浓缩成一句话，MacNet 要解决的核心问题是：

如何设计一个可扩展到上千个 agent 的多智能体协作框架，使性能随 agent 数量的增加而持续提升，同时不突破上下文窗口的物理限制？

这个问题其实拆成了三个子问题：第一，用什么结构来组织上千个 agent？第二，怎么编排交互才能既有序又不撑爆上下文？第三，加 agent 到底有没有用——如果有，规律是什么？

思考一下 如果你要让 1000 个 agent 协作完成一个任务，你会怎么组织它们？是让所有人讨论（全连接），还是排成一条长链，还是……？先想想你心目中的"最优结构"，再往下看论文给出的答案。

04方法详解

MacNet 的方法可以拆成三步：建网（网络构造）、排序（交互推理）、控量（记忆控制）。三步环环相扣，共同解决了"上千 agent 不爆炸"的难题。

第一步：用有向无环图（DAG）建网

MacNet 的第一个关键决策是：把 agent 之间的协作关系建模成一个有向无环图（Directed Acyclic Graph，DAG）。"有向"意味着信息有明确的流动方向——从上游 agent 流向下游；"无环"意味着不存在循环依赖——A 依赖 B、B 依赖 C，但 C 不能再依赖回 A，否则就会死锁。

形式化地，一个 MacNet 拓扑记为 $\mathcal{G}=(\mathcal{V},\mathcal{E})$，其中 $\mathcal{V}$ 是节点集合，$\mathcal{E}$ 是有向边集合：

$$ \mathcal{V}=\{v_{i}\mid i\in I\},\quad \mathcal{E}=\{\langle v_{i},v_{j}\rangle\mid i,j\in I\wedge i\neq j\} $$ (1)

论文研究了三大类拓扑结构，细分为六种变体：

  • 链式（chain）：线性串联，最接近原始 ChatDev。
  • 树式：又分"扁平"的星形（star）和"深递归"的树形（tree），允许一个 agent 把结果分发给多个下游。
  • 图式：最灵活，又分全连接网格（mesh）、分层 MLP 结构（layered）和随机不规则结构（random）。

但光有拓扑还不够。论文借鉴了 ChatDev 的核心设计——功能二分（functional dichotomy），把每个 agent 分成两种角色：

  • 监督者（instructor）：分配在边上，负责向下游发出指令——"你需要解决什么、改进什么"。
  • 执行者（assistant）：分配在节点上，负责根据指令产出具体的解决方案。

这个分配通过一个"agent 化"操作 $\rho(\cdot)$ 完成——给基础模型装上专业角色、外部工具和上下文记忆：

$$ \bm{a_{i}}=\rho(v_{i}),\ \forall v_{i}\in\mathcal{V};\qquad \bm{a_{ij}}=\rho(\langle v_{i},v_{j}\rangle),\ \forall\langle v_{i},v_{j}\rangle\in\mathcal{E} $$ (2)

也就是说，节点上是干活的，边上是发指令的。这种二分让角色各司其职，也让"有向"边有了明确的语义——边上的 instructor 告诉下游的 assistant 该做什么。

第二步：拓扑排序编排交互

有了网络，下一个问题是：谁来先说话？一千个 agent 总不能同时开口。MacNet 借用了图论里的一个经典算法——拓扑排序（topological ordering）。

拓扑排序的规则很简单：每个节点只有在它所有的上游依赖都被处理完之后，才会被访问。这就保证了信息流动的有序性——下游 agent 一定是在拿到上游所有结果之后才开始工作，不会出现"还没收到指令就开始瞎做"的情况。

类比 拓扑排序就像项目管理里的"前置任务表"：任务 C 依赖 A 和 B 的产出，那 C 一定排在 A、B 之后执行。MacNet 的拓扑排序就是给整张 DAG 生成一张"执行时刻表"，让每个 agent 知道自己什么时候该上场。

在每一轮交互中，只有相邻的两个 agent参与——边上的 instructor 向下游的 assistant 下达指令，assistant 根据上游传来的"工件"（artifact，可以是代码片段、推理结论、文本草稿等）进行精炼（refine），然后把精炼后的工件继续往后传。

第三步：只传工件，不传对话——记忆控制

这是 MacNet 能扩展到上千 agent 的真正秘诀。在传统的链式协作中，每个 agent 的完整对话历史都会传递给下游，上下文像滚雪球一样越来越长。MacNet 做了一个看似简单却关键的决定：

只把精炼后的工件传给下游邻居，不传完整对话。

也就是说，每个 agent 只看到上游传来的"成品"，而看不到上游 agent 之间漫长的讨论过程。这就把每个 agent 的上下文长度控制在了局部范围内——无论整个网络有多大，单个 agent 处理的 token 数始终是可控的。正是这个设计，让 MacNet 能在全连接的密集网络中支持超过一千个 agent而不会撑爆窗口。

05实验结果

MacNet 的实验设计围绕三个递进的问题展开，每一个都给出了令人意外的发现。

发现一：MacNet 全面超越基线

在四个异构任务上，MacNet 的链式结构平均性能就已经优于所有基线方法。论文对比了 CoT（思维链提示）、AutoGPT 和 GPTSwarm，覆盖逻辑推理（MMLU）、代码生成（HumanEval）、软件开发（SRDD）和文本生成（CommonGen-Hard）四类场景。

任务场景数据集能力维度MacNet 表现
逻辑推理MMLU多选题准确率优于全部基线
代码生成HumanEval函数级编程优于全部基线
软件开发SRDD仓库级软件优于全部基线
文本生成CommonGen-Hard受约束生成优于全部基线

发现二：不规则拓扑反杀规则结构——小世界现象

这是论文最反直觉的发现之一。直觉上，全连接的网格结构（mesh）应该最强——毕竟每个 agent 都能和所有其他 agent 交互。但实验结果恰恰相反：随机的不规则拓扑性能优于规则结构，包括链、树和全连接网格。

作者将其命名为"小世界协作现象"（small-world collaboration phenomenon）——那些拓扑结构接近小世界网络特性的，表现最好。原因是：随机连接缩短了信息传递的路径长度，减少了工件在长链中层层转述的损耗；同时，随机拓扑比密集的全连接网格少了 51.92% 的耗时，因为交互轮次更少。

此外，论文还发现拓扑的"方向性"很重要：发散型拓扑（子节点多于父节点）优于收敛型拓扑——因为让多个 agent 同时处理一个工件再分发，比把多个 agent 的结果汇聚到一个节点更容易。

发现三：协作缩放定律——S 型曲线与协作涌现

这是论文最具理论深度的贡献。当作者把 agent 数量从几个逐步增加到上千个时，性能呈现出一条漂亮的 S 型曲线（logistic growth）——初期缓慢上升，中期急剧拉升，后期趋于饱和（约 100 个 agent 时接近饱和）。

更令人惊讶的是对比：协作涌现的出现时间远早于神经涌现。传统神经缩放定律需要数十亿参数、海量训练数据才能看到性能跃升；而 MacNet 的协作涌现只需几十到上百个 agent 就能触发。作者给出的解释是：agent 不需要从零学习——它们底层的 LLM 已经预训练了海量知识，agent 之间的交互只是在激活和传播这些已有知识，通过反思和精炼让多维度的考量汇聚成更全面的方案。

06影响与意义

MacNet 的影响可以从三个层面来理解。

第一，工程层面：它把多智能体协作的规模上限从"几十个"推到了"上千个"，这直接回答了"加 agent 有没有用"这个被忽视的问题。"只传工件不传对话"的记忆控制策略，至今仍是大规模 agent 系统控制上下文长度的标准思路。

第二，理论层面：它把缩放定律从训练阶段（堆参数、堆数据）扩展到了推理阶段（堆 agent、堆协作）。这条"协作缩放定律"的 S 型曲线和"协作涌现早于神经涌现"的发现，为后续研究提供了可预测的资源-性能关系——你想知道加多少 agent 能达到什么性能，不再是拍脑袋，而是有了一条拟合曲线。

第三，生态层面：MacNet 直接被集成进了 ChatDev 的 macnet 分支，成为 OpenBMB 生态中多智能体协作的核心基础设施。后续同一团队的"puppeteer"（木偶师）范式进一步把静态 DAG 升级为可学习的动态编排器，正是建立在 MacNet 的基础之上。

07局限性与未来方向

MacNet 虽然打开了大规模协作的大门，但它本身也留下了几个明显的缺口：

  • 静态拓扑：DAG 结构是预先设定的，不会根据任务难度或中间结果动态调整。一个简单任务也用 100 个 agent，一个复杂任务可能还是同一张图。后续的 puppeteer 工作正是用强化学习训练一个"中央调度器"来动态编排，补上了这一短板。
  • 延迟代价：上千个 agent 意味着上千轮 LLM 调用。第三方测评显示，100 个 agent 时响应时间可达单 agent 的 2.3 倍。在延迟敏感的场景中，这不是免费的午餐。
  • 饱和效应：S 型曲线意味着加 agent 的收益会递减。论文发现约 100 个 agent 后性能趋于饱和——盲目堆 agent 并不经济，如何选"最优 agent 数"仍需进一步研究。
  • 拓扑搜索空间：论文只测了六种代表性拓扑，而 DAG 的可能结构是天文数字。哪种拓扑对哪类任务最优，还需要更系统的搜索。

08领域演进脉络

从大模型发展全貌来看，多智能体协作是一条与"模型训练"并行的技术线。它的演进可以这样梳理：

起步期（2022–2023）：ReAct 确立了"思考-行动"的循环范式，单个 agent 开始具备与环境交互的能力。Chain-of-Thought 和 Self-Consistency 让推理能力涌现，为多 agent 协作提供了"会思考的零件"。

协作萌芽期（2023 上半年）：CAMEL 用角色扮演让两个 agent 自主对话，点燃了多智能体协作的火种。AutoGen 提供了通用的对话框架。

工程化期（2023 下半年）：ChatDev 把对话焊成软件开发流水线，MetaGPT 用 SOP 工程化多 agent 分工。这个阶段的结构以链式为主。

规模化期（2024）：MacNet 出场——用 DAG 替代链，支持上千 agent，发现协作缩放定律。这是多智能体从"小作坊"走向"大规模系统"的转折点。

动态化期（2025）：puppeteer 把静态拓扑升级为 RL 训练的动态编排器，标志着协作网络开始自己学会怎么组织自己。

MacNet 正好处在"规模化期"的起点上——它回答了"能不能扩"的问题，同时为"怎么动态扩"留下了入口。

09趣味延伸

MacNet 背后有一个有趣的"传承"故事。这篇论文的一作 Chen Qian（钱辰）和通讯作者 Maosong Sun（孙茂松）来自清华大学自然语言处理实验室，而这正是 ChatDev 的诞生地。也就是说，MacNet 是 ChatDev 团队给自己的"链式结构"做的一次自我革命——他们亲手推翻了自己上一代作品的核心设计。

更有意思的是论文的代码仓库。MacNet 并没有新建一个独立 repo，而是直接开在了 OpenBMB/ChatDev 的一个分支 macnet 上。这种"在自家后院搞升级"的做法，透露出一种务实的工程师气质：不追求炫酷的新品牌，而是在已有生态上迭代演进。后来 puppeteer 同样开在 ChatDev 的 puppeteer 分支上——一条技术线、一个仓库、三代演进。

还有一个值得一提的细节：论文里有一个概念叫"工件"（artifact），指的是 agent 之间传递的中间产物。这个词来自软件工程领域——在软件开发中，"artifact"通常指编译后的二进制文件、文档或测试报告。MacNet 把它借过来，泛指 agent 产出的任何形式的中间结果。这个术语的选择透露了论文的工程底色：它把多智能体协作当成了一条软件生产线来设计。

还有一个有趣的现实映射：MacNet 的"小世界现象"与社会学里的经典理论遥相呼应。社会学家马克·格兰诺维特（Mark Granovetter）在 1973 年提出过"弱关系的力量"——在社交网络中，信息和机会往往不是通过紧密的小圈子传播的，而是通过那些"弱连接"的远距离关系跨越社群边界。MacNet 的发现异曲同工：随机的、不那么紧密的连接，反而比全连接更高效——因为全连接带来的是信息冗余和过载，而随机连接保持了"路径短"和"信息多样"的平衡。AI 的多智能体协作，竟然也遵循着人类社会的网络智慧。

10个人解读与延伸思考

MacNet 最让我震撼的不是"上千个 agent"这个数字，而是它揭示的一个深层洞察：缩放定律不只属于训练阶段。过去几年，整个行业都沉浸在"堆参数、堆数据、堆算力"的范式里——GPT-3 到 GPT-4 到 GPT-5，千亿参数、万亿 token。MacNet 提出了一条不同的路：在推理阶段，通过增加协作 agent 来扩展能力。

这意味着什么？意味着算力的使用方式正在分化。一部分算力用于训练更大的模型（训练缩放），另一部分算力用于在推理时跑更多的协作 agent（推理缩放）。这和 o1 开启的"测试时缩放"（test-time compute scaling）思路异曲同工——只是 o1 缩放的是单个模型的思考链长度，MacNet 缩放的是 agent 的协作规模。两条路殊途同归，都在说同一件事：推理阶段也有缩放空间，而且可能比训练阶段更便宜。

但 MacNet 也留下了一个值得深思的张力：S 型曲线意味着收益递减。100 个 agent 之后再加人，性能提升微乎其微。这和职场的直觉是一致的——一个 5 人精干小组的产出，往往高于一个 50 人的臃肿团队。那么，真正的挑战不是"能不能扩"，而是"什么时候该停"。MacNet 给了曲线，但"最优 agent 数"的选择仍然是一个开放问题——它可能取决于任务复杂度、模型能力、拓扑结构和成本预算的联合优化。

最后，"小世界现象"的发现让我对 AI 协作的未来多了一份乐观。它暗示着：最有效的协作结构不是高度集权的全连接，也不是松散无序的各自为政，而是介于两者之间的"小世界"——既有紧密的局部协作，又有跨越远距离的随机连接。这与人类最成功的组织形态惊人地一致。也许，当 AI 学会协作时，它最终也会发现人类几千年文明摸索出的那个道理。

留个问题给你 如果"协作缩放定律"是 S 型曲线，100 个 agent 后就接近饱和，那你认为影响饱和点位置的关键因素是什么？是模型能力、任务复杂度、拓扑结构，还是别的什么？换句话说——什么决定了"加到多少 agent 就该停"?
