SWE-Replay: Efficient Test-Time Scaling for Software Engineering Agents SWE-Replay：绕开价值函数，从历史轨迹里挑关键步重放——比 SWE-Search 更省更准的 SWE agent 测试时算力扩展

作者：Yifeng Ding, Lingming Zhang 机构：Siebel School of Computing and Data Science, University of Illinois Urbana-Champaign 发表：2026-01 / arXiv（ICML 投稿）
arXiv

上篇 SWE-Search 把蒙特卡洛树搜索塞进 SWE agent，换来的是平均 23% 的相对提升——但代价是 14 倍的采样成本。14 倍！这意味着跑完一个 SWE-bench 任务，agent 可能要在仓库里反复"列目录、读 README、打开同一个入口文件"几十次，每次都从第 0 步开始。你看着 token 账单蹭蹭往上涨，心里只剩一个念头：它刚才不是已经看过这个文件了吗？

更扎心的是，SWE-Search 想省钱，靠的是再养一个"价值 agent"给每一步打分、提前剪枝。可这个打分员自己也是个 LLM，它会判错方向——把对的岔路口标成死胡同，把死胡同当成金矿往里扎。而且它只认"流水线式"的固定工具调用，碰上会自己现场写 bash 脚本的现代 agent（比如 SWE-agent）就抓瞎了。这篇 SWE-Replay 抛出的问题就一句话：能不能不靠任何 LLM 当评委，照样把测试时算力扩展做得又省又准？

一句话总结 SWE-Replay 不再每次从头采样，而是把跑过的轨迹存进"档案库"，按"探索稀有程度 + 推理段落数"挑出关键中间步，在它之前恢复环境、在它之后换一条路重放——既绕开了价值函数、又能用在任意现代 agent 上，在 SWE-Bench Verified 上把成本砍掉最多 17.4%，性能反而涨了最多 3.8%。

01领域定位

这是 SWE agent 支线的第七篇，也是测试时算力扩展这条小脉络的第二个拐点。第 047 篇 SWE-agent 立了"人机接口"标杆，第 048 篇 Agentless 反问"那连 agent 都不要行不行"，第 049 篇 OpenHands 把 agent 做成开放平台，第 050 篇 MASAI 把一个 agent 拆成五个子智能体，第 051 篇 DEI 把多个 agent 编成"评审委员会"，第 052 篇 SWE-Search 把 MCTS 装进 agent 让它"边走边回溯"。前六篇都在回答"怎么造/挑/搜一个更好的 agent 或补丁"，而 SWE-Search 已经把重心推到了"测试时多采样换性能"这条新轴上。

SWE-Replay 站在 SWE-Search 的肩膀上，却做了一个看似更朴素、实则更彻底的选择：它不养价值 agent、不搞树搜索，而是把已经跑过的轨迹当资产重用——从中间某个"值得重新想想"的步骤分叉出去。这把测试时扩展从"靠外部裁判剪枝"拉回到"靠经验重放省力"，是这条小脉络从"加评委"走向"复用历史"的拐点，也为后面"训练时自博弈"打开了思路。

02研究背景

测试时扩展（test-time scaling）的核心思路很朴素：同一个任务，让 agent 多跑几遍、多采几条轨迹，再用测试反馈从里面挑一个能跑通补丁的解。Brown 等人早在 2024 年就观察到，SWE 任务的解决率随采样数对数线性上升——多采一条，多一份希望。听起来很美，直到你算算账：每采一条轨迹，agent 都要从第 0 步开始，把"列目录、读 README、打开入口文件"这一套前戏再走一遍。SWE agent 单条轨迹动辄几十步、每步几千 token，采 16 条就是 16 倍的重复浪费，而且这些重复几乎不产生新信息——前 5 步看到的仓库，第 16 次看到的时候还是那个仓库。

省钱的路子并不是没人走过。SWE-Search 用 MCTS 配一个"价值 agent"给每步打分，提前剪掉看着不行的分支；Satori-SWE 让 agent 自己给自己之前生成的轨迹打分，靠"自我改进"少采几条。但这俩兄弟有两个共同的、也是致命的毛病：

  • 评委自己也会出错。价值 agent 和奖励模型本质都是 LLM，它们对中间步的估计会有校准偏差（miscalibration）——把好岔路口判成死路，于是正确的解被提前剪掉；把死胡同当成金矿，于是算力继续往里砸。一句话，裁判不可靠，剪枝就是赌博。
  • 评委只认固定工具。这些方法都是给"流水线式"agent 设计的——那种 agent 调用的是预设好的"结构化搜索/检索工具"，评委只要照着工具模板写个 prompt 就能给分。可现代 agent（比如 SWE-agent）不一样，它自己现场写 bash 脚本当工具用，这次写个 grep -rn，下次写个 find . -name，没有模板可套。评委连"这一步在干嘛"都看不懂，更别说打分了。
类比 把测试时扩展想象成"派 16 个实习生去摸同一个仓库"。naive 做法是 16 个人各自从大门口排长队登记、领门禁卡、再走到工位——前 5 步的动作一模一样，纯属浪费时间。SWE-Search 的做法是再雇一个"领班"站在门口给每个人打分，看着不行就让他别进去了——可领班自己也看走眼，而且他只会照着"标准访客登记表"打分，碰上自己临时写脚本干活的实习生就懵了。SWE-Replay 干的是另一件事：让前一个实习生把走过的路记下来，后面的实习生从某个关键岔路口接着走，不用每次从大门口重新排。

03核心问题

能不能在不依赖任何 LLM 评委、不限定 agent 架构的前提下，让测试时扩展少跑重复的前戏、把算力花在真正该多想几遍的关键步上——同时还不掉点性能？更直白地说：能不能不养裁判、也能省下那 14 倍里大部分的冤枉钱？

思考一下 如果你是个老程序员，被派去修同一个 bug 16 次，你第二次起会怎么"复用"第一次的经验？你会从哪一步开始换路？是越早换越好（省的事多），还是越晚换越好（已经摸清的部分别浪费）？先想想看，再往下读 SWE-Replay 的答案。

04方法详解

SWE-Replay 的核心直觉一句话：已经走过的路不必再走，值得多想几遍的岔路口才该多采几条。它维护一个"轨迹档案库"（archive），初始放一条从零采的轨迹进去，然后反复做一件事——按概率决定这次是"从头探索一条新路"（explore），还是"从档案里挑一条旧轨迹、在某个关键中间步之前恢复环境、之后换条路重放"（exploit）。新采的轨迹再塞回档案，循环往复。整个过程没有一个 LLM 评委出场，挑哪一步完全靠两个轻量信号：这步能带 agent 去多稀罕的地方、这步背后藏了多少真正的推理。

下面把 exploit 这条路拆成三步讲清楚：怎么挑步、怎么重放、怎么分叉。

第一步：挑出值得重放的关键中间步

挑步是整篇文章最精巧的地方。SWE-Replay 用了一个四级流水线，从粗到细地筛出"该在哪儿换路"——而且全程不问任何 LLM"这步好不好"。

① 过滤掉引入回归失败的轨迹。档案库里不是每条轨迹都值得重用。SWE-Replay 先把那些最终补丁把仓库里原本能过的测试搞挂的轨迹整个删掉。理由很实在：会引入回归的轨迹，往往中间就埋着"看了不该看的文件"这种误导性步骤，重用它们只会把同样的错再传一遍。它借用 Agentless 的办法从仓库里抽现有回归测试来判，不用 LLM、也不信 LLM 生成的测试（那些自己都不一定对）。这一步是粗筛，把坏账先清出库。

② 用"文件级抽象"给步骤分组，按稀有度抽组。这是最关键的一步。直接拿原始环境输出当"状态"来比相似度不行——那玩意儿又长又几乎独一无二，比不出有意义的"同一类"。SWE-Replay 的取巧办法是：把每一步用一个轻量抽象表示——在这步之前 agent 已经看过哪些文件（一个文件集合）。这样一来，所有"看到过同样一组文件"的步骤就被归到同一个抽象状态 s_i。然后，它按"稀有度"给每个状态分一个采样概率——被更少步骤到达的状态，更值得回去再探：

$$ p_i = \mathrm{softmax}\!\left(\frac{1}{v_i}\right) = \frac{e^{1/v_i}}{\sum_{j=1}^{n} e^{1/v_j}} $$ (1)

这里 v_i 是落在状态 s_i 里的具体步骤数。v_i 越小（到这儿的步骤越少），1/v_i 越大，这个状态被选中的概率就越高。用 softmax 而不是贪心选最稀有的，是为了保留采样多样性——附录 A.7 验证了 softmax 比硬挑效果更好。一句话：这一步把"该多探哪片仓库"用文件访问频率这个客观信号回答了，完全不靠 LLM 评分。

③ 在组内按"推理段落数"挑具体那一步。选定一个抽象状态后，组里可能还有好几步都到达过它。SWE-Replay 在这些步骤里挑推理最密集的那一步作为分叉点。直觉是：需要 agent 多想几段话才决定下一步的，往往是关键决策点，在这里换条路最有希望走出新解。这里有个特别精巧的反直觉点——它不用推理的原始 token 长度，而用段落数。原因是：推理内容里常常夹杂大段复制的代码片段、原始输入，这些把 token 数撑得很长却几乎不带来"思考密度"。论文举了个对照：第 19 步推理文本更长，但内容是两份详尽却信息量低的编辑草稿；第 18 步短得多，却是好几段精炼地分析程序逻辑的洞察。消融实验也证实：段落数（60.0%）压过原始 token 长度（58.0%），结构化切分比堆字数更能反映思考质量。

④ 用随机采样平衡探索与利用。前三步挑出了"一个状态 + 状态里推理最密的那一步"，但 SWE-Replay 不会每次都铁定去 exploit 这一步。它用一个概率在"从头采条新的"和"从这步分叉"之间二选一，避免过早锁死在某条看似稀有的路径上。这是整条流水线最朴素也最稳的一环——不贪心、靠掷骰子留余地。

第二步：在挑中的步之前恢复环境

挑好分叉点 s_t 后，不能直接让 agent 从那儿继续——agent 跑 SWE 任务时改的是真实文件系统、跑的是真实命令，环境状态（哪些文件被改过、当前工作目录、git 状态）都得对上。SWE-Replay 的做法是把这条轨迹在 s_t 之前那一系列动作（s_1, s_2, …, s_{t-1}）重放一遍，把环境恢复到分叉前的样子。这一步看着朴素，却是省钱的真正来源——前面那些"列目录、读 README"的动作只跑一次（在重放时），后续所有分叉都从这个已恢复的状态接着走，重复的前戏只演一遍。

第三步：在分叉点采一个新动作

环境恢复好之后，SWE-Replay 让 agent 在 s_t 这一步重新采样一个新动作 s'_t，替换掉原来的 s_t，然后接着往下探索。带温度采样让这个新动作大概率走和原来不同的路——这正是"重用历史但不复读历史"的关键：前面的共识部分复用、在这一步换思路、之后又自由展开。新采出来的轨迹塞回档案库，下一轮可能又被挑中做新的分叉点。整个机制不靠任何打分，只靠"哪些文件被看得少"和"哪步推理想得多"两个客观信号——也正是它能在 SWE-agent 这种"自己写 bash"的现代 agent 上跑通的根本原因。

05实验结果

论文在 SWE-Bench Verified（主流基准）、SWE-Bench Pro（更难、更接近真实分布）和 SWE-Bench Multilingual（多语言）三个基准上验证。结果可以拆成"省钱"和"不掉点甚至涨点"两条线看。

基准 / 维度naive 从头采SWE-Replay变化
SWE-Bench Verified 成本baseline−17.4%（最多）省钱
SWE-Bench Verified 解决率baseline+3.8%（最多）涨点
SWE-Bench Probaseline一致更省/更准可迁移
SWE-Bench Multilingualbaseline一致更省/更准可迁移
覆盖的 LLM 后端—3 种稳健
覆盖的 agent 脚手架—2 种稳健

几个值得拎出来说的发现：

  • 省钱和涨点居然能同时发生。常见的省成本方法都是"砍掉一些采样换来掉点"，SWE-Replay 却是少花钱反而多解题——它把省下来的算力投到了"稀有文件区"和"高推理步"上，命中正确解的概率反而更高。
  • 消融把"段落数 > token 长度"坐实。把推理强度的度量从段落数换成原始 token 长度，性能从 60.0% 掉到 58.0%——一个看似微不足道的"怎么数思考量"的小决定，带来 2 个点的差距。
  • 它真的把探索推向了长尾。论文专门分析了 agent 访问文件的分布：naive 采样的轨迹反复在少数热门文件上打转，SWE-Replay 则明显把访问推向访问频率更低的长尾文件——这正是"按稀有度抽状态"在数据上的直观体现。
  • 跨 agent、跨模型都成立。3 个不同 LLM 后端、2 种不同 agent 脚手架都一致地显示出成本下降、性能不降反升，说明这套机制不是某个特定 agent 的奇技淫巧，而是普适的复用规律。

06影响与意义

SWE-Replay 是第一个不依赖任何 LLM 评委、又能用在任意现代 agent 上的高效测试时扩展方法。这件事的意义不止于"又省了点钱"：

  • 它把"评委"从测试时扩展里彻底摘出去。SWE-Search 和 Satori-SWE 都得养一个会失准的裁判，SWE-Replay 证明了——靠"文件访问稀有度"和"推理段落数"两个客观、可观测、不靠模型估计的信号，就能挑出值得重放的步。测试时扩展不需要再带一个会出错的模型当评委。
  • 它打通了现代 agent 这道坎。SWE-agent 这种"自己写 bash"的灵活 agent 之前没法用 MCTS 式的方法省力，因为评委看不懂它临时写的脚本。SWE-Replay 的挑步信号不依赖工具语义，天然适配任何脚手架，3 个 LLM 后端、2 种脚手架的稳定结果就是证据。
  • 它把"探索推向长尾"的洞察为后续工作铺了路。长尾文件往往是冷门但真正藏 bug 的地方，SWE-Replay 用稀有度信号把算力往那儿引——这个思路可以接上后面"训练时自博弈"的工作：让 agent 自己学会主动去看那些不容易看到的角落。

07局限性与未来方向

SWE-Replay 不是银弹，论文自己也点出了几条软肋：

  • 过滤还得靠现有回归测试。第①级筛选用仓库自带的回归测试判定轨迹好坏，可不少仓库根本没有像样的回归测试套件——这一步在测试稀疏的项目上会失灵。用 LLM 生成测试又回到"信不信 LLM"的老问题，论文选择不用是对的，但留下了空白。
  • 档案库的开销随轮次增长。每采一条新轨迹都入档，档案库越滚越大，挑步的代价也水涨船高。长时间运行下，需要更好的档案管理/淘汰策略，否则省钱效果会被挑步成本吃掉。
  • 它仍在"测试时"打转。重放是在推理阶段复用历史，没把"哪些步值得多想"这件事焊进模型权重。一个自然的下一步是：能不能把这些"高价值分叉点"当成训练信号，让 agent 在训练时就学会主动往稀有文件区探？这正是后面 Self-play SWE-RL 这类工作要接的棒。

08领域演进脉络

把 SWE agent 这条支线拉长看，能看出一条很清晰的"重心迁移"曲线：从"造一个 agent"（SWE-agent → OpenHands），到"挑一个 agent"（DEI 委员会投票），到"搜一个 agent"（SWE-Search 上 MCTS），再到本篇"重放一个 agent"（SWE-Replay 复用历史）。每一步都在回答"怎么用得起更多算力"——naive 多采贵，SWE-Search 加评委也贵还失准，SWE-Replay 干脆不请评委、复用历史，把成本压到最低的同时性能反超。

但所有这些方法都还停留在推理时。下一棒很自然会问：能不能把"该多探哪片仓库、该在哪步多想"这件事训练进模型，让 agent 一上来就自觉往稀有文件区看？这就从测试时扩展跨进了训练时自博弈——也是下期要讲的方向。

09趣味延伸

SWE-Replay 的两位作者 Yifeng Ding 和 Lingming Zhang 都来自 UIUC 的 Siebel 计算与数据科学学院。熟悉 SWE agent 支线的读者会注意到一条隐藏的"师承链"：SWE-Search 的作者里也有 Lingming Zhang——也就是说，SWE-Replay 直接出自 SWE-Search 同一个课题组。这就不难理解为什么 SWE-Replay 对 SWE-Search 的痛点（评委失准、不通用）抓得这么准：它是"自己人拆自己的台"，精准踩在上一作的局限上做改进。这种"同一课题组前作立靶、后作补刀"的节奏，在 SWE agent 这条支线上已经不是第一次了。

另一个值得一提的小细节是"段落数打败 token 长度"那个消融。这是个特别有"软件工程直觉"的发现——思考的密度不等于思考的字数。一个工程师写一大段贴满原始代码的"分析"，往往不如几段干净利落的逻辑拆解。SWE-Replay 用段落数当代理，等价于承认"会分段的人，通常是想得更清楚的人"。这种把人类写作直觉塞进 agent 评估的小决定，是这篇论文最有人情味的地方。

10个人解读与延伸思考

读完整篇，我最大的感受是 SWE-Replay 做了一个非常"克制"的选择。它没有引入任何新模型、没有训练任何东西、没有搞复杂的搜索算法——它只是把已经跑过的轨迹当资产，配两个不依赖 LLM 的轻量信号挑出关键步。这种"少即是多"的姿态，在一片"再加一个 agent、再训一个评委"的喧嚣里显得格外清醒：很多时候，省钱的钥匙不在于更聪明的裁判，而在于别让前人走过的路白走。

更值得玩味的是它对"思考密度"的处理。用段落数而不是 token 长度度量推理强度，看似是个工程小细节，背后其实藏着一种对人写作直觉的尊重——会分段的人，多半是想得更清楚的人。这种"把人类表达直觉当代理信号"的思路，可能比再训一个奖励模型更稳、更便宜，也更不容易过拟合。

展望一下：SWE-Replay 把"哪些步值得多想"这件事留在了推理阶段。下一步很自然是把这些高价值分叉点当成训练数据，让 agent 在训练时就学会主动往稀有文件区探——也就是从"测试时重放"走向"训练时自博弈"。当测试时扩展的复用规律被摸清之后，把它焊进权重只是时间问题。

留个问题给你 如果 SWE-Replay 的档案库无限增长下去，挑步的代价会越来越高。你觉得该用什么策略淘汰档案里的旧轨迹？是按"最近被重放次数"淘汰（冷门轨迹反而留着），还是按"最终是否跑通"淘汰（只留成功的）？这两种策略各自会把探索推向哪个方向？想想看，下篇可能会给你一个相关的答案。
