AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation Framework AutoGen：把多智能体协作变成"可编程的对话"——微软的通用多智能体框架，与 MetaGPT 的"流水线派"分庭抗礼

作者：Qingyun Wu, Gagan Bansal, Jieyu Zhang, Yiran Wu, Beibin Li, Erkang Zhu, Li Jiang, Xiaoyun Zhang, Shaokun Zhang, Jiale Liu, Ahmed Hassan Awadallah, Ryen W. White, Doug Burger, Chi Wang 机构：Microsoft Research, Pennsylvania State University, University of Washington, Xidian University 发表：2023-08 / arXiv（ICLR 2024 LLM Agent Workshop 最佳论文）
arXiv GitHub

上一篇 MetaGPT 给多智能体立了规矩：不许闲聊，每个人按 SOP 交出固定格式的文档，像软件公司流水线那样一节一节往前推。效果确实好——HumanEval 85.9%、任务完成率 100%，组织方式本身就是增益。可规矩太硬，总有人不服气：要是任务没法预先拆成几道工序呢？要是中途要换人、要拉个人进来拍板呢？要是 agent 之间的来回本身就是干活呢？

同一个 2023 年夏天，微软研究院抛出了另一个极端的答案：别急着定流程，先把"对话"这件事做成可编程的基础设施。agent 可以是 LLM，可以是人，可以是工具，甚至三者合一；它们怎么聊、谁先说话、要不要喊人，全都交给开发者用自然语言和代码灵活定义。这篇论文叫 AutoGen，它不押"流水线"，它押"对话"。当"流水线派"遇上"对话派"，多智能体到底该严格还是灵活？答案，藏在一个叫 Conversable Agent 的抽象里。

一句话总结 AutoGen 把"多智能体协作"抽象成"可编程的对话"——agent 可定制、可对话，能结合 LLM、人、工具或三者的混合，对话模式既可静态编排也可动态演化，开发者用自然语言和代码就能定义任意交互流程。

01领域定位

上一篇 MetaGPT，我们看到"群体协作"从涌现的火花走向工程化交付的转折。AutoGen 和它几乎同时（2023 年 8 月）出现在同一片浪潮里，却站在对立面：MetaGPT 押"组织"，AutoGen 押"对话"；MetaGPT 把人编成流水线，AutoGen 把人编进聊天群。这两篇加在一起，几乎框定了 2023 年多智能体设计的两极——一个是结构主义，一个是自由派。

在大模型发展脉络里，AutoGen 的位置很微妙：它不是某个新模型，也不是某项训练技巧，而是基础设施。它的真正贡献是把"多 agent 怎么搭"这件事，从一个临时拼装、各自为政的脚本活，升格成一套通用、可复用、可编程的框架抽象。后来无数 agent 框架（CrewAI、AG2、LangGraph 的一部分）都在它的影子下生长。可以说，它是"对齐与应用期"agent 线上，从"会玩的 agent"走向"能被工程师大规模搭起来的 agent 系统"的承重墙。

02研究背景

2023 年上半年，"自主智能体"热潮正盛。AutoGPT 给自己定目标、上网查资料、自己写代码；BabyAGI 用任务循环不停拆活；LangChain 给了"链"式编排，把 prompt、工具、记忆串成一串；各种"角色扮演"框架让多个 LLM 互相说话，看起来像在协作。

但真想搭一个能组合 LLM + 工具 + 人的系统，开发者很快撞上三堵墙。第一堵：能力孤岛——一个 agent 要么纯 LLM，要么纯工具调用，想把"人的判断""代码执行""模型推理"揉进同一个 agent，得自己手搓一堆胶水代码。第二堵：交互死板——大多数框架只支持一种预设流程，要么固定两两对话，要么固定角色轮次，遇到"中途要喊人拍板""要根据上下文换下一个发言者"这种动态需求就抓瞎。第三堵：人没法随时进出——人要么全程不在场，要么全程打断，没有一种"灵活级别"让人想插嘴就插嘴、想跳过就跳过。

类比 想象你在搭一个客服系统：有 AI 助手答常规问题，有代码执行器算报价，还有真人专家兜底处理疑难。旧框架要么让你把这三者焊死在一条链上（AI 答完→算报价→转人），要么干脆不让人参与。可真实业务里，你想的是"AI 搞不定就把人拉进同一个会话接着聊，人忙时 AI 先撑着"——这种"随时进出的群聊"，旧框架几乎给不了。

论文里那张经典的对比表（Table 1）把这些痛点量化了：它拿 AutoGen 和 LangChain、AutoGPT、BabyAGI、CAMEL 等同期系统比了四个维度——是不是通用基础设施、支不支持静态和动态对话、能不能执行 LLM 生成的代码、人能不能灵活介入。结果是没有一家四项全满足：有的只支持静态对话，有的不能执行代码，有的把人挡在门外。AutoGen 的切入点，正是把这四堵墙一起拆掉。

03核心问题

一句话：怎么设计一个通用、可复用、可定制的多智能体抽象，让它能覆盖从最简单到最复杂的各类应用，又不把开发者锁死在某一种对话模式里？

拆成两个关键子问题，论文自己写得明明白白：第一，单个 agent 怎么设计，才能既能力强、又可复用、又能灵活组合 LLM、人、工具？第二，agent 之间怎么交互，才能用一套统一接口，装下从两两对话到动态群聊的千变万化的模式？这两个问题答好了，"多智能体应用"才能从手搓脚本变成可工程化的基础设施。

思考一下 如果让你设计这个"万能 agent 基类"，你会让它默认带什么能力？是先定死一个角色（产品经理/工程师），还是只给一套"能收发消息、能自己回话"的最小骨架，把角色留给开发者去配？哪一种更经得起不同应用折腾？

04方法详解

AutoGen 的方法论可以浓缩成一句话：把 agent 抽象成"可对话、可定制"的统一基类，把协作抽象成"可编程的对话模式"。下面分三步看它怎么落地。

步骤一：Conversable Agent——一个能聊天、能定制的万能基类

先说人话：AutoGen 不一上来就给你"产品经理""工程师"这种预设角色，而是给一个最小骨架——叫 Conversable Agent（可对话智能体）。这个骨架只有两个核心能力：能收发消息（conversable），能被定制（customizable）。定制什么？定制它"收到消息后干嘛"——可以用 LLM 回话，可以调工具，可以问人，也可以把这些任意混合。

这个设计的妙处在于组合自由度。同一个基类，配 LLM 就是 AI 助手，配代码执行器就是"会跑代码的 agent"，配人工输入就是"人肉代理"，三者全开就是"既能想又能干还能问人"的全能选手。角色不是写死的，是配置出来的。论文还给了两个开箱即用的子类，让开发者拿来即用：

  • AssistantAgent：默认是个"纯 LLM 大脑"——收任务、写 Python 代码块给别的 agent 跑，收到报错还能自己改。不强制要人介入，也不自己执行代码。
  • UserProxyAgent：默认是"人的替身 + 代码执行器"——每轮先问人要不要说话，人不说就自动检测消息里有没有可执行代码块，有就跑、把结果灌回去。它把"人"和"工具"焊进了同一个 agent。

还有一个关键机制叫 auto-reply（自动回复）：agent 收到消息后，可以按注册的回复函数自动生成回复，也能随时把人拉回来插嘴。这就让多智能体既能自主跑起来，又不丢人在环的可能——自主和人控之间是连续的旋钮，不是非此即彼的开关。

这个抽象可以用一个极简等式概括——agent 的回复，是它"收到什么消息"和"自己被配成什么样"的函数：

$$ \text{reply}(a, m) = f_{\text{config}(a)}(m,\ \text{context}) $$ (1)

其中 $\text{config}(a)$ 决定 agent $a$ 用 LLM、工具还是人来生成回复，$m$ 是收到的消息，context 是共享上下文。一句话：同一个骨架，换个配置就是另一个角色。

步骤二：可编程的对话模式——从两人聊天到动态群聊

有了万能 agent，还得解决"它们怎么聊"。AutoGen 的第二刀，是把对话模式也做成可编程的。它内置了四种基本模式，还能让开发者用自然语言或代码自定义任意模式：

  • 两人对话（two-agent chat）：最简单，两个 agent 你一句我一句，由 initiate_chat 启动。
  • 顺序对话（sequential chat）：一串两人对话串起来，用"carryover"机制把上一段的总结带进下一段的上下文，像接力棒。
  • 群聊（group chat）：两个以上 agent 共享同一条对话线、同一个上下文。关键问题是"下一个谁说话"——AutoGen 给了四种选人策略：round_robin（轮流）、random（随机）、manual（人选）、auto（让 LLM 根据上下文决定）。最后一种就是动态对话的引擎。
  • 嵌套对话（nested chat）：把一整套工作流打包进单个 agent，外面看它像个普通 agent，里面其实藏着一个子工作流，方便复用。

这里有个关键区分：静态对话是无论输入什么，agent 拓扑都不变（轮流说话、固定顺序）；动态对话是拓扑本身随上下文演化（LLM 根据当前进展决定下一个谁说话）。AutoGen 两样都给——简单任务用静态够稳，复杂任务用动态够活。这正好补上了 MetaGPT 没覆盖的"流程跑着跑着要改路线"的缺口。

步骤三：人在环 + 代码执行，原生焊进 agent

第三刀最实用：AutoGen 把"人能随时进出"和"代码能自动跑"做成原生能力，而不是事后补丁。UserProxyAgent 是这套设计的缩影——它默认每轮先问人"要不要说话"，人不开口就自动扫消息里有没有可执行代码块，有就在 Docker 里跑、把 stdout 和报错灌回对话。这意味着"AI 写代码→执行→报错→AI 改"这个闭环，开箱就能跑。

# 最简两 agent：assistant + user_proxy 自动跑代码（简化）
assistant = AssistantAgent("assistant", llm_config=...)
user_proxy = UserProxyAgent("user", code_execution_config={"use_docker": True})
user_proxy.initiate_chat(
    assistant,
    message="画一张 META 和 TESLA 今年至今的股价变化图",
)
# → assistant 写代码 → user_proxy 自动执行 → 报错回灌 → assistant 改 → 出图

论文里那个贯穿全篇的例子就是这句"画 META 和 TESLA 股价图"：assistant 第一次写的代码忘了装 yfinance 包，user_proxy 一跑就报错，把报错塞回去，assistant 马上补一句"先 pip install"，再出图。整个过程没人插手，靠对话自己走通。这就是 AutoGen 想要的"对话即工作流"。

类比 MetaGPT 像一家有严格 SOP 的工厂：每个工位干什么、交什么，写得明明白白。AutoGen 像一个 Slack 群：你把任务甩进去，会写代码的、会跑代码的、会拍板的人都在群里，谁该接话谁就接，接不下去了 @ 一下人。前者稳，后者活——没有谁对谁错，只是任务长得不一样。

05实验结果

AutoGen 的实验不是去刷某个 benchmark 的 SOTA，而是用六个不同领域的示例应用，证明这套通用框架能 cover 住从简单到复杂的各类任务。这点很关键——它卖的不是某一项成绩，而是"通用性"本身。

应用领域所用对话模式关键发现
数学推理六 agent 群聊（求解者×3 + 批评 + 核对 + 汇总）多 agent 辩论优于单 agent
代码生成与调试assistant + user_proxy 两人开箱即用的写-跑-改闭环
供应链优化Commander + Writer + Safeguard人工干预减少 3–10×
在线决策（搜索/推荐）多 agent + 工具调用灵活组合 web 搜索能力
问答检索 + 生成 agent模块化能力组合
娱乐（狼人杀游戏）多角色动态群聊动态对话驱动涌现

几个发现值得细说。第一，数学推理那个六 agent 系统特别有意思：三个求解 agent 各写各的解法，一个批评 agent 找毛病，一个核对 agent 验算，一个汇总 agent 收口。这种"多解 + 互评 + 验算"的群聊，比单个 GPT-4 硬想更准——和上一篇 Self-Consistency、CoT 一脉里的"多路径投票"思路遥相呼应，只是把"采样多次"变成了"多 agent 同时干"。第二，供应链优化那个例子最显工程价值：用 AutoGen 搭的 Commander-Writer-Safeguard 三角，把人工干预次数砍掉 3 到 10 倍，编码工作量降到原来的 1/4 以下——这是真金白银的工程收益。第三，狼人杀那个例子最能体现"动态对话"的威力：谁是下一个发言者、要不要带节奏，全靠 LLM 根据当前局势现场决定，没有预设剧本，却跑出了像样的游戏逻辑。

最值得玩味的结论是：AutoGen 没有声称自己比 MetaGPT"更好"，它声称的是更通用。它的增益来源不是"组织方式"（那是 MetaGPT 的赌注），而是"把人和工具原生焊进 agent，把对话模式做成可编程基建"。两种增益不是对立的——后来的实践表明，最稳的多智能体系统，往往是 MetaGPT 式的流程骨架 + AutoGen 式的灵活对话缝在一起。

06影响与意义

AutoGen 的影响可以从三个层面看。学术上，它把"多智能体应用"从一个个临时脚本，升格成有通用抽象的基础设施课题——"可对话 + 可定制"这套基类设计，后来几乎成了 agent 框架的事实标准。它拿下 ICLR 2024 LLM Agent Workshop 最佳论文奖，被引用数百次。

工程上，它开源后迅速成为最受欢迎的多智能体框架之一，GitHub 星标一路涨到数万量级，和 MetaGPT、CrewAI 并列。微软官方持续迭代（0.2 → 0.4 多 agent 核心重写），社区还分叉出 AG2（原 AutoGen 社区版）继续维护。它直接催生了一大批"对话即工作流"的应用范式，让"人 + LLM + 工具"混合编排成了标配能力。

产业上，AutoGen 被广泛用于企业内部 agent 系统的原型与生产，从供应链、客服到数据分析，"多 agent 群聊"成了一种可复制的工程模板。一句话：AutoGen 让"多智能体"从"论文里的 demo"和"玩具脚本"，变成能被工程师大规模搭起来的通用基建。

07局限性与未来方向

AutoGen 不是没有软肋。首先，它高度依赖强 LLM 兜底——群聊里"LLM 选下一个发言者"这套机制，模型一弱就乱套，选错人、绕圈、死循环都见过。其次，对话本身有成本：多 agent 来回聊天 token 烧得飞快，复杂任务下对话拓扑该怎么优化、什么时候该收敛，论文当时没给自动解法（后来的 AgentOptimizer、EvolvableQ 才补上这一刀）。

再者，动态对话的可控性是个长期难题：灵活的另一面是难复现、难调试，同一个任务跑两遍可能走出两条完全不同的对话路径。还有那段绕不开的CAMEL 引用争议（下节详谈）——它暴露了"框架论文"在引用同期工作时的边界问题。后续工作沿几条路走：自动优化对话拓扑、把流程从"对话"扩展到"多智能体经济"、以及和 MetaGPT 式结构主义融合，取两派之长。

08领域演进脉络

把本篇放回大模型的整条时间线里（呼应图 1）：

  • 奠基期 2014–2017：Transformer 横空出世，attention 取代循环，为一切注意力模型铺路。
  • 预训练范式期 2018–2020：BERT 双向理解、GPT-2 单向生成，再到 GPT-3 把"大"玩明白，模型开始有"few-shot 学新任务"的能力。
  • 规模化探索期 2020–2022：Chinchilla 证明"更小模型 + 更多数据"反杀 GPT-3，算力最优训练法成型。
  • 对齐与应用期 2022–2023：InstructGPT、DPO 让模型听懂人话；CoT、Self-Consistency、ToT/GoT 把"提示工程"玩出花；ReAct、Toolformer、Reflexion、CRITIC、Self-RAG 把"工具 + 自我纠正"焊进单 agent；Voyager、Generative Agents 把 agent 从"会调工具"推向"会玩、会社交"；MetaGPT 把群体协作从"涌现"推向"工程化交付"。AutoGen 正紧接 MetaGPT，给出另一极的答案——不押组织押对话，把多智能体做成可编程基建。
  • 推理范式期 2025–：o1、DeepSeek-R1、Kimi K1.5 用强化学习训练思维链，推理范式时代开启——但 agent 要用上这种"会推理"的能力，还得靠 AutoGen 这类框架把多智能体编排好。

09趣味延伸

这篇论文最戏剧性的一段，不在正文，而在它和 CAMEL 的"引用官司"。CAMEL（Communicative Agents for "Mind" Exploration）是 KAUST 团队 2023 年 3 月发的论文，比 AutoGen 早了整整五个月，讲的是用"角色扮演 + inception prompting"让两个 LLM agent 自主对话完成任务——思路和 AutoGen 高度相似。但 AutoGen 在正文里几乎没提 CAMEL，把对比挪到了附录。

CAMEL 一作李国豪不干了。他在 ICLR 公共评论区指出这是"值得注意的遗漏"，意思很直接：你把我塞附录，读者基本看不到，结果大家都以为多智能体对话是你 AutoGen 首创的。ICLR 的审稿人和领域主席也点了 AutoGen 的名，说"在附录讨论同期工作不可取，因为附录的审核级别和正文不一样，等于变相让人没法公平看到"。这段插曲后来成了 agent 圈子里"arXiv 不是同行评审、发早了不代表被引"的经典案例。

另一个彩蛋在作者名单里：Doug Burger，微软技术院士，他给 AutoGen 站台时留下一句相当高调的话——"Capabilities like AutoGen are poised to fundamentally transform and extend what large language models are capable of. This is one of the most exciting developments I have seen in AI recently."（大意：AutoGen 这类能力有望根本性地改造和扩展大模型能干的事，是我近来在 AI 里见过的最激动人心的发展之一。）一个微软高级别老总亲自下场背书一篇框架论文，足见微软内部对它的期许。

还有个后话：AutoGen 后来经历了"分家"——微软官方继续推 0.4 重写版（多 agent 核心架构），社区分叉出 AG2（原 AutoGen 社区版）独立维护。一个框架长出两条命，也算是 agent 圈子里独有的风景。

10个人解读与延伸思考

我读 AutoGen 最大的感触是：它和 MetaGPT 合在一起，把多智能体设计里最核心的一对张力——结构 vs 灵活——摆到了台面上。MetaGPT 押"结构"，赌的是复杂任务靠 SOP 兜底；AutoGen 押"灵活"，赌的是真实世界任务长得千奇百怪，预设流程兜不住。两篇都对，也都各缺一半。

更深的启示在于：AutoGen 把"人"变成了 agent。这件事比它表面看更激进——以前"人在环"是个开关，要么全程在、要么全程不在；AutoGen 把人变成一个可对话、可定制的 agent，人就和 LLM、工具同构了。这意味着你可以在任何时刻把人拉进对话、又随时让人退出，自主和人控之间是连续光谱。当未来 agent 系统越来越强，"人什么时候该插手"会变成一个越来越重要的设计决策——AutoGen 给的旋钮，很可能就是答案的雏形。

当然，它也留下一个待解的张力：灵活的另一面是难复现、难调试。同一个任务跑两遍走出两条路，对研究是麻烦，对工程是噩梦。后来 LangGraph 用"图 + 状态机"试图把灵活性装回可复现的壳里，AG2 也在自动优化对话拓扑上下功夫。多智能体的未来，也许不是"纯对话"或"纯流水线"，而是把对话的可编程性，和结构的可复现性，缝在同一套基建里。

留个问题给你 如果让你搭一个"AI 投资研究助手"系统——要查财报、算估值、还要让分析师随时插嘴改判断——你会用 MetaGPT 的流水线，还是 AutoGen 的群聊？哪个环节该严格、哪个环节该灵活？如果两者都用，你会在哪里画那条分界线？
