大模型经典论文精读系列 #042

Experiential Co-Learning of Software-Developing Agents Experiential Co-Learning：让 agent 学会从历史里取经——把“经验记忆”焊进多智能体协作

作者：Chen Qian, Yufan Dang, Jiahao Li, Wei Liu, Zihao Xie, Yifei Wang, Weize Chen, Cheng Yang, Xin Cong, Xiaoyin Che, Zhiyuan Liu, Maosong Sun 机构：Tsinghua University · Dalian University of Technology · BUPT · Siemens 发表：2023-12 arXiv / ACL 2024
arXiv GitHub

上一期，我们看着 ChatDev 让一群 LLM 角色扮演成 CEO、CTO、程序员、测试员，靠"对话"就把一个能跑起来的软件从无到有造了出来。但你大概也会冒出一个疑问：如果让它们明天再做一款新软件，它们还记得昨天踩过的坑吗？

答案有点残酷——不记得。每接到一个新任务，这套 agent 团队都会像第一天上班的新人一样，从零开始摸爬滚打：同样的编译错误再犯一遍，同样的调试弯路再走一遍。这篇论文要解决的，就是给这些 agent 配一本"团队经验笔记本"，让它们学会从历史里取经。

一句话总结 让 instructor 和 assistant 两类 agent 从历史协作轨迹里自动挖出"捷径"经验，存进共享经验池，遇到新任务时先翻笔记本、再协作——多智能体协作正式跨入"会学习、能复用"的阶段。

01领域定位

在大模型的 agent 演化线上，这篇论文卡在一个很关键的拐点上。前面我们已经走过了一条清晰的脉络：ReAct 让单个 agent 学会"边想边用工具"，Voyager 把它塞进游戏里攒技能，Generative Agents 让 25 个 agent 在小镇里自发社交，再到 MetaGPT、AutoGen、CAMEL 把多智能体协作工程化，最后 ChatDev 把角色扮演焊成软件开发流水线。

但这里有个一直被回避的短板：上述所有框架，每个任务都是孤立求解的。agent 解决完 A 任务，所有对话记录就丢进故纸堆；遇到结构相似的 B 任务，它不会去翻 A 的经验，而是从头再来一遍。这与人差别巨大——人会记得"上次这里漏了个分号，这次先检查"。

Experiential Co-Learning（下文简称 ECL）正是补上这一块的论文。它回答的不是"agent 怎么协作"，而是"agent 协作时怎么把经验攒下来、用上去"。这是多智能体协作从"会干活"走向"会成长"的第一步，也为后来 ChatDev 团队自己的 MacNet（协作拓扑）、MAEL（跨任务经验迁移）等一系列后续工作埋下了火种。

02研究背景

要理解 ECL 为什么重要，得先看清 ChatDev 那套流水线的真实运行状态。在 ChatDev 里，软件开发被拆成若干阶段，每个阶段都是一对 agent 在对话：一个 instructor（指令者，类似提需求的 reviewer）给方向，一个 assistant（执行者，类似写代码的 programmer）出方案。reviewer 借助一个真实编译器不断反馈"这里没实现""这里有 bug"，programmer 再改代码，循环往复直到编译通过。

这套机制能跑通软件，但作者敏锐地指出了三个痛点：

  • 任务孤岛：每个任务独立求解，A 任务的经验对 B 任务毫无帮助，agent 永远是"新手"。
  • 重复试错：同一类编译错误、同一种调试弯路，在不同任务里反复出现，白白烧 token。
  • 最终还得靠人：因为缺乏跨任务的学习与迁移能力，遇到稍微陌生的任务就容易卡壳，最终需要人介入兜底。
类比 想象一家没有"项目复盘会"的外包公司。每个项目组解散后，文档全扔碎纸机，下一单来了重新组队、重新踩坑。哪怕你今年做过一百个待办清单 App，明年再来一个待办清单需求，新组的人照样得从"原来空指针会崩"开始学。ECL 想做的事，就是给这家公司建一个"经验库 + 内部检索系统"：每做完一单，自动把"从崩溃版本怎么走到能用版本"的捷径提炼出来存好；下一单开工前，先检索相关经验塞进对话里再开工。

值得一提的是，论文里专门澄清了一个词——"shortcut（捷径）"。在很多论文里 shortcut 带贬义，指模型投机取巧学到表面相关性；但这里作者用它取褒义，指"从历史轨迹里挖出的一条更高效的通路"，是 agent 应该主动去想的那条近路。这点命名上的"反其道而行"，也透露了作者的雄心：让 agent 像人一样主动走捷径、抄近道。

03核心问题

把背景拧成一句，论文要回答的核心问题是：

核心问题 如何设计、收集并应用"经验"，让 instructor 与 assistant 两类 agent 能从过去的协作轨迹里学到可复用的东西，从而在遇到没见过的新任务时，协作更准、更省、更少依赖人？
思考一下 在往下看方法之前，先停一下猜一猜：如果你来设计"agent 经验库"，最朴素的做法大概是什么？是不是直接把上次成功的整段对话原封不动存下来，下次原样塞回去？

这篇论文偏偏没这么干。它觉得"原样存对话"有大问题。你觉得问题可能出在哪？（提示：一次完整协作里，并不是每一步都在进步。）

04方法详解

ECL 的解法是三个模块串成一条流水线，分别对应"记录经验—提炼经验—使用经验"。两类 agent（instructor 和 assistant）贯穿始终，但分工在三个阶段略有不同。下面把三步拆开讲，每一步都配一句"人话"再给术语。

步骤一 · Co-Tracking（协同追踪）

先说人话：让两个 agent 在一批训练任务上像彩排一样协作干活，并把它们一来一回的整个过程完整记下来，形成一条"过程轨迹"。

再说术语：对训练任务集 $\mathcal{T}$ 里的每个任务 $t$，instructor 给出一串指令 $\mathcal{I}=\{i_1,i_2,\cdots,i_n\}$，assistant 回以一串解决方案 $\mathcal{S}=\{s_1,s_2,\cdots,s_n\}$，其中每个 $s_j$ 是一段"还算完整"的软件代码。这一来一回天然能建模成一条有向链：

$$ \mathcal{G}=(\mathcal{N},\mathcal{E}),\quad s_0 \xrightarrow{i_1} s_1 \xrightarrow{i_2} s_2 \xrightarrow{i_3} \cdots \xrightarrow{i_n} s_n $$ (1)

节点 $\mathcal{N}$ 是一个个代码方案（$s_0$ 是初始的空方案），边 $\mathcal{E}$ 是一条条指令，边 $(s_j, i_{j+1}, s_{j+1})$ 表示"在指令 $i_{j+1}$ 引导下，方案从 $s_j$ 变成了 $s_{j+1}$"。注意这条链记录的是过程，不只是最终结果——这是后面能提炼经验的前提。

步骤二 · Co-Memorizing（协同记忆）

这一步是全文最精巧的地方。先抛出作者的一个关键观察——它直接回应了前面思考题：

关键观察 链上并不是每一步都在变好。会出现两种"无效步"：一是回溯——改着改着又退回到之前的代码；二是由对到错——本来能跑的代码，被某条指令改坏了。所以"原样存整条轨迹"会把大量噪声、弯路、倒退也存进去，agent 照搬反而被带偏。

于是作者做了第一件事：把"链"压成"图"。用哈希函数把内容相同的方案映射到同一个节点，一条长长的、带重复的链，就被折叠成一张状态转移图——哪里在打转、哪里在倒退，一目了然。

接着是第二件事，也是最核心的——挖 shortcut。作者指出：图上相邻两个节点之间的一条边，代表 agent 已经会的"一步优化"；但真正有价值的经验，往往藏在"非相邻"节点之间——从某个差劲的方案，跳过中间那些弯路，直达一个好方案。这条"跨节点的近路"，就是一条 shortcut，也就是要存进经验池的东西。挖捷径靠的是外部环境反馈（编译器给的分）做启发。

挖到一条从 $s_j$ 到 $s_k$ 的 shortcut 后，作者还要把它转成 agent "能读能用"的形式——一段自然语言指令。比如有两种模板：一种是"从零生成某段代码要怎么做"，一种是"从源代码 A 怎么改到目标代码 B"。节点评分用外部信号成对计算，综合了代码与任务的相似度、与最终方案的相似度、能否编译等多个维度。最终，这些 (起点, 终点, 增益, 指令) 经验条目，会交错地写进 instructor 和 assistant 各自的经验池——instructor 池里存"该怎么指挥"，assistant 池里存"该怎么响应"。

步骤三 · Co-Reasoning（协同推理）

最后一步是"用"。遇到一个没见过的新任务时，instructor 和 assistant 不再从零对话，而是先各自去经验池里检索：用新任务的描述做 query，按代码/文本相似度找到最相关的几条 shortcut 经验，把它们作为 few-shot 示例塞进自己的对话上下文，然后再开始一来一回地协作。换句话说，经验池是两类 agent 共享的长期记忆，每次开工先翻笔记本。这就是开篇"团队经验笔记本"那个比喻的真正落地。

05实验结果

实验在 ChatDev 的软件开发基准上跑，对照 MetaGPT 和原始 ChatDev。评估分两个视角：自主性（软件质量四维）和效率。最让人印象深刻的是完整性和可执行性两项的跃升——下面这组数字最能说明问题。

把数字翻译成人话：完整性（软件实现了多少功能）从 ChatDev 的 0.6131 一路拉到 0.9497，接近满分，提升幅度超过 5 成；可执行性（代码能不能直接跑起来）从 0.8800 提升到 0.9650，几乎"开箱即跑"。MetaGPT 在这两项上分别只有 0.4472 和 0.4208，被甩开一大截。论文还报告：ECL 在效率视角下显著降低了协作成本与人工介入次数——也就是"更省 token、更少求人"。

为什么这么猛 关键不在"模型更聪明"，而在"经验被复用了"。agent 不必每个任务都重新发明轮子：当它在一个新软件里遇到似曾相识的结构，经验池会直接把"上次从半成品怎么走到能跑"的捷径递到它手里，省掉了大量无效试错。这也呼应了开篇的痛点——真正贵的不是算力，而是重复踩坑。

06影响与意义

论文自己最看重的贡献有三条，用大白话转述如下：

  1. 首次把经验搬进多 agent 协作：此前像 Reflexion 这类工作虽然也讲"从反馈里学"，但多局限在单 agent、同任务内的反思；ECL 把"跨任务经验"显式接进 instructor/assistant 两类 agent 的协作闭环。
  2. 把轨迹建成图、把 shortcut 当经验：用"任务执行图 + 非相邻节点捷径"这套抽象，给"什么是值得记的经验"提供了一个清晰、可操作的答案，鼓励 agent 在推理时走捷径思维。
  3. 用实验坐实了"会学习=更省更好"：在软件开发的可量化反馈上，证明了攒经验能同时提升质量与效率、降低人工介入。

更重要的是它对 ChatDev 团队自己后续工作的"火种"意义。这篇 ACL 2024 论文之后，同一个团队几乎沿着它打开的口子一路推进：2024 年 5 月的 Iterative Experience Refinement（IER）把"经验的获取、利用、传播、淘汰"做成完整闭环；6 月的 MacNet 把 ChatDev 的链式协作拓扑升级成支持上千 agent 的有向无环图；2025 年的 MAEL（跨任务经验学习）更进一步把经验按 agent 分池、用奖励信号引导检索。可以说，ECL 是这一整条"经验派"路线的起跑线。

07局限性与未来方向

客观地看，ECL 也有几处明显的边界。第一，它的"经验"高度依赖一个能给出客观反馈的外部环境——软件能编译、能跑，是"挖 shortcut"得以成立的前提。换到那些没有清晰对错信号的任务（比如开放式写作、头脑风暴），节点评分和捷径提取都会失去抓手。第二，经验是写在 prompt 上下文里复用的，没有反向更新模型权重，于是经验池越大、上下文越长，检索与注入成本也会随之上升，规模存在天花板。第三，shortcut 的"好坏"靠启发式打分，难免混入噪声捷径，长期可能把 agent 带偏。

这些局限恰恰成了后续工作的发力点：IER 解决经验怎么"动态淘汰与更新"，MacNet 解决协作拓扑"怎么扩到上千 agent"，MAEL 则把经验学习推向"奖励引导 + 跨任务"的更普适形态。一篇好论文的价值，往往就体现在它给自己留了多少"未竟之事"。

08领域演进脉络

把镜头拉远，agent 这条线大致可以这么梳理：早期是 单 agent + 工具调用（ReAct、Toolformer）；接着是 单 agent + 长期记忆与反思（Reflexion、ExpeL）；然后进入 多 agent 协作，从角色扮演（CAMEL）到群体涌现（Generative Agents），再到工程化框架（MetaGPT、AutoGen、ChatDev）。ECL 正站在"协作工程化"与"协作智能化"的交界——它承认前面的框架已经能干活，但补上了"协作要能成长"这一块。

再往后的走向也清晰：一方面是把协作拓扑从链/树做到图（MacNet）、再到可学习的中心编排器（NeurIPS 2025 的 Evolving Orchestration）；另一方面是把经验从"塞 prompt"做到"按 agent 分池 + 奖励引导检索"（MAEL），乃至共享经验社区（Spark）。本系列至此已带大家走过 41 篇，从 2017 年的 Transformer 一路到 agent 工程化，ECL 是第 42 块拼图——它让 agent 学会了"记得住、用得上"。

09趣味延伸

聊聊这篇论文背后的人和事。一作 Chen Qian（钱晨）彼时在清华，后来转到上海交通大学；这篇他和 Yufan Dang 并列一作，背后站着清华 OpenBMB 团队的刘知远、孙茂松师徒——也就是说，ChatDev 这条线，是同一个团队连发的"连续剧"。CAMEL 是 2023 年 3 月（被我们系列第 40 期考证为角色扮演真正的起源），ChatDev 是 7 月，ECL 是 12 月（次年 ACL 2024 录用），中间只隔几个月，节奏像追番。

还有个值得一提的小细节：论文在 related work 里特意把自己和 ExpeL 做了对照——ExpeL 把"成功轨迹的整段历史"当经验，ECL 偏不，它坚持要"挖捷径"而不是"存全程"。这个看似不起眼的取舍，其实透露了团队的一个执念：经验不该是流水账，而该是提炼过的捷径。后来的 IER、MAEL 都延续了"经验要精炼、要可淘汰"的思路，源头就在这里。

一个彩蛋 这篇论文的代码并不在独立仓库，而是直接合进了 OpenBMB/ChatDev 主仓的 ecl 模块，2024 年 1 月 25 日发的发布说明里写着"已集成 Experiential Co-Learning Module"——也就是说，你今天 clone ChatDev，就能直接用上这套经验学习。这也是它和很多"只发论文不开源"的 agent 工作的一大不同。

10个人解读与延伸思考

读完整篇，我最大的感触是：ECL 把一个被 agent 社区长期回避的问题——"经验怎么攒、怎么用"——给出了第一个干净利落的工程答案。它没有去动模型权重（不像 RLHF 那样重），也没有发明新的对齐算法，而是用"图 + 捷径 + 经验池 + 检索复用"这套组合拳，把in-context 的经验做出了体系感。这种"轻量但成体系"的风格，恰恰是 agent 工程化最缺的一类贡献。

把视角放到今天，这套思路其实正悄悄变成 agent 平台的"标配能力"：你会看到各种 agent 框架都开始内置"记忆/经验"模块，本质都在回答 ECL 当年提出的问题——只是各自在"记什么、怎么检索、要不要带奖励"上做文章。一个朴素但重要的判断：agent 的下半场，比的不是单次任务多惊艳，而是谁能把第一次的经验稳定用到第一百次。ECL 是这条赛道上一个清晰的起点。

留个问题给你 ECL 的经验是靠"外部编译器反馈"来打分的。如果换成一个没有客观对错的领域——比如让 agent 团队写一篇市场分析报告，或者帮你策划一次旅行——你打算用什么信号去判断"哪条协作轨迹值得提炼成捷径"？欢迎带着这个问题，等下一期我们一起看更普适的经验学习框架。
