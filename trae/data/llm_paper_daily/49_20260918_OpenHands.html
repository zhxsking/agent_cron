大模型经典论文精读系列 #049

OpenHands: An Open Platform for AI Software Developers as Generalist Agents OpenHands：把 AI 软件开发者做成开放平台——回到 agent 路线，但这次让 agent 通用起来

作者：Xingyao Wang*, Boxuan Li, Yufan Song, Frank F. Xu, ... Graham Neubig 等 24 位 机构：UIUC, CMU, Yale, UC Berkeley, All Hands AI 等 10 家 发表：2024-07 / arXiv v1（ICLR 2025）
arXiv GitHub

上一篇我们讲完 Agentless——UIUC 的 Lingming Zhang 组甩出一巴掌："别用 agent，一条死板流水线也能在 SWE-bench Lite 上拿到 32%，还便宜 6 倍"。可同在 UIUC，另一拨人根本不服气。他们不仅要用 agent，还要把 agent 做成一套人人都能上手的基础设施。

2024 年 3 月 12 日，一个名叫 OpenDevin 的开源项目悄悄挂上 GitHub——名字直白地致敬了 Cognition AI 那个引爆全网的闭源"AI 软件工程师" Devin。不到四个月，它改名 OpenHands，挂出论文，汇聚了 UIUC、CMU、Yale、UC Berkeley 等 10 家机构的 24 位作者，拿到 ICLR 2025 录用。它要做的事只有一件：把"让 LLM 写代码、敲命令、逛网页"做成一个开放、通用、安全的平台，谁都能往里塞自己的 agent。当"流水线派"在喊"别用 agent"，OpenHands 反手搭了座桥——agent 这条路不仅没死，还要把它做成基础设施。

一句话总结 OpenHands 是一个社区驱动的开源平台，用"事件流 + Docker 沙箱运行时 + 通用动作空间"三大件，让任意 LLM 都能像人类开发者一样写代码、跑命令、逛网页——同一个 agent 不改 prompt，在软件工程、网页浏览、杂项辅助三大类任务上都有竞争力。

01领域定位

顺着这个系列的脉络，第 35 篇 ReAct 打通"思考-行动"循环，第 47 篇 SWE-agent 把循环落到真实仓库上并给出 ACI 接口设计，第 48 篇 Agentless 反手抽走"自主决策"也能 SOTA。这条故事线到此出现了一个有趣的分叉：一边是"把 agent 拆光"的流水线派，一边是"把 agent 做厚"的框架派。OpenHands 站在后者，而且是站得最稳的那个。

它的位置很特殊：SWE-agent 解决的是"单 agent + 好接口"，Agentless 解决的是"无 agent + 好流水线"，而 OpenHands 解决的是一个更底层的问题——整个 agent 生态缺一套统一的、开放的、可复现的基础设施。论文里那句定位很准：它要做的是"通用型与专用型 AI agent 的开发平台"，而不只是某个跑分高的 SE agent。换句话说，前两篇在争"agent 要不要"，OpenHands 在争"agent 该长在什么地基上"。

02研究背景

2024 年上半年，软件工程 agent 圈子被一个名字点燃：Devin。Cognition Labs 在 3 月放出这个"AI 软件工程师"——闭源、配 IDE + 终端 + 浏览器，让 GPT-4 在循环里自己计划、敲命令、跑测试、改代码。演示视频一出，全网沸腾，"AI 程序员要抢饭碗"的标题刷屏。

可问题来了：Devin 是闭源黑箱。它用什么 prompt、怎么设计工具、怎么调度循环——外界一无所知。学术界想复现、想改进、想做对比实验，根本无从下手。于是 SWE-agent、AutoCodeRover、Aider、Moatless……一批开源工作跟上，但每个人都有自己的一套 agent 抽象、自己的环境接口、自己的评测脚本——碎片化到了没法横向比较的地步。

论文开头点了三个本质挑战，正是这个乱象的根源：

  • 复杂软件的创建与修改：真实仓库动辄几万行，怎么让 agent 在复杂代码库里定位、编辑、重构？
  • 即时信息收集：修 bug 得先看报错、查文档、跑测试——agent 怎么随时调工具收集信息？
  • 安全与副作用：让 LLM 自由执行代码，一个 rm -rf 就能把用户系统搞挂——怎么隔离？

这三个挑战，SWE-agent 解决了"接口"那一层，Agentless 干脆绕过了"自主决策"那一层。但整个社区缺一套统一的、开放的、能复现的基础设施——一个大家都能往上加 agent、加工具、加评测的公共地基。这才是 OpenHands 要填的坑。

类比 想象 2008 年之前的手机 App 生态：每个开发者各自为政，没有统一的应用商店、没有统一的开发框架、没有统一的审核标准。苹果做了 App Store + iOS SDK 之后，App 生态才真正爆发。OpenHands 想做的，就是 agent 世界的"iOS SDK + App Store"——一套公共的运行时、一套统一的动作/观测协议、一个社区可以贡献 agent 的中心（AgentHub）。区别只在于，它是完全开源、MIT 许可、谁都能拿去商用。

03核心问题

论文要回答的问题，比"怎么修 bug"大得多：

论文核心命题 How can we build an open, general, and safe platform for AI agents that interact with the world through software?
如何为"通过软件与世界交互"的 AI agent，搭建一个开放、通用、安全的平台？

这个问法把战场重新划了一遍。SWE-agent 问的是"怎么设计接口让单 agent 修好 bug"，Agentless 问的是"要不要 agent 都行"——它们都在优化"某个具体任务上的表现"。OpenHands 问的是更底层的：这个领域要往前走，得先有一套公共地基。没有统一平台，每个人造轮子、每个人报自己的分、每个 agent 没法公平对比——整个 SE agent 研究就是一盘散沙。

而且"通用"这个词分量很重。论文副标题特意加了 as Generalist Agents——它不想只做修 bug 的专用 agent，而是要让同一个 agent能写代码、能逛网页、能做杂项任务。这是对 SWE-agent / Agentless 这种"专精 SWE"路线的一次横向扩张。

思考一下 如果你要搭一个"通用 agent 平台"，最少需要哪几个部件？不妨先列三条：agent 怎么和环境通信？环境长什么样、怎么保证安全？怎么让别人能往里加新 agent？读完下面的架构，对比你想漏了哪块。

04方法详解

OpenHands 的答案是一套由三大主组件构成的平台：智能体抽象（Agent）、事件流（Event Stream）、运行时环境（Runtime）。这套设计的核心思想一句话能说完：把"agent 怎么和环境交互"标准化成一套统一的动作/观测协议，再把环境做成安全的 Docker 沙箱，让任何 agent 实现都能插进来跑。

组件一：智能体抽象与事件流（Agent & Event Stream）

OpenHands 把"agent"定义成一个极简的接口：一个 step(state) → action 函数。agent 拿到当前状态（State），吐出一个动作（Action）。状态的核心是事件流——一个按时间顺序记录所有动作与观测的序列，包括 agent 自己的动作和用户的交互。

动作类型受 CodeAct 启发，被设计成基于编程语言的统一动作空间：

  • IPythonRunCellAction：在沙箱里执行任意 Python 代码
  • CmdRunAction：执行 bash 命令
  • BrowserInteractiveAction：通过 BrowserGym 的领域语言操控浏览器
  • AgentDelegateAction：把子任务委派给另一个 agent

这套基于编程语言的动作空间，是 OpenHands 和传统 JSON 工具调用 agent 的根本分野。传统 agent 得为每个工具预定义一个 JSON schema（如 search_file(pattern="def main")），OpenHands 的 agent 直接写 Python：

# CodeAct 方式：把工具调用统一成可执行 Python
print(openhands.edit_file(start=1, end=1, content="EDITED_CODE"))
openhands.create_file('app.py')

这样做的好处是动作空间天然无限——agent 甚至能在 API 不存在时自己写一个 Python 函数当工具。代价是输出更难约束，但对通用性来说，这个取舍值得。观测（Observation）则描述环境变化——命令的输出、代码执行的结果、浏览器的截图——回流到事件流里，agent 下一轮 step 就能看到。

组件二：运行时环境（Runtime with Docker Sandbox）

这是整套设计里最硬核也最让人放心的一块。OpenHands 给每个任务会话启动一个安全隔离的 Docker 容器沙箱，所有动作都在里面执行——rm -rf / 也删不到用户主机。沙箱内跑着一个 REST API 服务器（即 OpenHands action execution API），对外接收动作、对内调度三个子服务：

  1. bash shell：连接由 docker image 指定的操作系统环境，执行命令
  2. Jupyter IPython 服务器：处理交互式 Python 代码执行请求
  3. 基于 Playwright 的 Chromium 浏览器：提供 BrowserGym 定义的动作原语（导航、点击、输入、滚动），返回 HTML、DOM、accessibility tree、截图等丰富观测

最妙的是支持任意 Docker 镜像——你想要一个预装 PyTorch + CUDA 的环境？自己造个镜像，OpenHands 会把 action execution API 装进去。这让"环境"不再是写死的，而是可定制的。

组件三：AgentSkills——可扩展的人机接口

SWE-agent 强调"精心设计的 ACI 对复杂任务很重要"，可造一堆专用工具、维护、分发都是工程噩梦。OpenHands 的解法是 AgentSkills：一个自动导入 IPython 环境的 Python 包，由不同工具函数组成。社区想加新工具？写个 Python 函数就行——门槛被压到最低。

纳入标准很克制：不为 LLM 已能直接写代码完成的功能重复造轮子（比如读 CSV 用 pandas 就行），只在"LLM 无法直接写代码完成"（如编辑文件指定行）或"涉及调用外部模型"（如语音转文本）时才加技能。当前技能含从 SWE-agent 和 Aider 改编的 edit_file、scroll_up/down、parse_image/parse_pdf 等。

组件四：多智能体委派与 AgentHub

通用 agent 不可能什么都强。OpenHands 用 AgentDelegateAction 让一个 agent 把子任务委派给另一个——比如通用 CodeActAgent 浏览网页能力有限，就委派给专用的 BrowsingAgent。这让"通用"和"专精"不再对立，而是组合关系。

更关键的是 AgentHub：一个社区贡献的智能体中心，用户可以选不同的 agent 实现（CodeAct Agent、Browsing Agent、GPTSwarm Agent、Micro Agent……）当基线。这是 OpenHands 做"平台"而非"单个 agent"的体现——它卖的是地基，不是某栋楼。

类比 传统工具调用 agent 像一个带固定工具箱的工人——老板事先给好锤子、扳手、螺丝刀，少一把就干不了活。CodeAct agent 像一个带着 3D 打印机的工人——要什么工具当场打印一个出来，甚至能打印出"打印机的零件"来组装新机器。前者的动作空间是封闭集合，后者的动作空间是图灵完备的。这就是 OpenHands 选 CodeAct 当默认 agent 的原因。

05实验结果

OpenHands 最硬的实验结论不是某个单项分数，而是同一个 agent、不改 system prompt、在三大类任务上都有竞争力。这套通用性，是它和 SWE-agent / Agentless 这种"专精 SWE"路线的根本差别。

三个让人印象深刻的点：

  • 通用性碾压：同一个 CodeAct agent，在软件工程（SWE-bench、HumanEvalFix、ML-Bench）、网页浏览（WebArena、GAIA）、杂项辅助（GPQA）三大类上都有竞争力——而基线 agent 通常专为某一类设计和优化。论文原话："the same CodeAct agent, without any modifications to its system prompt, demonstrates competitive performance across three major task categories"。
  • 成本可接受：SWE-bench Lite 上用 claude-3-5-sonnet 平均一题 1.10 美元，用 gpt-4o-mini 只要 0.01 美元——比 SWE-agent 的 1.67 美元还便宜。注意 OpenHands 跑的是完整 agent 循环，不是 Agentless 那种死板流水线，但成本没失控。
  • SWE-bench 不是终点：虽然 SWE-bench Lite 上 26.0% 略低于 Agentless 的 27.3%，但 OpenHands 的价值不在单项跑分——它的 CodeAct agent 后来在 SWE-bench Verified 上飙到 53%（2024.11），再后来甚至到 77.6%（2026.01）。平台的价值会随模型变强而持续放大。

06影响与意义

OpenHands 的影响是三层叠加的。

第一层：基础设施。它第一次让 SE agent 圈有了一套统一的、开放的、可复现的平台。在那之前，每个团队造自己的轮子、报自己的分、没法横向比较。OpenHands 之后，所有"agent + 工具 + 环境"的工作都有了一个公共地基可以往上搭。论文表 1 的框架对比里，OpenHands 是唯一在 GUI、标准化工具库、内置沙箱、内置浏览器、多智能体协作、人机协作、AgentHub、评估框架、Agent QC 九个维度上全部打勾的系统——SWE-agent 只勾了"内置沙箱"，Agentless 几乎没勾。

第二层：社区与产业。论文发表时已 32K GitHub stars、188+ 贡献者，截至 2026 年已超 64K stars。三位核心贡献者——CMU 教授 Graham Neubig、Robert Brennan、UIUC 博士生 Xingyao Wang——联合创立了 All Hands AI 公司，2024 年 9 月拿到 500 万美元种子轮（Menlo 领投，Hugging Face 联合创始人 Thom Wolf、PyTorch 创造者 Soumith Chintala 等天使投资）。一个学术论文直接长出了一家 agent 公司，这在 SE agent 圈是头一遭。

第三层：评测生态。它集成了 15 个基准测试，覆盖软件工程、网页浏览、杂项辅助三大类，让"agent 通用性"第一次有了系统化衡量的尺子。后续的 OpenHands-Versa、SWE-bench Verified 等工作都建立在它这套评测框架之上。可以说，没有 OpenHands 把"评测基建"做厚，后面"通用 agent 到底行不行"的争论根本无从展开。

07局限性与未来方向

论文附录 A 标题就叫 Limitations and Future Work，作者自己也承认短板。

第一，安全性与可靠性。让 agent 执行任意代码本身就是风险——Docker 沙箱隔离了主机，但 agent 仍可能下载恶意包、泄露 API key、在沙箱里搞破坏。论文把"安全可靠的 agent"列为公开挑战，后续 V1 SDK 才引入了内置安全分析。

第二，多模态支持不足。早期对图像、PDF 等多模态处理有限，虽然有 parse_image/parse_pdf 技能，但 agent 对视觉信息的理解仍靠外部模型转文本，不是原生多模态交互。论文明确把"增强多模态支持"列为未来重点。

第三，单体架构的局限。V0 的单体架构（monolithic）导致沙箱假设僵化、可变配置蔓延、研究与生产耦合过紧——这也是后续 V1 Software Agent SDK（MLSys 2026）完全重新设计的动机。一个平台越成功，它的架构债越显眼。

第四，长程任务易陷入循环。单 agent 在长程、多步任务上容易原地打转——生成→失败→再生成，烧 token 不出活。这催生了后续的委派机制强化、记忆增强、以及强化学习训练 agent 决策（SWE-RL）等方向。

08领域演进脉络

把 OpenHands 放回整个 LLM agent 发展的脉络里看，它的位置是承前启后的枢纽。

起步期，ReAct（第 35 篇）确立了"思考-行动-观察"循环范式，那时大家的目标很轻——调调搜索引擎、跑跑计算器。Toolformer、Voyager 把工具调用焊进模型权重，但场景仍是单文件级的代码生成。软件工程这个"真实仓库级"战场，长期是空白。

2023 年底 SWE-bench 一出，这块空白被显式化——3.8% 的成绩等于在喊"现有 agent 范式不够"。SWE-agent（第 47 篇）接住这一棒，把 ReAct 循环落到软件工程环境里，给出 ACI 接口设计框架，拉到 12.47%。Devin（闭源引爆）把"AI 软件工程师"这个词炒热，但黑箱属性让学界没法跟进。Agentless（第 48 篇）反手说"别用 agent 也能 SOTA"，在 SWE-bench Lite 上 32%。

OpenHands 在这条时间线上的位置，是开放平台派的奠基之作。它不否定 SWE-agent 的"接口设计"结论，也不否定 Agentless 的"无 agent 也能行"结论——它回答的是更底层的问题：不管你用不用 agent，这个领域要往前走，得先有一套公共地基。它之后，整个领域有了两条并行的轨道：一条继续卷具体 agent 的跑分（MASAI、SWE-Gym、SWE-RL），另一条卷平台与基建（OpenHands V1 SDK、OpenHands-Versa）。这两条轨道的分叉起点，就是 2024 年 7 月的这篇 OpenHands。

09趣味延伸

OpenHands 这篇论文背后，故事比代码还多。

第一，名字的由来：OpenDevin → OpenHands。项目最初叫 OpenDevin——直白地致敬 Cognition AI 的闭源 Devin。两个创建者是阿里巴巴 Qwen 团队的 Binyuan Hui（崔一鸣）和 Junyang Lin（林俊旸）——你没看错，就是那个著名的开源大模型 Qwen 的团队。2024 年 3 月 12 日项目挂上 GitHub，开源社区迅速汇聚。后来三位核心贡献者（Graham Neubig、Robert Brennan、Xingyao Wang）联合创立 All Hands AI 公司继续推进，项目改名 OpenHands——"open hands"，张开的手，比"open Devin"少了一点对标、多了一点独立人格。论文脚注还特意注明："While initially inspired by AI software engineer Devin, OpenHands has quickly evolved to support much wider range of applications beyond software engineering"——从"致敬"走向"超越"。

第二，UIUC 的"内部对决"续集。上一篇我们讲过，Agentless 出自 UIUC 的 Lingming Zhang 组，论证"别用 agent"；而 OpenHands 的第一作者 Xingyao Wang 同在 UIUC（Hao Peng / Heng Ji 组），做的是全球最火的开源 agent 框架。一个学校两个组，一个喊"别用 agent"，一个造"agent 平台"——这种学术同侪间的内部对立在 AI 圈相当罕见。更妙的是，OpenHands 论文里还引用了 Agentless，并在 SWE-bench Lite 上和它直接比跑分——同校两拨人，论文里你来我往。

第三，24 位作者、10 家机构。这篇论文的作者名单长得像奥斯卡致辞——UIUC、CMU、Yale、UC Berkeley、Contextual AI、KAUST、ANU、HCMUT、阿里巴巴、All Hands AI。其中 Niklas Muennighoff（Contextual AI）后来在 Gemma、MTEB 等工作里都活跃。这种"跨校跨公司"的大规模合作，在 agent 圈几乎是把社区共识焊进了论文署名——它不是某一家之言，是整个开源社区的集体背书。

第四，MIT 许可证：随便商用。OpenHands 选了最宽松的 MIT 许可证——允许商用。这意味着任何公司都能拿去改造成自己的产品。在 AI 圈"开源但限制商用"成风的当下，这个选择相当敞亮，也是它能在工业界快速铺开的原因之一。

10个人解读与延伸思考

放长视角看，OpenHands 的真正价值不在于某个跑分，而在于它把"agent 平台"这件事从概念做成了基建。

agent 这个词被滥用已经很久——任何带 LLM 调用 + 工具调用的系统都自称 agent。第 47 篇 SWE-agent 证明"接口比 agent 重要"，第 48 篇 Agentless 证明"无 agent 也能 SOTA"，OpenHands 证明的是第三件事：不管你用不用 agent，这个领域要健康往前走，得先有一套公共地基。这三篇合起来，把 agent 这个概念的边界、接口、平台三个维度都划清楚了——这比任何单项跑分都值钱。

更深一层，它和 Agentless 的"对垒"其实不是谁对谁错，而是两个层面的正交问题。Agentless 回答的是"修 bug 这件具体事，要不要 agent"——答案是不要。OpenHands 回答的是"整个 agent 生态，要不要公共地基"——答案是要。一个在优化"某栋楼"，一个在搭"地基"。产业落地的 coding agent（Cursor、Cline、Devin）大多是 Agentless 式的分阶段流水线 + 局部 agent 决策混合体，但它们都跑在类似 OpenHands 的沙箱 + 事件流地基上。换句话说，Agentless 赢了"范式落地"这一仗，OpenHands 赢了"基建落地"那一仗——它们不冲突。

放到今天看，预言性也很足。短短两年，OpenHands 从一个致敬闭源产品的开源项目，长成了 ICLR 2025 论文 + All Hands AI 公司 + 64K stars 的平台。它的 CodeAct agent 在 SWE-bench Verified 上从 26% 飙到 77.6%——平台的价值会随模型变强而持续放大，而流水线派的红利会随模型变强而收窄。这或许是它和 Agentless 最大的差别：流水线有天花板，平台没有。

留个问题给你 OpenHands 强调"通用 agent 不改 prompt 跑三类任务"，可 SWE-bench Lite 上它（26%）略输 Agentless（27.3%）。当模型强到某个临界点——能直接吃整个仓库、能自己生成并跑测试——通用 agent 的天花板会不会反过来盖过专用流水线？换句话说，"通用 vs 专精"的取舍，是不是也有一个"模型变强之后会自动反转"的保质期？

MASAI: Modular Architecture for Software-engineering AI Agents

OpenHands 搭好了通用 agent 平台，可 SE agent 到底该怎么分模块？微软研究院（MSR India）给了个答案：把一个大 agent 拆成几个子 agent，每个配专属策略——有的负责定位、有的负责改、有的负责验证——用"分而治之"在 SWE-bench Lite 上拿下 28.33%。当"通用平台派"和"无 agent 流水线派"吵得不可开交，MASAI 选了第三条路：不是不要 agent，而是把 agent 拆成模块。下一篇，我们看模块化架构怎么和通用平台、流水线三足鼎立。
