大模型经典论文精读系列 #046

The Illusion of Multi-Agent Advantage 多智能体优势的幻象：自动 MAS 全面输给 CoT-SC，还贵 10 倍——同一支团队的自我打脸

作者：Prathyusha Jwalapuram*, Hehai Lin*, Chuyuan Li, Fangkai Jiao, Sudong Wang, Yifei Ming, Zixuan Ke, Chengwei Qin, Giuseppe Carenini, Shafiq Joty 机构：Salesforce AI Research, HKUST-Guangzhou, UBC, NTU 发表：2026-06 / arXiv
arXiv Project

上一篇我们讲完 MAS-Orchestra——Salesforce 团队把多智能体编排建模成一次函数调用强化学习，一口气生成整个 MAS，效率提升 10 倍。当时结尾留了个钩子：同一支团队，几个月后掉头开炮。现在，炮来了。

他们拿自己造的 MAS-Orchestra，加上另外五个主流自动 MAS 框架，一起扔到四个基准、四个大模型上跑了一遍。结果让人倒吸一口凉气：六个自动 MAS 框架，全部输给了一个最朴素的基线——链式思考加自洽投票（CoT-SC），而且花了人家 10 倍的钱。更狠的是，他们把每个框架的内部架构拆开来看，发现那些花里胡哨的多 agent 图谱，跑着跑着全退化成了"换个名字的 CoT-SC"。这篇论文叫 The Illusion of Multi-Agent Advantage——多智能体优势的幻象。

一句话总结 自动生成的多智能体系统（MAS）在绝大多数任务上打不过一个会"多想几遍再投票"的单智能体（CoT-SC），还贵 10 倍——因为那些复杂架构在实践中退化成了冗余的"换皮"投票，真正有用的只有专家手动设计的 MAS。

01领域定位

从第 35 篇 ReAct 开始，这个系列花了整整 11 篇的篇幅，从推理范式（CoT、Self-Consistency、Tree of Thoughts）走到自我纠正（Reflexion、CRITIC、Self-RAG），再走到工具调用（Toolformer、Voyager），然后一头扎进多智能体（MetaGPT、AutoGen、CAMEL、ChatDev……），最后在 puppeteer 和 MAS-Orchestra 把编排做到极致。一路走来，潜台词始终是：agent 越多、协作越复杂，效果越好。

这篇论文恰好是这条叙事线的急刹车。它不做新框架，不做新编排器，而是做了一件整个领域都回避的事——把"自动 MAS 一定更强"这个前提，拿去和最简单的单智能体基线正面对决。结果发现：皇帝没穿衣服。它既是多智能体热潮的清算时刻，也给下一阶段的 agent 设计划了条红线——不是"多少个 agent"重要，而是"每个 agent 有没有用"重要。

02研究背景

2023 年到 2026 年，多智能体系统（MAS）几乎是 agent 领域的"政治正确"。框架层出不穷：MetaGPT 用 SOP 让一群 LLM 像创业团队一样分工，AutoGen 把多智能体变成可编程对话，CAMEL 用角色扮演驱动自主协作，ChatDev 焊成软件开发流水线，MacNet 搭出上千节点的 DAG，puppeteer 用强化学习训练调度器，MAS-Orchestra 一次性生成整个系统。每个新框架都声称自己比单智能体更强，理由也很充分——

  • 上下文隔离：每个 agent 只看自己需要的信息，不会被无关上下文干扰
  • 并行处理：多个 agent 同时干不同子任务，速度更快
  • 角色专精：一个当"程序员"、一个当"测试员"，各司其职
  • 交叉验证：agent 之间互相检查、辩论、纠错

听起来完美。但有个问题一直被悄悄绕过：这些框架的"基线"是谁？

翻遍论文，你会发现大多数 MAS 的对比基线是"裸 CoT"——就是一个模型，做一次链式思考，出一版答案。这就像你造了辆 F1 赛车，跟一个骑共享单车的人比谁快，然后宣布"赛车赢了"。但真正公平的对比应该是：同样预算下，一个模型多想几遍再投票（CoT-SC），效果如何？

更关键的是，大多数评测用的是数学题、问答题这类孤立的推理任务——一道题、一个输入、一个输出。可 MAS 的核心卖点是"任务分解""上下文隔离""并行"，这些优势在"一问一答"的任务上根本没有发挥空间。你用百米短跑来评测一辆卡车，当然说卡车不行。

类比 想象你开了家公司，招了 10 个员工，每人年薪 50 万。你跟一个自由职业者比"谁产出多"——但那个自由职业者只拿 5 万。结果你赢了，你到处宣传"团队就是比个人强"。可你从来没想过：如果把那 500 万预算给 10 个自由职业者，让他们各自独立做、最后投票选最好的方案，是不是比你那 10 个互相开会、扯皮、传话的员工更高效？这正是这篇论文要回答的问题。

03核心问题

这篇论文要回答三个层层递进的问题：

  1. 公平对决：在同等甚至更低预算下，自动 MAS 真的比 CoT-SC 更强吗？
  2. 任务适配：如果自动 MAS 在普通任务上输了，是因为任务本身不适合多智能体，还是 MAS 设计本身有问题？
  3. 架构解剖：那些自动生成的复杂多 agent 架构，在实际运行中真的实现了"分工""并行""交叉验证"吗？还是只是看起来复杂？
思考一下 如果你是一个 agent 框架的设计者，面对这三个问题，你会怎么设计实验来回答？特别是第二个问题——怎么区分"任务不适合 MAS"和"MAS 设计得不好"？

04方法详解

论文用三步回答了上面三个问题，每一步都像手术刀一样精准。

第一步：大规模系统评测——公平对决

作者选了 6 个代表性的自动 MAS 框架，覆盖两大范式：

  • 推理时范式（inference-time）：DyLAN、MAS-Zero、ADAS——在推理时动态决定 agent 拓扑
  • 优化范式（optimized）：AFlow、MaAS、MAS-Orchestra——通过搜索或强化学习预先生成最优架构

对照基线是 CoT-SC：同一个模型，独立采样多条思维链，取多数票。简单到不能再简单。

评测覆盖 4 个基准 × 4 个骨干模型：

基准任务类型说明
GPQA-Diamond科学推理研究生级科学问答
HLE-Maths数学推理人类终极考试数学子集
SWE-Bench Lite代码修复真实 GitHub Issue 修复
BrowseComp-Plus网页交互多步浏览+信息检索
骨干模型提供商能力层级
GPT-4oOpenAI中端
GPT-OSS-120BOpenAI中端开源
GPT-5OpenAI前沿
Gemini-2.5-ProGoogle前沿

关键变量是推理成本——不是只看准确率，而是看"花多少钱拿到多少分"。这把过去所有"MAS 赢了"的论文都放在了聚光灯下：你赢了，但花了人家 10 倍的钱，这算赢吗？

第二步：SMFR 诊断基准——排除"任务不适配"

第一步的结果已经很残酷了。但作者很严谨：万一自动 MAS 输了，只是因为 GPQA、HLE 这类任务本来就不适合多智能体呢？万一给它们一个"天生适合分解、并行、上下文隔离"的任务，它们就能翻盘？

为此，他们造了一个全新的诊断基准：Synthetic Multi-Hop Financial Reasoning（SMFR，合成多跳金融推理）。每个问题的结构是：

  1. 给一个"股票价格草垛"——B 家公司 30 天的开盘/收盘价
  2. 给 2~6 个投资者的交易记录
  3. 对每个投资者：抽取相关交易 → 计算盈亏 → 算出目标价 → 找到匹配日期
  4. 最后跨投资者聚合，按"最早/最晚日期"选出赢家

这个任务天生就是为 MAS 设计的：每个投资者的计算互相独立，天然可并行；每个子任务需要不同的上下文窗口，天然需要上下文隔离；最后需要聚合，天然需要角色分工。如果 MAS 在这种任务上都赢不了，那就不是任务的问题了。

SMFR 包含 588 道测试题和 16 道验证题，全部从真实美股价格分布程序化合成，免疫数据污染。

更妙的是，作者还设计了一个 Expert-MAS（专家手工设计的 MAS）作为"天花板"参照：

  • 一个 Meta-Agent 先把问题解析成结构化 schema
  • 确定性的 Python 调度器编排多个子 agent：Extractor 抽数据、Calculator 算价格、Aggregator 选赢家
  • 每个投资者的计算管线并行执行

关键设计：协调逻辑交给确定性代码，不让 LLM 自己瞎编排。这消除了自动 MAS 最大的噪声来源——编排不确定性。

第三步：架构解剖——拆开看每个 agent 到底在干什么

前两步证明了"自动 MAS 不行"，但为什么不行？作者没有停留在结论表面，而是把六个框架生成的 MAS 架构逐一拆解，追查每个 agent 在运行中实际扮演了什么角色。这是全文最精彩的部分。

他们发现了三个普遍的病理特征：

  • 角色冗余：被分配了不同角色（如"数学家""逻辑学家"）的 agent，在功能上完全等价，换了名字没换活
  • 功能退化：复杂的 agent 图谱在运行中退化成了基础的 CoT-SC——多跑几遍、投票，仅此而已
  • 缺乏专精：这种"没有真正的分工"现象跨任务一致，说明自动设计范式根本没学会自适应任务分解

以三个框架为例：

DyLAN 的卖点是"agent 多样性带来性能"。但数据显示：agent 们在约 70%（GPT-4o）甚至超过 90%（GPT-5）的案例中立即达成一致意见——这哪是"动态协商"，分明是"全员举手同意"的 CoT-SC。更讽刺的是，所有 agent 都设成同一个角色（全当"助手"）的配置，准确率 54.4%，反而比精心设计角色分工的 53.4% 更高。角色分工纯属心理安慰。

MAS-Zero 的设计是让一个"裁判 agent"从多轮搜索结果中选最优。但裁判有严重的位置偏见——GPT-4o 在超过 45% 的情况下选了最早的输出，后续轮次的输出被选中率不足 15%。这意味着后面几轮的 worker agent 全变成了"昂贵的证人"——花满额推理成本跑了一遍，对最终答案的因果贡献约等于零。

ADAS 的自动搜索生成的架构充满了冗余节点，搜索过程非单调——多搜几轮反而更差，因为搜索到的是"启发式伪影"而非真正有用的拓扑。

类比 这就像你开了一家"精品餐厅"——菜单上写着"主厨秘制酱汁""分子料理""低温慢煮"，但后厨实际上是 6 个厨师各自炒了一盘一模一样的番茄炒蛋，然后经理尝了一口说"就上第一盘"。你为 6 个厨师付了工资，客人吃到的只是一盘番茄炒蛋。这就是"架构膨胀"——结构看起来很复杂，但每个节点的边际贡献约等于零。

05实验结果

三步实验的结果可以浓缩成一句话：自动 MAS 全面落败，专家 MAS 一骑绝尘。

大规模评测：CoT-SC 碾压式胜出

在 GPQA-Diamond、HLE-Maths、SWE-Bench Lite、BrowseComp-Plus 四个基准上，CoT-SC 以不到 10%的计算成本，在几乎所有组合中取得了更高的准确率。唯一例外是 HLE-Math 上使用 GPT-5 和 Gemini-2.5-Pro 时，MAS 有微弱提升——这说明 MAS 只在骨干模型本身已经足够强时才有一点点用。

更扎心的是"能力桥接"假说的破产：人们本以为"用复杂 MAS 能让弱模型达到强模型的水平"。数据直接打脸——一个用 GPT-5 跑 CoT-SC 的单 agent，稳定地打败了最精巧的 GPT-4o 自动 MAS 框架（包括 ADAS 和 AFlow），还只花了不到一半的 token。

关键对比CoT-SC最佳自动 MAS成本倍数
GPQA-Diamond (GPT-5)更高更低~10×
HLE-Maths (GPT-5)基准微弱提升~10×
SWE-Bench Lite (GPT-5)更高更低~10×
BrowseComp-Plus (GPT-5)更高更低~10×

SMFR 诊断：即使任务天生适合 MAS，自动 MAS 依然赢不了

这是最具说服力的结果。SMFR 是一个专为 MAS 设计的任务——有明确的子任务分解、上下文隔离、并行化空间。如果"任务不适配"是自动 MAS 输的原因，在这里它们应该能翻盘。

但它们没有。

SMFR 上的表现CoT-SCExpert-MAS最佳自动 MAS
GPT-5~49%96.7%+4~6pp / 2~10×成本
GPT-OSS-120B22.4%36.0%微弱提升 / 高成本
GPT-4o基准瓶颈无改善

关键数字：GPT-5 从 CoT-SC 的约 49% 跃升到 Expert-MAS 的 96.7%——几乎翻倍。而六个自动 MAS 框架里最好的（MAS-Orchestra）也只加了 6 个百分点，花了 1.9 倍的钱。DyLAN 加了 4.3 个百分点，花了 2.5 倍的钱。都不值。

这说明：任务适配不是问题，MAS 设计才是问题。专家手动设计的 MAS 能在这类任务上大放异彩，自动生成的完全做不到。

另一个发现是"能力门槛"：GPT-4o 无论用什么编排，都做不好——模型的底层推理能力不够，再好的 MAS 也白搭。MAS 需要骨干模型先跨过一个能力门槛，才有用武之地。

令人惊讶的发现 Expert-MAS 在 SMFR 上把 GPT-5 的准确率从 ~49% 拉到 96.7%——这不是微调，不是训练，只是换了一种编排方式。这意味着：很多时候模型不是"不会做"，而是"没被组织好去做"。自动 MAS 的失败不在于模型能力，而在于编排质量。

06影响与意义

这篇论文的意义不在于提出了什么新方法——它没提。它的价值在于说了别人不敢说的话，而且用最扎实的数据说了。

  • 终结了"MAS 一定更强"的迷信：从此以后，任何声称"我的 MAS 比单 agent 强"的论文，都必须先回答一个问题——你的基线控制了计算成本吗？你跟 CoT-SC 比了吗？
  • 定义了 MAS 评测的新标准：不能只看准确率，必须看边际效用——多花的那 9 倍钱，换来了几个百分点？SMFR 也给领域提供了一个"天生适合 MAS"的诊断工具。
  • 指明了正确方向：Expert-MAS 的成功说明，MAS 范式本身没有错，错的是自动生成。未来的方向不是更复杂的自动搜索，而是让人和代码来做编排，让 LLM 来做执行。
  • 为 agent 平台设计划了红线：别盲目堆 agent。每个 agent 都要有清晰的边际贡献，否则就是"昂贵证人"。

07局限性与未来方向

论文自身也承认了几点局限：

  • 模型选择偏差：只测了 OpenAI 和 Google 的模型，未覆盖 Claude、开源大模型等，自动 MAS 在其他模型上的表现可能不同
  • 推理 vs 工具：评测集中在推理任务，对工具调用密集型任务（如代码执行、API 编排）的 MAS 优势未充分探索——这类任务可能更适合多 agent
  • 优化超参：自动 MAS 的搜索超参可能未调到最优，存在"被低估"的可能
  • 只评了集中式编排：去中心化的 agent 团队系统（agent 之间更独立地通信）有不同的缩放特性，未纳入评测

但作者很清楚：这些局限不改变核心结论。即使给自动 MAS 最优的超参、最适合的任务，它们也赢不了 CoT-SC 的性价比，更追不上 Expert-MAS 的天花板。问题不在调参，在范式。

08领域演进脉络

回望整个 agent 系列的旅程，这条线索变得格外清晰：

起步（ReAct #35）：一个 agent，一边想一边调工具，已经足够惊艳。繁荣（MetaGPT #38、AutoGen #39、CAMEL #40、ChatDev #41）：既然一个 agent 能做事，那多个 agent 协作岂不是更强？于是框架井喷，每个都声称自己比单 agent 好。复杂化（MacNet #43、puppeteer #44、MAS-Orchestra #45）：协作拓扑从链式到 DAG 到动态编排，越来越精密。

然后，本篇站出来说：等一等——你们跟 CoT-SC 比了吗？一比，发现整个繁荣期的"MAS 更强"叙事，建立在不公平的基线和不适配的任务之上。这不是否定前人的工作，而是给狂热降温、给方向纠偏。

下一步的线索应该是：如果自动 MAS 不行，什么行？Expert-MAS 指了一条路——让人设计架构、让代码做调度、让 LLM 做执行。这恰好与 agent-computer interface（ACI）设计的思路不谋而合：重要的不是多少个 agent，而是 agent 和工具之间的接口设计得好不好。

09趣味延伸

这篇论文最有趣的层面，是它的身份。还记得第 45 篇 MAS-Orchestra 吗？那篇论文的核心贡献是：用函数调用强化学习，一次性生成整个多智能体系统，效率提升 10 倍。而本篇论文评测的六个框架里就有 MAS-Orchestra 自己。

没错——同一支 Salesforce 主导的团队，先造了一把剑，然后发了一篇论文说这把剑砍不过一根木棍。这在学术界其实非常罕见。通常的研究叙事是"我做了个新东西，它比旧的强"；这篇的叙事是"我做了个新东西，然后我发现它和所有同类东西一样，都不如最简单的基线"。

这不是"自我打脸"——这是科学的诚实。MAS-Orchestra 那篇论文解决的是"如何高效生成 MAS"，它确实做到了。但本篇追问的是一个更根本的问题："生成的 MAS 值不值得用？"答案是：目前不值得。两篇论文合在一起读，才是一个完整的故事——MAS-Orchestra 解决了"怎么做"，本篇回答了"该不该做"。

另一个有趣的细节：论文标题里的 Illusion（幻象）一词，呼应了认知科学中"幻觉"的概念——你看到的不一定是真的。自动 MAS 的架构图看起来很复杂、很专业，但拆开一看，里面的 agent 要么在重复劳动，要么在无效等待，真正起作用的只是最外层那层投票。这不就是"皇帝的新衣"吗？

10个人解读与延伸思考

读完这篇论文，我最深的感触是：简单被低估了。CoT-SC 的逻辑简单到可以一句话说完——"多想几遍，取多数票"。但它有效。而那些花了几十页论文描述的复杂 MAS 架构，拆开一看内核还是它，只是套了层"分工""协商""验证"的壳，还多花了 10 倍的钱。

这不意味着 MAS 没有未来。Expert-MAS 在 SMFR 上把 GPT-5 从 49% 拉到 96.7% 的数据太震撼了——同样的模型、同样的任务，只是换了一种编排方式，准确率翻倍。这证明 MAS 范式本身有巨大的潜力，只是当前的自动生成方法还没找到正确的打开方式。

我的判断是，接下来 agent 领域的竞争焦点会从"谁的 agent 多、谁的拓扑复杂"转向"谁的接口设计好、谁的编排确定性强"。Expert-MAS 的成功靠的是把协调逻辑交给确定性代码——不让 LLM 猜该怎么编排，而是用程序保证编排的正确性。这和传统软件工程里"把关键路径用代码保证、把灵活部分留给 AI"的思路一脉相承。

对从业者来说，这篇论文是一条实用的决策规则：在花力气搭多 agent 系统之前，先试试 CoT-SC。如果 CoT-SC 够用，别上 MAS。如果不够用，先想想是不是模型不够强（能力门槛），再想是不是任务需要分解（SMFR 式结构）。最后才考虑 MAS——而且优先考虑人工设计架构，而非自动生成。

留个问题给你 如果 Expert-MAS 在 SMFR 上能把 GPT-5 从 49% 拉到 96.7%，那为什么不让所有任务都用 Expert-MAS？你觉得"为每个任务手工设计 MAS"这件事，可以自动化吗？如果能，自动化的边界在哪里——是让 AI 学会"设计架构"（而非"生成架构"），还是让人来设计、AI 来执行？欢迎带着这个问题去读下一篇——那里会有一个关于"设计正确的接口"的答案。
