大模型经典论文精读系列 #066

MemGPT: Towards LLMs as Operating Systems MemGPT：让 LLM 自己当操作系统——上下文是内存，对话是中断，一段 system prompt 实现的虚拟内存管理

作者：Charles Packer, Sarah Wooders, Kevin Lin, Vivian Fang, Shishir G. Patil, Ion Stoica, Joseph E. Gonzalez 机构：UC Berkeley · Sky Computing Lab 发表：2023-10 · arXiv 2310.08560（v2 更新于 2024-02）
arXiv GitHub Project

2023 年 10 月 12 日是个周四，伯克利 Sky Computing Lab 的博士生 Charles Packer 把团队的论文悄悄挂上了 arXiv，想着周末过完再张罗正式发布。结果周日就有人把论文翻了出来，贴上了 Hacker News——帖子在榜首挂了大约 48 小时，那个还没来得及宣传的 GitHub 仓库几天之内涌进 11000 个 star、1200 多个 fork。Packer 后来只能苦笑：“someone scooped us”（被人抢发了）。一篇不训练、不微调、参数一行不改的论文，凭什么让整个社区集体失眠？因为它干了一件听起来像科幻的事——让 LLM 自己当自己的操作系统。

上篇 MemOS（#065）结尾留了句话：“仅靠系统调用，建不成操作系统。”MemOS 给 AI 装了一个有调度器、有三层架构的“Windows”，但这条“记忆操作系统”路线的源头，其实是两年前这个更疯狂的实验：没有独立进程，没有注册表，整套内存管理逻辑全部塞在一段 system prompt 里，模型一边跟你聊天，一边给自己“换页”、给自己“写盘”。它就是 MemGPT——本系列连讲四篇的记忆赛道（WikiSkill → ReasoningBank → Agent KB → MemOS），今天终于要回到那个起点。

一句话总结 把操作系统的“虚拟内存”思想塞进 LLM 的 system prompt：上下文窗口是内存，外部存储是磁盘，函数调用是系统调用——让模型自己决定什么留在“内存”、什么换出到“磁盘”、什么时候再换回来，用一个固定上下文的模型，造出“上下文无限”的幻觉。

01领域定位

在本系列的谱系里，MemGPT 是“agent 记忆”这条线的正源。往前看，它站在几篇本系列老朋友的肩膀上：Toolformer（#034）教会了模型调函数，ReAct（#035）让思考与行动交织，Voyager（#036）给 agent 攒出了第一个技能库，Generative Agents（#037）的“记忆流”第一次让 25 个 agent 记住了彼此。这些工作其实都在暗示同一件事：模型需要一个窗口之外的状态。MemGPT 第一次把这个状态做成了完整的“操作系统”——有分层存储、有中断机制、有自我编辑，一步到位。

往后看，它孵化出记忆赛道最炙手可热的创业公司 Letta（原 MemGPT 项目，2024 年 9 月出隐身即拿下 Felicis 领投的 1000 万美元种子轮，天使投资人里赫然写着 Google DeepMind 首席科学家 Jeff Dean 的名字），也直接刺激了 Mem0、Zep、MemOS（#065）等一整个赛道的诞生。可以说，没有 MemGPT 的“疯狂”，就没有后来“给 AI 装记忆”这门生意的火种。

02研究背景

2023 年秋天，AI 圈的主要矛盾，是人民群众日益增长的长对话需求和 LLM 死活不变的上下文窗口之间的矛盾。论文里有一张今天看来颇为怀旧的表格：

模型上下文窗口大约能聊几条消息
Llama 24k tokens~60 条
Mistral 7B8k tokens~140 条
GPT-3.5 Turbo16k tokens~300 条
GPT-432k tokens~600 条
GPT-4 Turbo128k tokens~2600 条

按 1k token 系统提示、每条消息约 50 token 估算（论文表 1）。也就是说，当时的旗舰模型陪你认真聊一个下午就“失忆”了。

乍一看，出路有两条，但论文开篇就把两条都堵死了。第一条路：把窗口做大。注意力的计算和显存开销随序列长度二次方增长，成本先扛不住；更要命的是 Liu 等人 2023 年的著名发现——即便给了长窗口，模型也用不好，放在窗口中间的信息照样被无视，学界管这叫 lost in the middle。窗口大了，只是把“金鱼”养进了更大的鱼缸，记性并没有变好。

第二条路：截断或总结。聊不下的旧消息直接扔掉，或者让另一个模型压缩成摘要。这条路的问题是丢失是必然的：“你上周说过你和 James 分手了”这种一句顶一万句的细节，在摘要里大概率会被压成“用户聊了聊近况”。对客服机器人是小事，对一个要长期陪伴用户的助理，是致命的。

类比

把上下文窗口想象成你的办公桌桌面。方案一是换一张 100 平米的大桌子——贵得离谱，而且事实证明桌子越大，东西越容易找不到（lost in the middle）。方案二是每天下班让秘书写一页“今日工作摘要”烧掉所有原件——省地方，但细节全灭。而操作系统界在半个多世纪前就给出了第三条路：虚拟内存——桌面就这么大，但系统在桌子底下接了一个仓库，按需把文件搬上桌、用完搬回去，让你产生“桌子无限大”的错觉。1960 年代的程序员靠这个技巧跑起了比内存大得多的程序；MemGPT 的作者们问的问题是：这个老 trick，能不能原封不动搬给 LLM 用？

顺带一提这项研究的起点，一点也不宏大——Letta 官方博客后来披露，MemGPT 最初只是想给一个 Discord 聊天机器人改善记忆：让网友们的机器人能记住昨天聊过什么。结果做着做着，问题滚雪球般滚成了“LLM 的内存管理到底该怎么做”，于是一支系统研究团队把它做成了一篇论文。

03核心问题

论文要解决的问题可以一句话说清：如何让一个上下文窗口固定且有限的 LLM，产生“上下文无限”的幻觉——同时不打断对话、不丢失关键事实、不依赖人工写死的规则。

这里面藏着一个真正的设计难题：在内存和磁盘之间搬数据的“搬运工”该是谁？传统操作系统的搬运工是内核里的页面调度算法，冷酷、精确、不懂业务。但 LLM 的“页面”是自然语言，哪些消息重要、哪些事实值得留下，恰恰是需要理解语义才能做的判断——这又正是 LLM 自己最擅长的事。

思考一下 如果由你来决定“哪些信息留在上下文里”，你会选谁当搬运工：一套人工规则（比如“永远保留最近 20 条”）？一个专门训练的小模型？还是让 LLM 自己管自己？前两个方案听起来稳妥，MemGPT 偏偏选了最激进的第三个——先记住你的选择，看看论文的理由能不能说服你。

04方法详解

先说结论：MemGPT 的“工程清单”短得可疑——一个原封不动的商用 LLM、两个外部数据库、两段管理代码、一份长长的 system prompt。没有训练，没有微调，没有梯度。整篇论文的核心，是把操作系统的内存管理哲学翻译成模型能读懂的说明书。

第一步：把“内存”切成三段

模型的 prompt——也就是它的“内存”——被划成三个连续区块，各司其职：

  • 系统指令：只读的“主板说明书”，写明内存层级怎么用、有哪些函数可以调。相当于 BIOS/固件，开机后谁也不许改。
  • 工作上下文：一块固定大小的可读写便签，存放蒸馏过的关键事实——用户叫什么、喜欢什么、agent 自己的人设是什么。它只能通过函数调用修改，是“核心记忆”的载体。
  • FIFO 队列：一段滚动的消息流水账，用户消息、模型回复、系统警告、函数结果都往里追加。注意队首第一条永远是递归摘要——被驱逐消息的摘要的摘要，保证模型对“很早以前”至少有个模糊印象。

第二步：把“磁盘”建成两个数据库

窗口之外的一切都叫外部上下文，分两类：召回存储是全部历史消息的完整日志——注意是全文，不是摘要，永久保存、随时可搜回来；归档存储则是一个通用读写仓库，能塞任意长度的文本，底层用向量数据库实现（论文版本用的是 PostgreSQL 的 pgvector 扩展加 HNSW 索引，检索跑在 text-embedding-ada-002 嵌入上）。语义检索打分用的就是标准余弦相似度：

$$ \text{sim}(q,d) = \frac{q \cdot d}{\lVert q \rVert \, \lVert d \rVert} $$ (1)

其中 $q$ 是查询的嵌入向量，$d$ 是某条存储内容的嵌入向量。公式本身平平无奇——真正新奇的是按下检索键的权限归谁：在传统 RAG 里，检索由外部流水线做主；在 MemGPT 里，检索是模型自己发起的系统调用。

第三步：队列管理器——唯一“冷酷”的部分

整个系统里只有队列管理器是纯粹的普通代码，不掺一点模型的不确定性。它干两件事：

  • 70% 警戒：当 prompt 用量到达上下文窗口的约 70%，它往队列里插一条系统消息——“内存快满了”。相当于手机弹出“存储空间不足”的通知，给模型一个抢救的机会：赶紧把重要事实抄进便签、把长流水账搬进仓库。
  • 100% 冲刷：用量触顶时，驱逐大约一半的消息腾地方，并用“旧摘要 + 被驱逐消息”生成新的递归摘要。被驱逐者并不消失——它们全文进入召回存储，之后随时可以被搜回上下文（“换入”）。

第四步：一切输出皆系统调用

这是 MemGPT 最异想天开的设计：模型输出的不是聊天文本，而是函数调用。想记事，调 working_context.append；想改便签，调 working_context.replace；想存长材料，调 archival_storage.insert；想翻旧账，调 recall_storage.search 或 archival_storage.search——连“回复用户”这个动作本身，都要通过 send_message 函数完成。函数执行的结果（包括报错，比如“便签已满写不进去了”）会被塞回上下文，模型看到后果再决定下一步。这是论文里最像操作系统的时刻：系统调用、错误码、重试，一应俱全。

// 模型的"内心独白"全部变成函数调用：
{
  "function": "archival_storage.search",
  "args": { "query": "James 六旗乐园 生日", "page": 0 },
  "request_heartbeat": true
}
// ↑ 干完这件立刻叫醒我，我还有下一步

{
  "function": "send_message",
  "args": { "message": "你们是在六旗乐园认识的呀，太巧了！" }
}
// ↑ 不带 heartbeat：说完这句，把控制权还给用户

第五步：中断与心跳——让模型“想说完再停”

很多任务一口气调不完函数：搜到第一页结果，得翻到第二页；读完一份文档，还得再去搜另一份。MemGPT 借来操作系统的中断概念，给每个函数调用留了个特殊参数 request_heartbeat=true——含义是“函数执行完，请立刻把我叫醒继续”。就像你嘱咐外卖小哥“放门口之后给我发条消息”，模型可以一口气完成“搜索 → 翻页 → 再搜 → 读文档 → 作答”的链式动作，再交还控制权。触发推理的“事件”也被泛化了：不只是用户消息，系统警报、文档上传完成的通知、甚至定时器都能唤醒模型——最后这个意味着 agent 可以不请自来，主动找你说话。

如果 Transformer 是发动机（#001），InstructGPT 教会它说人话（#006），Toolformer 教会它用计算器（#034），那 MemGPT 做的事相当于把发动机装上车之后，再教它考驾照、看仪表盘、自己决定什么时候加油——车上的每一件事，都由它自己判断，因为只有司机知道目的地在哪儿。

05实验结果

论文选了两个“上下文窗口是硬天花板”的领域做实验：多轮会话（记忆）和文档分析（阅读）。全部实验零训练零微调，直接拿 API 模型跑。

实验一：深度记忆检索（DMR）——最惊人的翻盘

在 MSC（Multi-Session Chat）数据集上，模型先陪用户连聊五段会话，然后被问一个只在很早会话里出现过的细节问题（“用户和 James 第一次见面是在哪儿？”）。固定上下文的基线模型只能拿到前几段会话的有损摘要，MemGPT 则可以翻查完整历史。结果：

底层模型固定上下文+ MemGPT准确率提升ROUGE-L 提升
GPT-3.5 Turbo38.7%66.9%+28.2 pt0.394 → 0.629
GPT-432.1%92.5%+60.4 pt0.296 → 0.814
GPT-4 Turbo35.3%93.4%+58.1 pt0.359 → 0.827

注意一个反直觉的细节：基线里 GPT-4 比 GPT-3.5 还惨（32.1% 对 38.7%）——因为大家都被“摘要”这个有损压缩坑了，模型再聪明，也变不出被摘要抹掉的细节。而 MemGPT 版 GPT-4 把准确率拉到 92.5%，靠的不是模型变聪明，而是它终于能翻到原始记录。用论文的话说：基线拿到的是会议纪要，MemGPT 拿到的是完整录音 + 播放器。

实验二：开场白任务——机器比人更像“那个人”

让 agent 主动给用户发起新会话的开场白——考的是它对用户人设的记忆掌握得多细。用与“标准人设标签”的嵌入余弦相似度（SIM-1）打分：人类写的参考开场白得分 0.800，MemGPT（GPT-4）拿到 0.868——机器生成的开场白比数据集里人类自己写的更像“它认识的那个人”，而且更啰嗦，覆盖的人设细节更多。你的 AI 比你朋友还记得你上个月随口提过的事，想想有点微妙。

实验三：文档分析——窗口小不是读不了长文档的借口

在 Liu 等人那套基于 NaturalQuestions-Open 的多文档问答设置里，检索回来的文档越多、越长，固定上下文的基线就越狼狈——塞不下就得截断，截断就可能正好删掉答案。MemGPT 则完全不慌：文档一页一页换进来读，读不完的翻页再读，准确率随文档数量增长保持稳定，彻底没有“截断衰减”这回事。顺带一提，同样的架构还能顺藤摸瓜读完全远超窗口的单个大文件——论文之外的读者很快发现，这就是后来各种“AI 读 PDF”产品的雏形。

实验四：嵌套键值检索——多跳链式查找的降维打击

最能体现“函数链”威力的是这个刻意设计的任务：给模型一批“键值对”，但值本身可能是另一个键——要拿到真正的值，就得一层一层追下去。140 对 UUID、约 8k token、最多四层嵌套，像不像在图书馆查“马斯克的生日”， encyclopedia 说“见 B 卷 312 页”，翻过去写着“见 D 卷索引”……

GPT-3.5 固定上下文在一层嵌套时就完全失灵，GPT-4 扛到三层也归零——因为它们得一次性在心里追完整条链。MemGPT 靠 request_heartbeat 驱动的函数链，一层一层查、查完再查下一层，四层嵌套依然近乎满分。把“深度推理”翻译成“顺序执行的系统调用”，是这套架构最漂亮的一击。

最令人惊讶的发现

整套系统没有训练任何东西。“记忆能力”完全来自 system prompt 里那份自然语言说明书——GPT-4 读了说明书就会当操作系统了。这大概是 2023 年关于“涌现能力”最实用的注脚：有些看起来需要专门构建的能力，其实早就睡在模型里，缺的只是一份足够好的说明书。

06影响与意义

MemGPT 对领域的第一重贡献是词汇：它发明并普及了 virtual context management（虚拟上下文管理）和"LLM OS"这套话语体系。在此之前，“给模型加记忆”是各家 prompt 工程师的自留地技巧；在此之后，它变成了一门有分层、有调度、有中断语义的系统工程学科——有了正确的词汇，大家才能讨论架构。今天你听到的 stateful agent（有状态智能体）、memory tier（记忆分层）、context engineering（上下文工程），源头都能摸回这篇论文。

第二重贡献是赛道。论文项目后来演化为开源框架与创业公司 Letta——2024 年 9 月 23 日出隐身当天宣布两件事：项目从 MemGPT 改名 Letta，以及完成 Felicis 领投的 1000 万美元种子轮（投后估值 7000 万美元），天使名单里包括 Jeff Dean 和 Hugging Face CEO Clem Delangue。Packer 对 TechCrunch 放话：“我们要做 OpenAI 的开源替代品。”而在它身后，Mem0、Zep、LangMem、MemOS（#065）相继入场，本系列近几篇讲的 WikiSkill、ReasoningBank、Agent KB，都在回答 MemGPT 提出的问题。

第三重贡献是持续的研究纲领。Letta 团队 2025 年 4 月又发表 sleep-time compute：让一个后台 agent 在“闲时”替主 agent 重新整理记忆，同样的准确率，测试时算力开销约降至五分之一，每查询平均成本约降至四成——等于给这台“操作系统”加上了睡眠整理碎片整理功能。

07局限性与未来方向

论文自己也承认，这套“操作系统”的毛病不少，而且个个要命：

  • 函数调用依赖症。整个系统的前提是模型能可靠地按说明书调函数。GPT-4 表现优秀，GPT-3.5 就明显拉胯——DMR 上 66.9% 对 92.5%，文档分析里差距更大。操作系统再精巧，也得看 CPU 给不给力：这个"OS"的版本号，实际上是被底层模型的指令遵循能力锁死的。
  • 贵，而且慢。一次用户提问可能触发一长串推理调用——搜索、翻页、再搜、读文档、作答，每一步都是真金白银的 token。论文没有给出延迟与成本分析，但每个复现过的人都会第一时间感受到账单的凉意。
  • 递归摘要有损。“会议纪要的纪要的纪要”，摘要叠摘要，细节注定层层蒸发。MemGPT 靠“原文都在召回存储里”兜底，但队首那条摘要本身，仍然是压缩过的二手货。
  • 换页策略全凭“良心”。传统 OS 的页面置换算法经过几十年打磨；MemGPT 的换页策略是模型读说明书后“凭自觉”执行的，没有任何学习机制。模型哪天判断失误，把关键信息存歪了地方，就真的找不回来了。
  • 评测偏窄。只考了问答类任务，没有复杂推理、创意写作，也没有和“直接把文档塞满 128k 窗口”的长上下文原生用法做正面对比。

这些坑，后来者各认领了一个：Mem0 说记忆不该让模型自己管，该做成平台服务（下期主角）；MemOS 说光靠系统调用建不成操作系统，得有真正的调度器与存储分层（上篇主角）；Letta 自己则用 sleep-time compute 补成本课，用记忆块可视化（ADE）补可控性课。一篇论文留下一串 TODO，才是它成为经典的方式。

08领域演进脉络

把镜头拉远，看看这一篇在全图里的位置。2017 年 Transformer（#001）造出发动机；2018–2020 年 BERT（#002）与 GPT-2/3（#003/004）确立预训练范式；2020–2022 年 GPT-3 与 Chinchilla（#005）把“规模化”逼成显学；2022 年起 InstructGPT（#006）、DPO（#008）解决对齐，CoT（#024）点燃推理，agent 化浪潮随之而来——Toolformer（#034）、ReAct（#035）交出工具与行动，Voyager（#036）、Generative Agents（#037）攒出技能库与记忆流。到 2023 年秋天，所有零件都在桌上了，只差有人把它们组装成整车：MemGPT 用操作系统的图纸完成了这次总装，LLM 从“会说话的引擎”变成“带内存管理的机器”。

此后两年，两条线并行狂奔：一条是推理范式期（#013–023），o1、DeepSeek-R1 把“思考”本身做成可训练的能力——但再能思考的模型，窗口之外依然一片黑暗；另一条就是 MemGPT 开出的记忆赛道：ReasoningBank（#063）把推理策略存进银行，Agent KB（#064）让经验跨 agent 流动，MemOS（#065）给记忆装上调度器与计价体系。窗口越做越大（2k → 128k → 百万级），记忆赛道却越来越火——因为所有人都看清了一件事：“窗口大”和“记得住、用得好”根本是两回事，而这个判断，正是 MemGPT 在 2023 年就写下的注脚。

09趣味延伸

这篇论文的诞生史本身就是个段子合集。起点卑微到好笑：一切只是为了给一个 Discord 聊天机器人改善记忆。发表过程堪称事故：2023 年 10 月 12 日（周四）论文悄悄挂上 arXiv，团队打算周末后正式宣传，结果周日就被人翻出来贴上 Hacker News，霸榜约 48 小时，GitHub 几天内 11000 星——Packer 的原话是 “someone scooped us”，学术圈少见的“被自己的论文抢先发布”。仓库最初挂在他个人账号 cpacker/MemGPT 下，2024 年 2 月攒到约 1.8 万星，改名迁移到 letta-ai/letta，如今两万多星。

考据党还能发现一个细节：对比 arXiv 的 v1 和 v2，作者名单变了——v1 只有六个人，v2 里多了一位压阵的大佬：Ion Stoica。这位 Sky Computing Lab 的联合主管是 Databricks 联合创始人，实验室更是 Spark 和 Ray 的诞生地。这也解释了论文气质的来源：在一间系统研究实验室里，“LLM 的上下文问题”从来不是什么 AI 前沿难题，而是 1970 年代就解决过的内存管理问题——系统人看 AI，看到的全是老朋友。所谓降维打击，就是用五十年前的操作系统教科书，给最前沿的 AI 指出一条明路。

还有改名的段子。2024 年项目从 MemGPT 改叫 Letta，官方理由啼笑皆非又无比真实：当时 "MemGPT" 一词身兼三职——指论文里的技术、指“带记忆的聊天机器人”这个物种、指他们那个代码仓库，大家聊天全靠猜。一个名字三个意思，索引彻底失效，只好挥刀改名。顺带一提，在后来的 Letta 框架里，论文里的“工作上下文”演化成了可插拔的记忆块，函数也改了名：core_memory_append、archival_memory_search……古老的系统调用，至今还在迭代版本号。

10个人解读与延伸思考

回头看，MemGPT 最持久的遗产不是那套具体机制（后来的框架大多改得面目全非），而是它示范的一种方法论：当 AI 的新问题看起来无从下手时，去计算机科学的历史档案馆里翻一翻——1950 年代至今，人类在“有限的机器上跑无限的需求”这件事上攒了一整柜子的智慧，虚拟内存、进程调度、中断、缓冲区管理，每一个都可能正好对上 LLM 的某个痛点。MemGPT 翻到的是“虚拟内存”这一页；MemOS 翻到的是“存储分层与调度”那一页；一定还有人在翻“文件系统权限模型”那一页。跨学科的类比不是修辞，是生产力。

更深一层，我觉得 MemGPT 悄悄改写了“记忆”的定义。在它之前，大家默认记忆是训练出来的东西——要么在预训练语料里，要么在微调权重里；在它之后，记忆成了运行时的东西——一张可以被读写的便签、一个可以被查询的仓库。本系列前面讲的 ReasoningBank 的记忆银行、Agent KB 的共享知识库、MemOS 的记忆立方体，本质上都是沿着这条路往下走：把“学习”从梯度下放到读写操作。模型参数不变，状态在变——这可能是通向持续学习最朴素的第一块踏脚石。

而 MemGPT 与 MemOS 的对照尤其耐人寻味。MemGPT 的哲学是“自治”：让 LLM 自己当内核，自己管理自己，优雅，但黑盒；MemOS 的哲学是“分层”：记忆该交给独立的操作系统去调度，可控，但笨重。这几乎就是操作系统史上“微内核 vs 宏内核”之争在 AI 世纪的复刻。两篇文章隔着两年遥遥相望，谁也没说服谁——而这场架构路线之争，大概率会伴随整个记忆赛道的青春期。

留个问题给你 上下文窗口这几年涨了一百倍不止，百万 token 的模型已经不稀奇。有人因此宣判“记忆管理已死”。可 lost in the middle 从未根治，长窗口的推理成本更是随长度高企。你觉得：当窗口真的“无限长”的那天，我们还需要 MemGPT 这样的操作系统吗？还是说，“能用注意力看完一切”和“该看什么才看什么”，永远是两个问题？
