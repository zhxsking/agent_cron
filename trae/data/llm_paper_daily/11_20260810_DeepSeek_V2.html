2024 年 5 月，国内大模型 API 市场突然被一颗"价格炸弹"击中——DeepSeek-V2 的 API 定价只有 GPT-4 Turbo 的百分之一左右，而且中文 benchmark 还能跟 LLaMA3-70B 打得有来有回。一时间所有人都在问同一个问题：凭什么？

凭什么一家成立不到一年的团队，能在 236B 总参数的 MoE 模型上把推理做到这么便宜？答案不在神秘的数据配方，也不在炼丹玄学，而藏在论文第 2 节那两个看起来毫不起眼的小标题里——多头潜在注意力（MLA）和细粒度专家混合（DeepSeekMoE）。一篇关于"少存一点什么"的论文，就这样改写了开源 MoE 的游戏规则。

一句话总结 DeepSeek-V2 用 MLA 把每个 token 在 KV cache 里要存的东西从"完整 K/V"压成一个低维潜向量（约 1/14 大小），同时用细粒度 + 共享专家的 DeepSeekMoE 让 21B 激活参数打出 70B 稠密模型的能力——KV cache −93.3%，训练成本 −42.5%，吞吐 ×5.76。

01领域定位

上一篇我们聊到 Mixtral 8x7B 把 MoE 这扇门踹开，但也留下了一个尴尬的副作用——46.7B 参数全得常驻显存。算力省了，显存却更贵了，长上下文推理时 KV cache 更是先一步把 HBM 撑爆。这是 2024 年初所有 MoE 模型的共同痛点。

DeepSeek-V2 就站在这个十字路口：它承接了 Mistral/Mixtral 开源 MoE 的工程经验，又承接了 Google 系 GShard/Switch Transformer 在 MoE 理论上的早期积累；同时它第一次把"重新设计注意力机制"这件事放到开源 LLM 主舞台上——此前 LLaMA、Mistral 都只是把 Transformer 标准件照搬放大，没人敢动 attention 内部结构。DeepSeek-V2 动了，而且动得很彻底。

它的历史位置可以这样概括：开源 MoE 从"架构搬运"走向"架构创新"的分水岭。在这之后，MLA + 细粒度 MoE 成了 DeepSeek-V3、DeepSeek-R1 一脉相承的"家族标志"，也成了无数国产开源模型模仿的对象。

02研究背景

要理解 DeepSeek-V2 为什么非动 MLA 不可，得先看清楚一件事：在大模型推理阶段，真正的瓶颈不是算力，而是显存带宽。

每次生成一个新 token，模型都得把所有历史 token 的 K、V 拉进 GPU 算一遍 attention。这些历史 K/V 不会被重复计算，于是被缓存下来反复读取——这就是 KV cache。问题在于它的体积会随上下文长度线性增长：以 DeepSeek-V2 的配置（128 头 × 128 维 × 60 层）算，单个 token 在 MHA 下要存约 196 万个元素，128K 上下文一上，KV cache 轻轻松松把 HBM 撑爆，算力反而闲着等数据。

此前的开源解法是 GQA（Grouped-Query Attention）——让多个头共享同一组 K/V，比如 LLaMA-2/3 就是这么做的。GQA 确实把 cache 砍下来一截，但代价是性能也跟着掉。论文附录 D.1 的消融实验很直白：在 7B 同等规模下，GQA 和 MQA 在大部分 benchmark 上都不如 MHA。

另一边，Mixtral 8x7B 把开源 MoE 推上了主流，但它有个刺眼的问题——稀疏激活省了 FFN 的算力，可 attention 部分一点没省。也就是说，MoE 越大、上下文越长，KV cache 越成为头号大胃王。MoE 让 FFN 这条腿跑得飞快，attention 那条腿却还拄着 MHA 的拐杖。

DeepSeek 团队想要的就是：既能像 MHA 那样保持每个头独立的表达能力，又能像 GQA/MQA 那样省下 cache——最好是鱼和熊掌都不放过。

类比 · 仓库管理员的故事 把 attention 想象成一个仓库管理员：每来一个新订单（query），他都得去仓库里翻所有历史订单的存档（K/V），看看哪个最相关。

MHA 是每个管理员在仓库里各存一份完整档案，重复得离谱；GQA 是几个管理员共用一份档案，省了地方但每次只能查到同一批信息，灵活度打折；MQA 更极端——所有管理员共用同一份档案，最省，但也最死板。

MLA 的思路截然不同：仓库里不存档案原件了，只存一份"档案摘要"（潜向量），每个管理员需要时各自从摘要里"还原"出自己那份档案。摘要体积小，但能还原出来的信息量却不输原件。这就是"低秩压缩"的精髓。

03核心问题

把背景压成一句话，DeepSeek-V2 要回答的是：能否设计一种新的注意力机制，在保持（甚至超越）MHA 表达能力的同时，把 KV cache 压到接近 GQA/MQA 的水平，并把它和细粒度 MoE 一起塞进一个能实战部署的 236B 模型？

这其实是三个子问题捆在一起：

  • 表达力：能否不靠"共享头"这种粗暴手段，仍能压 cache？
  • MoE 协同：新 attention 能不能跟稀疏 FFN 一起把训练成本也拉下来？
  • 系统可落地：新设计能不能跑在实际 GPU 上，而不是只在论文里好看？
思考一下 如果你来设计，在不削弱每个头表达能力的前提下压 KV cache，会从哪里下手？是"少存几个维度"还是"换一种存法"？先想 30 秒再往下看。

04方法详解

DeepSeek-V2 仍然沿用 Transformer 的整体骨架（PreNorm、RoPE、RMSNorm、SwiGLU 一个不少），但同时换了两个组件：把 attention 换成 MLA，把 FFN 换成 DeepSeekMoE。我们一个一个看。

4.1 MLA：把 K/V 压成一条潜向量

MLA 的核心是低秩键值联合压缩。具体分三步。

第一步，下采样。对当前 token 的隐状态 $h_t$，用一个矩阵 $W^{DKV}$ 把它压成一条短得多的潜向量 $c_t^{KV}$：

$$ c_t^{KV} = W^{DKV}\, h_t,\qquad c_t^{KV} \in \mathbb{R}^{d_c},\ d_c \ll n_h \cdot d_h $$ (1)

在 DeepSeek-V2 的配置里 $d_c = 512$，而原始 K/V 的总维度是 $n_h \cdot d_h = 128 \times 128 = 16384$——直接压到 1/32。这条 $c_t^{KV}$ 才是真正要存进 KV cache 的东西。

第二步，上采样还原。真正要算 attention 时，再用两个矩阵 $W^{UK}$ 和 $W^{UV}$ 把潜向量分别还原成各头的 K 和 V：

$$ k_t = W^{UK}\, c_t^{KV},\qquad v_t = W^{UV}\, c_t^{KV} $$ (2)

这里有个非常聪明的工程细节：推理时不需要真的把 K、V 物化出来。把 $W^{UK}$ 吸收进 query 的投影矩阵里，attention 分数可以直接用 $q \cdot c_t^{KV}$ 算出来——也就是说，压缩这一步不仅省了显存，还顺手省了一次大矩阵展开。这种"算路改写"是 MLA 能真正跑得快的工程关键，论文附录 C 把所有变形公式都写明白了。

第三步，解耦 RoPE。这里有个看似不起眼但极为关键的细节。DeepSeek-V2 沿用 RoPE 做位置编码，但 RoPE 是位置敏感的旋转——它要求 K 在被使用前先做旋转。如果对压缩后的潜向量 $c_t^{KV}$ 直接套 RoPE，会破坏掉它"低秩可还原"的结构，前面的省算路技巧就废了。

解法是解耦：另开一条小路专门走 RoPE。从 $h_t$ 单独投影出一个小维度（$d_h^R = 64$）的"位置键" $k_t^R$，它绕开潜向量、独立做 RoPE。最终的 attention 分数是两部分相加：

$$ q_t \cdot k_j = \underbrace{q_t^C \cdot (c_j^{KV})^\top}_{\text{内容分数}} + \underbrace{q_t^R \cdot (k_j^R)^\top}_{\text{位置分数}} $$ (3)

这样一来，位置信息走自己的小通道，内容信息走潜向量的大通道，互不打架。最终每个 token 在 cache 里只需要存 $d_c + d_h^R = 512 + 64 = 576$ 个元素。

4.2 DeepSeekMoE：细粒度 + 共享专家

attention 解决了 cache 问题，FFN 这一边也不能闲着。DeepSeek-V2 没有沿用 Mixtral 的"8 个大专家选 2 个"那种粗粒度方案，而是把自家的 DeepSeekMoE 搬了过来，做了两件别人没做过的事。

第一件，细粒度专家分割。把每个原本粗大的专家，沿中间隐藏维度切成 m 个小专家，每个小专家的中间维度只有原来的 1/m。同时把激活专家数从 K 个增加到 mK 个——总计算量不变，但每个 token 可选的专家组合数从 $\binom{N}{K}$ 暴涨到 $\binom{mN}{mK}$。组合灵活度的指数级增长，意味着同样的算力能学到更精细的知识分工。

第二件，共享专家隔离。挑出 $K_s$ 个专家当"常驻班"——无论路由器怎么决定，这 $K_s$ 个共享专家对每个 token 都激活。它们的职责是处理那些所有 token 都需要的通用知识（语法、常用搭配等），让路由专家不必再各自重复学一遍。在 DeepSeek-V2 里，这个配置是：160 个路由专家 + 2 个共享专家，每个 token 激活 6 个路由专家 + 2 个共享专家，合计 8 个细粒度专家。

$$ h_t^l = \underbrace{\sum_{i=1}^{K_s} \text{FFN}_i(u_t^l)}_{\text{共享专家，必激活}} + \underbrace{\sum_{j=K_s+1}^{mN} g_{j,t}\, \text{FFN}_j(u_t^l)}_{\text{路由专家，Top-K 选择}} + u_t^l $$ (4)
类比 · 医院的分诊系统 把每个 token 想象成一个来看病的病人。Mixtral 那种粗粒度 MoE 就像只有 8 个全能主任医师——每个病人随机派 2 个，可主任医师啥都得会，知识容易混杂。

DeepSeekMoE 的细粒度方案，是把每个主任医师拆成 4 个更专的副主任医师，总人数从 8 变成 32，但每人更专一。每个病人依然只看 2 个人次（细粒度后是 8 个副主任医师人次），但配对组合灵活得多——总能找到更对症的组合。

共享专家则是全科门诊——每个病人必先去全科做基础检查（处理通用知识），再按需转诊给副主任医师。这样副主任医师不必每个人都自学一遍全科知识，省下的容量可以更专一。

4.3 把两件事缝在一起：训练与对齐

有了 MLA + DeepSeekMoE，剩下的就是把它们组装成一个能训练的庞然大物。DeepSeek-V2 的整体结构是：

  • 60 层 Transformer，隐藏维度 5120，128 个注意力头 × 128 维
  • 第 1 层是 Dense FFN（暖身），其余 59 层全部是 DeepSeekMoE
  • 总参数 236B，每 token 激活 21B，原生支持 128K 上下文
  • 预训练语料 8.1T tokens，多源高质量数据，中文比例明显高于 LLaMA 系

对齐阶段走的是 SFT + RL 两段式，这里有个伏笔——RL 用的不是 PPO，而是 DeepSeek 自家的 GRPO（Group Relative Policy Optimization），去掉 critic 网络、用一组采样的相对奖励做基线。这个细节在 V2 里只是露了一面，等到 V3/R1 才真正大放异彩，下一篇再说。

MoE 训练特有的几个工程问题，论文也逐一接住：设备限制路由（每个 token 最多落到 4 个 GPU 上，省 All-to-All 通信）、三层负载均衡损失（专家级 + 设备级 + 通信级）、token-dropping（专家过载时主动丢一些 token，保吞吐）。这些都是后面 V3"无辅助损失"方案要进一步优化的痛点。

05实验结果

结果一上来就很反常识——一个 21B 激活参数的 MoE，在大多数 benchmark 上能跟 LLaMA3-70B 这种 70B 稠密模型平起平坐。换言之，DeepSeek-V2 用约 1/3 的激活算力，拿到了同档位的表现。

BenchmarkLLaMA3 70BMixtral 8x22BDeepSeek-V1 67BDeepSeek-V2
MMLU（英文综合）78.977.871.378.5
BBH（推理）81.078.968.778.9
HumanEval（代码）48.246.3—45.7
GSM8K（数学）83.083.7—79.2
C-Eval（中文综合）65.254.6—81.7
CMMLU（中文综合）67.253.4—84.0

读这张表，有几个细节值得圈出来。

第一，中文遥遥领先。C-Eval/CMMLU 上 DeepSeek-V2 把 LLaMA3-70B 甩开 15 分以上——这不是中文数据简单"多"出来的，而是 8.1T 语料里中文配比和清洗策略有意识的设计。

第二，英文综合（MMLU）几乎追平 LLaMA3-70B。78.5 vs 78.9，差距已经小到统计噪声级别，可激活参数只有对方的 30%。

第三，代码与数学还略逊一筹。HumanEval/GSM8K 上落后 LLaMA3/Mixtral 4-5 分。这其实是 V2 留下的尾巴，后面 V3 在数学推理上的爆发，正是从这里补的课。

第四，最关键的是效率-能力曲线被整体推上去了。论文 Figure 1(a) 那张"激活参数 vs MMLU"散点图上，DeepSeek-V2 的点位于 Pareto 前沿，明显高出"激活参数相近"的开源模型一截。

对齐后的聊天版本表现同样亮眼：在 AlignBench（中文综合对话）拿到 8.97 分，MT-Bench 8.97，做到了当时开源对话模型的中文第一梯队。

06影响与意义

DeepSeek-V2 的影响是分层的，从浅到深可以拆成三层。

最浅一层：把开源 MoE 的"性价比"立成新基准。论文里那句"21B 激活打出 70B 表现"被反复引用，直接推动了后面 Qwen-MoE、OLMoE、Phi-3.5-MoE 等一系列"小激活大容量"的开源 MoE 出现。"激活参数"从此成了一个比"总参数"更被关注的指标。

中间一层：MLA 让"重新设计 attention"成为可能。自 Transformer 论文以来，主流 LLM 几乎没人敢动 attention 的内部结构——LLaMA 系、Mistral 系、Qwen 早期全是 MHA 或 GQA 的微调。MLA 是第一个被实战验证、能在大模型上跑通、还跑出更好效果的"非主流"注意力。它告诉所有人：attention 不是不能改，是之前没人想清楚怎么改。

最深一层：把"算法-系统协同设计"这件事变成了范式。MLA 的设计完全围绕HBM 带宽瓶颈展开——不是先有数学优雅再有性能，而是先看清"瓶颈在哪"再倒推数学结构。这种思路后来成了 DeepSeek 整个团队的标志：V3 的 FP8 训练、无辅助损失负载均衡、MTP（多 token 预测）全是同一种"系统驱动算法"的哲学。可以说，DeepSeek-V2 是这家团队"方法论风格"的奠基作。

07局限性与未来方向

但 DeepSeek-V2 不是没有代价，论文自己也坦白了几处。

第一，显存账还没还清。MLA 把 KV cache 砍了 93.3%，但 236B 总参数仍然全部要常驻显存——这跟 Mixtral 的"大胃病"是一回事，只是胃变小了一号。消费级显卡照样跑不动满血 V2，部署门槛还是高。

第二，解耦 RoPE 是个工程妥协，不是原理性方案。论文很坦诚地解释：RoPE 跟低秩压缩在数学上"打架"，所以才另开一条小路绕过去。这意味着 MLA 的设计空间被 RoPE 卡住了一截——如果换一种位置编码（比如 ALiBi、NoPE），结构还能进一步简化。这是留给后来者的题目。

第三，token-dropping 会丢信息。专家过载时主动丢弃部分 token 换吞吐，这种"先丢为敬"的策略在训练稳定性上是有效的，但对小批量、长尾分布的 token 来说有损精度。V3 后来用"无辅助损失"的偏置微调方案替代了它，正是对这个痛点的回应。

第四，数学与代码能力还落后于闭源旗舰。GSM8K 79.2、HumanEval 45.7，相对 GPT-4 时代的水平差距明显。这也是 V3/R1 后续要重点补的课——R1 在数学推理上的爆发，本质上就是从 V2 的底座继续往上长出来的。

08领域演进脉络

把 MLA 和 DeepSeekMoE 这两条暗线分别拉出来看，能更清楚地看到 DeepSeek-V2 在历史里的位置。

Attention 演进线：2017 年 Transformer 提出 MHA，每个头独立存一份 K/V——表达力满但 cache 巨大。2019 年 Shazeer 提出 MQA（所有头共享一份），把 cache 砍到极致但精度下降。2023 年 Ainslie 的 GQA 折中，被 LLaMA-2/3 采用。2024 年 5 月，DeepSeek-V2 用 MLA第一次把"压缩"和"共享"换成另一条思路——低秩潜向量，并证明能在不损失精度的情况下越过 GQA 的下限。

MoE 演进线：1991 年 Jacobs & Hinton 提出 MoE 雏形；2017 年 Shazeer 用稀疏 Top-K 唤醒它；2020-2022 年 Google 密集产出 GShard、Switch、GLaM、ST-MoE，但全闭源；2023 年 12 月 Mistral 7B 出场，2024 年 1 月 Mixtral 8x7B 把开源 MoE 推上主流。2024 年 1 月 DeepSeekMoE 论文（arXiv 2401.06066）提出"细粒度 + 共享专家"，2024 年 5 月 V2 把它放大到 236B 并验证可用。这条线在 V3（671B）达到第一个高峰，R1 则把它和强化学习绑在一起推向推理赛道。

整体路线：从 Mixtral 的"开源 MoE 可行" → DeepSeek-V2 的"开源 MoE 可创新" → V3 的"开源 MoE 可极致" → R1 的"开源 MoE + RL 可对标 o1"。本系列读到第 11 篇，正好走到这条线从量变到质变的转折点。

09趣味延伸

DeepSeek-V2 论文之外的故事，比论文本身还要热闹。

背景：从量化基金到大模型。DeepSeek 背后是幻方量化——一家靠算法交易起家的对冲基金。创始人梁文锋在 2023 年成立 DeepSeek 时，团队里很多人没做过 NLP，反而是系统、高性能计算、芯片背景居多。这点其实能解释很多事：MLA 那种"先看带宽瓶颈再设计数学结构"的思路，本质上是量化研究员看交易系统延迟的肌肉记忆。换一个 NLP 出身的团队，未必会从 HBM 带宽这个角度切入。

价格战：1/100 的 API。V2 上线时 API 定价是每百万 token 1 元人民币左右，而当时 GPT-4 Turbo 折算下来要 100 多元。价格差到 100 倍直接引爆了国内"API 一元时代"——智谱、月之暗面、阿里通义、字节豆包全都跟着调价。一篇学术论文引发了商业市场重新洗牌，这种事在大模型圈其实非常少见。

"开源吓坏了硅谷"。V2 之后，国外对 DeepSeek 的关注急剧升温。Semianalysis、Interconnects 等技术评论开始认真分析 MLA 的数学细节，承认这是"非西方团队第一次在大模型架构层面提出被认真对待的新方案"。

命名的小细节。"DeepSeek" 这个名字本身就带着团队气质——seek 不是 build，不是 train，是"寻找"。幻方起家时叫 High-Flyer，也是这股子"探索派"的味道。

10个人解读与延伸思考

读 DeepSeek-V2 这篇论文，最让我感慨的不是 1/14 的 cache 压缩比，也不是 5.76 倍的吞吐，而是这家团队"先看清瓶颈，再设计算法"的工作方式。

大部分 LLM 论文是反着来的——先有一个数学上漂亮的 idea，再去找它在系统上"恰好"也快。这种思路经常撞墙：idea 是好的，但要么显存爆了、要么通信卡了、要么训练不稳定。DeepSeek-V2 完全是另一条路：从"decode 阶段 GPU 在等数据"这个具体现象出发，反推"那 K/V 该怎么存才能少读几次"，最后才落到 MLA 这个数学结构上。它不是"算法找系统"，是"系统找算法"。

这种范式有它独特的复利效应。一旦一个团队习惯了"看系统瓶颈→改算法"，下一次遇到新瓶颈（FP8 精度、通信开销、推理延迟）就能很快出活——这也是为什么 DeepSeek 后面 V3、R1 的产出节奏能这么密。论文之间不是孤立的"灵感闪现"，而是一条主线在迭代。

对从业者来说，DeepSeek-V2 还留了一个启示：在大模型这个高度工程化的领域，"懂系统"和"懂数学"正在变成同一种能力。只会推公式而不懂 GPU 内存层次的研究者，会越来越难做出有影响力的工作；只会调系统而不懂数学结构的人，也卡在工程优化的天花板。DeepSeek-V2 这种"两个圈交集"的工作，恰恰是未来 LLM 研究的典型形态。

留个问题给你 如果 RoPE 跟低秩压缩"打架"是 MLA 必须解耦的根本原因，那换一种位置编码（比如 ALiBi、或者干脆 NoPE），MLA 是不是能进一步简化？这条小路在 V3 里走通了吗？读完下一篇你就会知道答案。

DeepSeek-V3 Technical Report

V2 把 MLA + 细粒度 MoE 的招牌立起来了，V3 要把它放大到 671B 总参数 / 37B 激活，并端出三道更狠的菜：FP8 混合精度训练把成本压到 557.6 万美元、无辅助损失的负载均衡让 MoE 训练更稳、多 token 预测（MTP）让推理再加速。当一套架构被推到极致，故事才真正到了高潮——而且，R1 的火种已经在 V3 里悄悄埋下了。
