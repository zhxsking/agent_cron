大模型经典论文精读系列 #028

Graph of Thoughts: Solving Elaborate Problems with Large Language Models Graph of Thoughts：把思维树升级成思维图——允许不同分支的思路合并、回溯与重用，让推理从树形探索走向网状协同

作者：Maciej Besta, Nils Blach, Ales Kubicek, Robert Gerstenberger, Michał Podstawski, Lukas Gianinazzi, Joanna Gajda, Tomasz Lehmann, Hubert Niewiadomski, Piotr Nyczyk, Torsten Hoefler（共 11 位） 机构：ETH Zürich (SPCL) / Warsaw University of Technology / Cledar 发表：2023-08 / arXiv（AAAI-24 收录）
arXiv GitHub

设想你在策划一场复杂的多日旅行：行程、预算、景点、同伴偏好、天气……你会在纸上列出几条候选路线，比较它们；写着写着发现路线 A 的"住宿段"其实可以塞进路线 B 里，于是你把两段思路合并成一个更优的方案；接着你回头改掉了第一晚的住处，又把删掉的旧想法捡回来重新评估。一通操作下来，纸上不是一条直线，也不是一棵规整的树，而是一张涂涂改改、互相勾连的网。

这恰恰是 2023 年以前大语言模型最难做到的事。从思维链到思维树，模型要么只能"一条道走到黑"，要么只能在树形分叉里探索、回退——每个中间想法都有且只有一个父亲，谁也没法把两条岔路上的好点子合并成一个新答案。这篇来自 ETH 苏黎世高性能计算实验室的论文，要解决的就是这件"司空见惯却一直被结构封印"的小事。

一句话总结 把 LLM 的推理过程建模成一张任意图，让"合并、精炼、回溯"成为一等公民——在排序任务上比思维树质量高约 62%、成本低 31% 以上，并首次给出"思维体积"这个衡量提示策略潜力的指标。

01领域定位

把目光从"模型本身"挪开，只看提示范式这条暗线，它的形状演化极其优雅：先是一条链（Chain-of-Thought，让模型把推理拆成步骤），再是一束平行链（Self-Consistency，多想几遍再投票），接着长成一棵树（Tree of Thoughts，分叉、评分、回溯）。每一步都在"解锁更复杂的拓扑结构"。

而 Graph of Thoughts（下文简称 GoT）站在这条演化的下一站：把树彻底松绑成任意图，允许一个想法同时被好几条思路"喂养成型"，也允许它回头精炼自己。它承接了 ToT 的搜索与回溯，开启了"网状协同推理"这一族——后来 LangGraph 这类 agent 编排框架、以及同一团队的 Topologies of Reasoning、Knowledge Graph of Thoughts，都能看到它的影子。

02研究背景

GoT 出现前，结构化提示已经走过三代，但每一代都背着同一个隐含约束：每个想法只有一个来源。

  • IO prompting：一道题、一个答案，单点。
  • Chain-of-Thought：把推理显式拆成一串中间步骤，形成一条链——但只能走直线，错了没法回头。
  • Self-Consistency (CoT-SC)：多采几条链再投票，仍是互不相交的平行链，链与链之间不交换信息。
  • Tree of Thoughts：把链长成树，能分叉、能评分、能回溯——但树上每个节点依旧只有一个父亲，两条岔路走到一半想"合流"？做不到。
类比 把推理想成在白板上解一道大题。CoT 像只能从上往下写一列算式，写错了只能划掉重来；CoT-SC 像在白板边贴了好多张小纸条、最后数哪张票多；ToT 像画了一棵决策树，可以回到上一层换条岔路。可现实里解题的人会做一件它们都做不了的事——把左半边的思路和右半边的思路圈在一起，合成一段新解。GoT 就是把这块白板的拓扑从"树"松绑成"网"，让"合流"成为合法动作。

更妙的是，作者把动机挂回了三个本就在"成网"的现象：人类推理会跨链合并点子、大脑神经元以递归回路相连、算法执行天然就是有向无环图（DAG）。换句话说，图才是更自然的推理骨架，链和树只是它的退化特例。

03核心问题

一句话：如何在不动模型权重的前提下，让 LLM 的中间想法能合并、精炼、回溯、复用，并且把这套机制做成一个可扩展、可复用的工程框架，而不是某道题的临时手抖？

思考一下 如果树已经能分叉、能回溯了，那从"树"到"图"到底多出了什么能力？换个问法：有没有什么任务，是树结构在原理上就表达不了的？

提示在前文类比里：树表达不了"两条独立岔路的合流"，也表达不了"一个想法反复精炼自己"的自环。这正是 GoT 要补的两块拼图。

04方法详解

GoT 的方法可以拆成三层：先把推理建模成图，再定义图上的一组操作，最后用一套静态/动态双图架构把它工程化。

步骤一：把推理过程建模成有向图

推理过程被抽象成一个四元组 $(G, T, E, R)$：

  • 顶点 $V$ 是一个个 LLM 思想（一段段中间解，可以是一段话、一个排好序的数列、一段代码草稿）；
  • 有向边 $(u,v) \in E$ 表示"想 $v$ 是把 $u$ 当直接输入生成出来的"；
  • $T$ 是可施加的思想变换集合；$E$ 是给某个思想打分的评估函数；$R$ 是按分数挑出前 $h$ 名的排名函数。

关键在于：这里的图不限定是树，可以是 DAG，甚至可以有自环。一个节点可以有任意条入边——这正是"合流"得以发生的数学基础。

步骤二：四种思想变换

每次变换 $T(G, p_\theta)$ 都在重写图：加入新点和新边、必要时删掉旧点旧边。形式化写作：

$$ V' = (V \cup V^{+}) \setminus V^{-}, \qquad E' = (E \cup E^{+}) \setminus E^{-} $$ (1)

其中 $V^{+}, E^{+}$ 是新增的点和边，$V^{-}, E^{-}$ 是被移除的。围绕这套重写，论文重点定义了三种"图原生"变换（外加由删边达成的回溯）：

把它们的形式化写出来：

  • 聚合：$V^{+}=\{v^{+}\}$，$E^{+}=\{(v_1,v^{+}),\dots,(v_k,v^{+})\}$——把 $k$ 个想法汇入一个新节点，这是树结构在原理上表达不了的动作。
  • 精炼：$E^{+}=\{(v,v)\}$——一条自环，代表"基于反馈再改一遍它自己"。
  • 生成：从一个父节点生出 $k$ 个子节点，ToT 的分叉、CoT-SC 的多次采样都被它涵盖。
为什么这是真正的"升级" ToT 的分叉 = 生成；ToT 的回溯 = 删边。也就是说树是图的退化特例。GoT 真正新增的是"聚合"和"自环"——前者让独立岔路能合流，后者让一个想法能被反复打磨。论文把这两类操作称作graph-enabled transformations，是链和树"天然表达不了"的。

步骤三：思维体积——为何"图"能赢

论文给了一个漂亮的理论指标：思维体积。一个想法 $v$ 的体积，等于能通过有向路径走到 $v$ 的、它之前的所有想法数量——直观说就是"最终答案能吸收多少上游信息"。

在总预算 $\Theta(N)$ 个想法下，四种拓扑的延迟与体积对比如下：

拓扑结构延迟最终想法体积
IO单点11
CoT一条链NN
CoT-SCk 条平行链N/kN/k
ToT树logk Nlogk N
GoT图（含聚合）logk NN

读这张表的重点在最后两行：ToT 用分叉把延迟压到对数级，但代价是每个叶子只能看到根到叶那一条路，体积也只剩对数；GoT 在同一棵"分叉树"上额外加几条聚合边，就让最终答案能依赖全部 $N$ 个想法——低延迟与高体积兼得。这是 GoT 最核心的理论卖点。

步骤四：静态 GoO + 动态 GRS 的工程架构

要把上面的抽象跑起来，论文给了一套模块化架构，核心是两张图：

  • Graph of Operations (GoO)——静态图，由用户事先写好：节点是要执行的操作（Generate / Aggregate / Score / KeepBestN / Improve / GroundTruth 等），边是数据流向。相当于"推理的剧本"。
  • Graph Reasoning State (GRS)——动态图，运行时由控制器边走边搭：真正生成的那些思想节点、它们的依赖、分数、合法性。

围绕它们的有四个组件：Prompter（把当前 GRS 编码成发给 LLM 的提示）、Parser（把 LLM 回复解析回结构化思想并更新 GRS）、Scoring & Validation（打分校验，可由 LLM 或人来做）、Controller（按 GoO 调度、决定何时停、何时换变换）。整套流程还把每次 LLM 调用序列化成 JSON，方便事后审计成本与中间想法。

这套设计把"用图编排推理"变成了可声明、可扩展的工程问题：换任务只需重写 GoO，换模型只需替换 LLM 包装器，新增变换只需加一个操作类——这也是它区别于"某道题的 prompt 技巧"的关键。

05实验结果

论文在四个天然需要"合流"的任务上对比 IO、CoT、CoT-SC、ToT 与 GoT，主力模型是 GPT-3.5（预算考虑，GPT-4 与 Llama 2 有限验证；Llama 2 表现通常不及 GPT-3.5）。每任务 100 个样本（文档合并为 50），温度 1.0，4k 上下文（文档合并 16k）。

排序（32/64/128 元素）中位错误数比 ToT 降约 62%同时成本降 >31%
集合交（32/64/128 元）集合越大优势越明显IO/CoT 随规模快速崩

排序任务最能体现 GoT 的"分治+合流"哲学，也是头条数字来源：

四个任务呈现出同一种模式：凡是能"拆成独立子块、各解其解、再合流"的问题（排序、集合交、关键词计数、文档合并），GoT 都把质量顶上去、把成本压下来；而越是规模变大、答案塞不进单条链的任务，它相对 IO/CoT/ToT 的优势越大。关键词计数那条"GoT 解对 25 题 vs CoT 1 题 vs ToT 0 题"的反差，几乎是一张图就能说服你"为什么合流这么重要"。

06影响与意义

GoT 的贡献不止于"又一个 prompting 技巧"，它至少在三条线上留下了痕迹：

  • 理论语言：它给"提示策略"配了一组可比较的术语——拓扑、变换、思维体积。同一团队后来的综述 Topologies of Reasoning 把链/树/图排进一个统一分类法，GoT 是其中"最一般的拓扑"。
  • 工程范式：GoO + GRS + Controller 这套"声明式编排 + 动态状态图"的思路，几乎就是后来 LangGraph 这类 agent 编排框架的雏形——把 LLM 调用组织成一张可遍历的状态机图。
  • 后续研究：衍生出分层版 HGoT（用于检索增强事实性评估）和持久知识图版 Knowledge Graph of Thoughts，把"图"从单次推理延展到跨轮记忆。

更重要的是，它把一个直觉钉进了社区共识：链和树只是退化，网状协同才是更接近人脑/算法执行本质的推理骨架。这个直觉后来在 agent 时代被反复验证。

07局限性与未来方向

表达力的代价也很实在，论文与后续实践都点出了几处：

  • 图要人手画：GoO 由用户事先指定，分解点、聚合时机、$N$ 取多少都得人工调，没有自动合成器——一次性任务里"设计图"的成本可能盖过收益。
  • 评分是命门：每个 Aggregate/KeepBestN 都依赖评分函数，打分一旦跑偏，错误会沿图传播。
  • 对"合不了"的任务收益有限：在难以干净分块的问题上，头条质量与成本增益会缩水；GoT 最值当的场景是结构天然可分、可合流的。
  • 模型覆盖有限：主体实验在 GPT-3.5，GPT-4 受预算限制，Llama 2 表现更差，跨模型族的迁移性留了口子。
  • 调参旋钮多：何时聚合、何时生成、KeepBestN 留几个，都是 CoT 没有的新旋钮，流水线容易变脆。

未来方向也清晰：自动合成 GoO、更鲁棒的评分、把"图"从单次推理延展到持久记忆与多 agent 协作——后两者已被 KGoT 与 agent 框架部分接住。

08领域演进脉络

把镜头拉远，这条"思想结构"的演化脉络是这样一脉相承的：CoT 证明"把推理显式拆步"有用 → CoT-SC 证明"多想几遍再投票"更稳 → ToT 证明"分叉+评分+回溯"能在搜索类任务上更强 → GoT 把结构松绑成图，证明"合流+自环"能兼顾低延迟与高信息体积。再往后，这条线并未终结于"提示期"：当 o1、R1 把推理搬进训练阶段、用强化学习让模型自发产生长思维链，"思想结构"的编排权部分从人手里交还给了模型本身——但 GoT 留下的"网状协同"直觉，依然是 agent 时代编排多步推理的底色。

09趣味延伸

这篇论文最有意思的"出身"，是它不在 NLP 实验室诞生。作者团队来自 ETH 苏黎世的 SPCL（Scalable Parallel Computing Laboratory）——一个高性能计算与图计算的研究组，资深作者 Torsten Hoefler 是 HPC 领域的顶尖学者，第一作者 Maciej Besta 本行做稀疏图计算。对一个整天和 DAG、并行调度、计算图打交道的人来说，"把推理组织成一张可遍历的图"几乎是肌肉记忆——所以 GoT 读起来有种系统人的干净利落：不调权重、不炼丹，直接把推理当分布式系统来编排。Besta 也凭这条线的工作连拿 IEEE TCSC 与 TCHPC 两个早期职业奖。

另一桩趣事是撞名：2023 年前后叫 Graph of Thoughts 的论文有好几篇（有偏模型内部图编码的、有偏逻辑推理的），但 Besta 这篇凭借"框架 + 开源 + AAAI 收录"成了被引用最多、社区默认指代的那一个。开源仓库 spcl/graph-of-thoughts 还贴心地支持你用它复刻 CoT、ToT——毕竟在它眼里，链和树都只是图的特例。

10个人解读与延伸思考

读 GoT 我最深的感受是：它把"提示"从文案技巧抬升成了系统设计。一旦你接受"推理是一张可遍历的图"，就再难满足于线性地写一段 prompt——你会开始问：这条子任务能不能并行？那个中间结果要不要回头精炼？两个 agent 的输出该在哪一层合流？这套思维在今天的 multi-agent 与 LangGraph 里几乎成了默认姿势。

但也要清醒：GoT 的收益强依赖问题结构。它对"可分治、可合流"的任务是降维打击，对"一锤子买卖"的线性任务反而是过度工程。把它当成万能开关，不如把它当成一个拓扑选择器——先问"这问题的天然形状是链、是树、还是网"，再决定要不要上 GoT。

留个问题给你 如果模型本身已经被 RL 训得会自发反思、验证、回溯（想想 o1、R1），那"人手画一张 GoO"还有必要吗？还是说，GoT 的未来恰恰是让模型自己学会生成这张图？欢迎你带着这个问题往下读。
