大模型经典论文精读系列 #040

CAMEL: Communicative Agents for “Mind” Exploration of Large Language Model Society CAMEL：用角色扮演 + inception prompting 让两个 LLM 自主对话完成任务——多智能体角色扮演的真正起源，比 AutoGen 早五个月，却被埋进附录

作者：Guohao Li, Hasan Abed Al Kader Hammoud, Hani Itani, Dmitrii Khizbullin, Bernard Ghanem 机构：King Abdullah University of Science and Technology (KAUST) 发表：2023-03 / arXiv · NeurIPS 2023
arXiv GitHub Project

想象一下：你完全不懂股票交易，却想做一个自动交易机器人。你打开 ChatGPT，输入“帮我写个交易机器人”，对方回你一堆似是而非的模板代码。你想追问，却不知道该怎么问——因为你连“止损”“市价单”都说不清楚。人在不懂行的领域里，连提问本身都是个难题。

2023 年 3 月，KAUST 的一群研究者抛出一个看似简单的点子：既然人不会提问，那就让一个 LLM 替你提问，让另一个 LLM 负责回答。两个 agent 自己聊着，把活儿干完。这篇论文就是 CAMEL，它要回答的问题是——能不能让智能体之间自主协作，人类只丢一个想法就够了？

一句话总结 CAMEL 让两个 LLM 分别扮演“AI 用户”和“AI 助手”，用对称的 inception prompting 锁住各自角色，靠多轮对话自主把任务做完——人类只需要给一个模糊的想法和两个角色名。

01领域定位

在大模型的发展史上，CAMEL 处于“agent 化”浪潮的真正起点。在那之前，我们见过 ReAct 让一个模型边想边调工具，见过 Generative Agents 让 25 个 LLM 在小镇上自发地传八卦、办派对。但前者是“单兵作战 + 工具”，后者是“群体涌现 + 仿真”，都还没有一个干净的、面向任务完成的多智能体协作范式。

CAMEL 补上的正是这一块：它定义了“角色扮演 + 起源提示”这套后来被反复复用的最小骨架——一个下指令的 agent、一个干活的 agent、一段锁住身份的系统提示。它是后来 AutoGen、MetaGPT、ChatDev 这些工程化框架的“概念祖先”，只不过 CAMEL 自己把更多篇幅留给了数据生成与行为分析，工程化的故事让给了后继者。

02研究背景

2023 年初，ChatGPT 火了没多久，所有人都在尝试用对话模型干活。但一个尴尬的事实浮现出来：对话模型的成功，严重依赖人能不能问对问题。你让它写代码，它就回一段代码；你提示得不够具体，它就给你一个通用得没用的答案。想要它做得好，你得起码懂这个领域——可如果我真的懂，我还找你干嘛？

论文里举了一个特别到位的例子：一个不懂交易的人，想让模型帮他做一个股票交易程序，他甚至不知道该用“止损”还是“网格”这种词去追问。于是问题被倒过来了——能不能不要人来引导对话，让一个 agent 代替人去“提问”，让另一个 agent 去“回答”？这就是 CAMEL 想解决的事。

类比 把它想成剧组里的两个人：一个是“导演”（AI User），负责提要求、定方向；一个是“演员”（AI Assistant），负责按导演的要求把戏演出来。导演不一定懂表演细节，演员不一定懂整体剧本，但只要他俩都对得上“我们今天要拍哪场戏”这个想法，就能自己把戏拍完——你作为制片人，只需要丢一句“拍一场雨夜分手戏”就够了。

但研究者很快发现，让两个 LLM “自己聊”并没有想象中那么顺。他们做了一些初步实验，结果撞上一堆离谱的失败模式：两个 agent 说着说着就角色对调了（演员开始指挥导演）；assistant 不停重复同一句指令；给出敷衍式回复（“好的，我会做的” 然后就没了）；甚至陷入无限循环，谁也不肯往前走一步。说白了，LLM 的“注意力”太容易被自己上一句话带跑，聊着聊着就忘了自己是谁。

03核心问题

一句话：怎么让两个 LLM 在没有人类持续介入的情况下，稳定地、按各自角色地把一个模糊任务做完？

这里其实捆着两个子问题：一是怎么让 agent 不跑偏（不角色对调、不无限循环、不敷衍）；二是怎么让这个过程可规模化——不只是跑通一次 demo，而是能批量生成大量高质量的多轮对话数据，用来研究 agent 的行为，甚至反哺训练更强的 LLM。

思考一下 如果让你来设计，你会用什么招数防止两个 agent 忘掉自己的角色？提示工程？硬编码一个状态机？还是干脆每次都把完整的系统提示重新塞进去？先别往下看，自己猜一个 CAMEL 会选哪条路。

04方法详解

CAMEL 的答案很“轻”：不搞状态机，不加额外训练，全部用提示工程解决。整套方法可以拆成三个组件——任务细化器、AI 用户、AI 助手，外加一个叫 inception prompting 的“锁身份”机制。

第一步：Task Specifier（任务细化器）

人类给的输入通常很糙，比如“开发一个股票交易机器人”。CAMEL 先用一个独立的 agent 把它“展开”成更具体的版本，比如“开发一个基于 Python 的 swing trading 机器人，扫描市场趋势、监控个股、生成带止损和止盈的买卖信号”。这一步看起来不起眼，但它直接决定了后续两个 agent 有没有可能聊到点子上——任务越具体，对话越不容易跑偏。

第二步：Role-Playing（角色扮演）

细化后的任务交给两个 agent：AI User 负责“提要求”，AI Assistant 负责“给方案”。它俩轮流说话，每一轮 AI User 给一条指令，AI Assistant 回一个解决方案，循环往复，直到 AI User 自己判定“任务完成了”才停。整个过程没有人类插嘴——这正是不跑偏机制最关键的考验。

第三步：Inception Prompting（起源提示）

这是 CAMEL 的灵魂。研究者给两个 agent 各写了一段对称的系统提示，里面塞满约束：告诉 AI User“你只能给指令、不能替对方干活”，告诉 AI Assistant“你只能回答、不能反过来指挥”，还反复强调“不要重复指令”“不要敷衍”“别陷入循环”。说白了，inception prompting 就是把人类工程师“踩过的坑”预先翻译成 prompt 里的红线。

类比 起源提示像给两个演员各发一张“角色卡”，上面写满“你绝对不能干的事”：导演卡上写“不许抢戏去演”，演员卡上写“不许反过来指挥导演”。每次开演前都把这张卡重新念一遍，保证谁都不会忘了自己是谁。这种“把约束写进系统提示”的思路，后来几乎成了所有多智能体框架的标配。

论文还把这个机制做成了一条可规模化的数据生产线：因为对话完全自动，你可以让它在 50 个 user 角色 × 50 个 assistant 角色的组合上批量跑，自动产出成千上万条多轮指令-解决方案对话。CAMEL 就这样生成了 AI Society、Code、Math、Science 四个数据集，外加一个专门模拟“没对齐的恶意 agent”的 Misalignment 数据集。

05实验结果

实验围绕三个问题展开：CAMEL 生成的方案到底好不好？自动产生的对话数据能不能反过来让小模型变强？这些 agent 协作里到底藏着哪些坑？

第一个问题用两套评委打分：一套是 GPT-4，一套是人类。对比的基线是 gpt-3.5-turbo 单次生成的方案。结果显示 CAMEL 角色扮演产出的方案在两种评估里都明显胜过单次生成——两个 agent 多轮聊出来的，确实比一个 agent 一次性憋出来的强。

第二个问题更有意思。研究者用 CAMEL 自动生成的 AI Society 数据集，渐进式地微调 LLaMA-7B——也就是随着数据越积越多，看模型能力怎么涨。结果是：随着对话数据量增加，小模型在“AI 社会相关”的问题上表现越来越好，呈现出一种知识涌现的趋势。这说明 CAMEL 不只是个跑 demo 的玩具，它生成的数据真的能反过来喂出更强的模型。代码能力方面，团队还在 HumanEval 和 HumanEval+ 上做了基准测试。

第三个问题则是 CAMEL 最诚实的地方。论文专门用一整节列出 agent 协作里出现的“翻车现场”：role flipping（角色对调）、assistant repeats instruction（助手复读指令）、flake replies（敷衍回复）、infinite loop（无限循环）、conversation termination（终止条件难定）。这些不是 bug 报告，而是被当成研究贡献公开出来——后来几乎所有做多智能体的人都得跟这些坑打交道。

06影响与意义

CAMEL 的影响分三层。第一层是概念层：它给整个 agent 领域定下了“角色扮演 + 起源提示”这套最小可行骨架。后来的 AutoGen 把它泛化成“可编程的对话”，MetaGPT 把它工程化成“SOP 流水线”，ChatDev 把它特化成“软件开发流水线”——但根上都长在 CAMEL 这棵树上。

第二层是数据层：AI Society、Code 这些自动生成的多轮指令数据集，给后来研究“对话型指令微调”的人提供了现成的素材，也第一次让人看到“agent 自动产数据 → 反哺训练更强 agent”这条闭环的可能性。

第三层是社区层：开源的 CAMEL 库后来长成了 CAMEL-AI 社区，聚集了 100 多位研究者，催生了 OASIS（百万级 agent 社会模拟）、OWL（通用多智能体助手）、CRAB（跨环境 agent 基准）等一连串后续工作。一个 2023 年 3 月的 arXiv 预印本，硬是养出了一个持续运转的研究集体。

07局限性与未来方向

CAMEL 的局限，论文自己也很坦白。最核心的一条是：所有约束都靠 prompt，没有任何结构性的强制。agent 要是想角色对调，能拦住它的只有系统提示里那句“别对调”，没有协议层的硬保障。这意味着一旦模型变强、上下文变长，prompt 的“软约束”随时可能失效——这恰恰是后来多智能体系统最头疼的事。

其次，论文的评估主要在 GPT-4 上做，评委也包含 GPT-4 自己。审稿人就直接指出：GPT-4 与人类在这项研究里是对齐的，但这不保证在真实执行中一定成功——模型自评的可信度始终是个悬而未决的问号。再者，论文标题里写着“Large Language Model Society”，但实际只验证了两个 agent 互动，“社会”的说法多少有点超前。

后来者的修补方向也清晰：ChatDev 给对话加了流水线结构、MetaGPT 加了 SOP、AutoGen 把对话变成可编程对象——都是在补 CAMEL “纯靠 prompt”这个口子。而 OASIS 等工作则真的把 agent 数量扩到了百万级，把“社会”两个字坐实。

08领域演进脉络

把 CAMEL 放回整条线看，脉络是这样的：Transformer（2017）给了大模型一个能“看到很远”的底座；GPT-3（2020）证明了“大 + 提示”能涌现出多任务能力；CoT / Zero-shot CoT（2022）教会模型“分步想”；ReAct（2022）把“想”和“做”接上工具，单 agent 能边推理边调外部接口。

到了 2023 年，线开始分叉。一边是 Generative Agents，把 25 个 LLM 塞进小镇做“社会仿真”，重点在记忆与涌现；另一边就是 CAMEL，把“两个 agent 协作完成任务”这件事第一次干净地定义出来，重点在角色扮演与起源提示。之后 MetaGPT、AutoGen、ChatDev 接力把这套范式工程化、流水线化，再往后就是 OASIS 把规模拉到百万、OWL 把通用任务自动化拉满。CAMEL 站的，正是这条“agent 协作范式”支线的起点。

09趣味延伸

CAMEL 的命名其实藏着一个彩蛋：CAMEL 是 Communicative Agents for “Mind” Exploration of Large Language Model Society 的首字母缩写——把每个大写字母拎出来正好拼成“骆驼”。骆驼以耐力著称，能长时间不喝水穿越沙漠，这恰好暗合了 CAMEL 让 agent 在无人监督下长时间自主协作的野心。

论文开头还引了电影《盗梦空间》（Inception）里 Dom Cobb 的那句台词：“最顽强的寄生虫是什么？是一个想法。”这正是“inception prompting”这个名字的来源——研究者想表达的，是一个好想法一旦植入 agent，就能自己长成一整套任务。把流行文化台词塞进学术论文开头，在 2023 年的 LLM 圈还不算常见，CAMEL 算是开了个有点俏皮的先例。

还有个被很多人忽略的细节：CAMEL 其实比 AutoGen 早了整整五个月（CAMEL 是 2023 年 3 月，AutoGen 是 2023 年 8 月），但名声却被后者盖过一截。一个可能的原因是 CAMEL 把大量篇幅留给了数据生成与行为分析，工程化叙事偏弱；而 AutoGen 一上来就强调“可编程的多智能体对话框架”，正好戳中了开发者社区最想要的那个点。这多少有点“埋进附录”的意味——但这正是这个系列要把它翻出来重读的理由。

10个人解读与延伸思考

读 CAMEL 最大的收获，是看清了“agent 协作”这件事的真正难点不在算力、不在模型大小，而在怎么让一个 agent 不忘掉自己是谁。这个难点至今没被彻底解决——你看现在几乎所有多智能体框架都在反复设计“角色锁定”“状态管理”“对话收敛”，本质上都是在跟 CAMEL 当年撞见的同一批坑搏斗。

另一个值得琢磨的点：CAMEL 把“失败模式”当研究贡献公开出来，这件事在 2023 年其实挺超前。它等于告诉所有人——别再拿一个跑通的 demo 当成果了，把坑画出来才是真正能推动领域的事。后来 OASIS 做百万级 agent、OWL 做真实任务自动化，回过头看都建立在“先承认 agent 会跑偏”这个诚实的起点上。

放到今天看，CAMEL 的“纯 prompt 软约束”已经不够用了，但它提出的那个核心直觉依然没过时：把人类的“提问权”外包给一个 agent，是让不懂行的人也能用上 AI 的关键一步。今天我们谈 AI 普惠、谈 agent 即服务，根上还是 CAMEL 那个“你只管丢一个想法”的承诺。

留个问题给你 如果让你今天重做 CAMEL，你会用哪些“硬结构”来补上它“纯靠 prompt”的软约束短板？是状态机、是角色权限隔离、还是干脆把角色身份训进模型权重里？欢迎带着这个问题，去看下一篇怎么把角色扮演焊成流水线。
