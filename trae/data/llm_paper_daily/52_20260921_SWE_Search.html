SWE-Search: Enhancing Software Agents with Monte Carlo Tree Search and Iterative Refinement SWE-Search：把蒙特卡洛树搜索塞进 SWE agent——DEI 作者的下一篇：从"委员会投票"走向"树形探索"

作者：Antonis Antoniades*, Albert Örwall*, Kexun Zhang, Yuxi Xie, Anirudh Goyal, William Yang Wang 机构：UC Santa Barbara / Moatless AI / Carnegie Mellon University / National University of Singapore / Mila 发表：2024-10 / arXiv（ICLR 2025 录用）
arXiv GitHub Demo

想象一位围棋棋手，每落一子前都要"在脑子里走完几十手"。她不是顺着一条线往下算，而是同时摆出十几条变化图，看到哪条死路就回退换一条，看到哪条好路就再多算几步。人类高手下棋靠的不是"一手走到底"，而是这种树形探索 + 回溯的本能。

可你看看现在的大模型 agent——它们解题的方式更像是个只会"一条道走到黑"的愣头青：定位到 A 文件就改 A 文件，改完提交，跑测试，对了开心，错了……它还是接着改 A 文件。第 051 篇 DEI 用一个"评审委员会"在事后挑补丁，但解题过程本身依然是线性的。SWE-Search 想干的事就一句话：能不能让 agent 在解题时就像下围棋一样，边走边回头、边走边换路？

一句话总结 SWE-Search 把蒙特卡洛树搜索（MCTS）塞进 SWE agent：用一个能在 git 提交树上来回切换状态的 Action Agent 做探索，用一个既给数字又写人话的 Value Agent 做评估，再用一个会"辩论"的 Discriminator Agent 做终选——五个模型在 SWE-bench 上平均相对提升 23%，让开源小模型逼近 GPT-4o。

01领域定位

这是 SWE agent 支线的第六篇，也是 DEI 的"亲儿子"。第 047 篇 SWE-agent 立"人机接口"标杆，第 048 篇 Agentless 反手问"那连 agent 都不要行不行"，第 049 篇 OpenHands 把 agent 做成开放平台，第 050 篇 MASAI 把一个 agent 拆成五个子智能体，第 051 篇 DEI 把多个现成 agent 编成"评审委员会"。前五篇都在回答"怎么造/挑一个更好的 agent 或补丁"，但解题过程本身始终是线性的——一次行动只指向下一个状态，错了也只能硬着头皮往下走。

SWE-Search 换了个姿势。它不再问"agent 怎么走得更好"，而是问"agent 能不能像棋手一样边走边回溯"。它把 DEI 的"事后投票"翻了个面：评审员不等到 agent 交卷才打分，而是边解题边打分，让 agent 知道"这条思路看着不行，回上一个岔路口换条路"。这把 SWE agent 的研究重心从"事中线性 + 事后集成"推向"事中树形探索"，是这条支线从单线流水走向搜索式推理的拐点。

02研究背景

要理解 SWE-Search 的动机，得先看它出生时 SWE agent 圈子的两个心病。第一块心病来自硬件层：agent 不能回退。SWE-bench 上一个标准 agent 跑一遍的流程是：读 issue → 在仓库里搜相关文件 → 编辑代码 → 跑测试 → 提交。这条路是单向的——一旦改了 A 文件，再发现应该改 B 文件，要么硬着头皮在 A 上叠补丁，要么干脆推倒重来从头跑一遍。前者越改越糟，后者贵得肉疼。论文里有一句话很扎心："current LLM-based software agents often follow linear, sequential processes that prevent backtracking"——它们压根没有"回退"这个动作。

第二块心病来自评估层：没有"中间分"。DEI 的评审员之所以能挑对补丁，是因为它在 agent 全跑完后看 diff，这时候"对/错"已经是尘埃落定的事实。可一旦你想让 agent 边跑边回头，就立刻撞上一个新问题：凭什么判断"这条思路该不该继续"？跑到一半的轨迹既不是对的也不是错的，它是"还看不出对错"。这就要给中间状态打分——一个不像围棋有终局胜负、不像象棋有明确评估函数的诡异场景。

类比 把 SWE agent 想象成在陌生城市找餐厅的旅人。线性 agent 是"走错一条街就硬走到天黑"的愣头青——撞墙了也不回头；DEI 是"派五个人各走一条街，事后比谁先到"的委员会——但是五个人都得走到底才有结果。SWE-Search 想做的是"边走边看地图、走错就回头换条路"的聪明旅人——可问题来了：走到一半，你怎么知道这条路"看着还行"？这就是它要解决的第二个难题：给"半路状态"打分。

作者敏锐地抓住了第三块心病——它在 DEI 的局限性讨论里已经露头：DEI 把评审员从"事后"挪到"事中"听上去简单，但传统 MCTS 的"评估函数"在 SWE 场景里压根不存在。围棋有模拟到终局，象棋有手写评估函数，但"修 GitHub bug 走到一半"该怎么估分？这是 SWE-Search 真正要回答的核心难题。

03核心问题

SWE-Search 要回答的核心问题可以拆成三句：第一，能不能给 SWE agent 装上"回退"能力，让它像棋手一样在解题树上探索、换路、回溯，而不是一条道走到黑？第二，能不能用一个 LLM 当"价值函数"，给中间状态同时打出一个数字 + 一段人话解释，让搜索过程既有量化信号又有可读的反馈？第三，能不能在搜索结束时用一个"辩论式"评审员把多条候选解里最优的那条挑出来，逼近"全知评审员"的理论上限？

思考一下 如果让你设计"给修 bug 走到一半的状态打分"的函数，你会给它看什么？只看测试通过率够不够？如果只跑到一半还没跑测试呢？先猜一猜：要让一个 LLM 评判"这条思路行不行"，最少需要喂它哪几样东西？SWE-Search 的答案藏在第三节里。

04方法详解

SWE-Search 的设计哲学是"不动模型，只加搜索 + 反馈"。它不训练新模型，而是把现成的 LLM 当成三块拼图：一块负责在树上探索、一块负责给节点打分、一块负责在树叶辩论选优。下面分四步拆解。

第一步：把"修 GitHub issue"形式化成带历史的 MDP

作者先把任务套进一个带上下文与历史的 MDP，记作 $\mathcal{M}=(\mathcal{S},\mathcal{C},\mathcal{A},\mathcal{V},\mathcal{P},p_0,\rho)$。其中 $\mathcal{S}$ 是状态（当前仓库长什么样、文件上下文是什么），$\mathcal{C}$ 是上下文（仓库元信息 + issue 描述），$\mathcal{A}$ 是动作空间，$\mathcal{V}$ 是价值函数，$\mathcal{P}$ 是状态转移。这套记号的关键变化在于：价值函数 $v$ 不只看当前状态和动作，还看完整历史$\{s_i\}_{i=0}^{t-1}, \{a_i\}_{i=0}^{t-1}$——这就破了马尔可夫假设。形式化如下：

$$ \max_{\pi} V_T(\rho) = \max_{\pi} \mathbb{E}_{\tau} \left[ \sum_{t=0}^T \mathcal{R}(s_{t,\tau}, a_{t,\tau}, c) \;\middle|\; c \sim \rho;\, \pi \right] $$ (1)

翻译成人话：agent 的目标是找一个策略 $\pi$，让其在所有可能轨迹上累积奖励的期望最大。论文用这套记号给后面的搜索和价值函数留位置——它强调"非马尔可夫"，是在暗示 SWE 任务里历史很重要：你前几步搜过哪些文件、改过哪些代码，会直接决定下一步该怎么走。

第二步：Moatless-Adapted——给 agent 装上"回退"能力

这一步是 SWE-Search 的地基。作者在 moatless-tools（论文作者 Örwall 自己维护的 SWE agent 框架）之上做了三件关键改造：

  • 状态机改造成树：原本 moatless-tools 是个线性状态机——一个状态只能转下一个状态。改造后每个状态可以扩展出多个子状态，整张图变成一棵树。
  • git 提交树做"快照"：每次代码改动都 commit 一次，每个状态持有一个 commit 引用。想回退？直接 checkout 之前的 commit 即可，仓库瞬间恢复到那个时刻的样子。
  • 动作类型放开：原本 Plan 状态只能转到 Edit，作者把这条限制拆掉——Plan 可以转到任意状态（Search、View、Edit、Commit 等）。这一改是搜索能展开的关键：搜索要的就是"在任意节点都可以走任意岔路"。

动作空间本身被组织成两层：动作类型 $t \in \mathcal{T}$（Search、Plan、Edit 等）和该类型下的具体动作 $a \in \mathcal{A}_t$。形式化记作 $\mathcal{A} = \{(t, \tau, a) \mid t \in \mathcal{T}, a \in \mathcal{A}_t\}$。这套两层结构让 agent 在 Plan 节点既可以选择"搜代码"也可以选择"改代码"，而不是被钉死在一条流水线上。

第三步：Value Agent——一个既给数字又写人话的"中间评审员"

这是 SWE-Search 最有意思的设计。传统 MCTS 的评估靠模拟到终局，但 SWE 没有终局——你不可能在解题半路把所有测试跑完。作者的解法是用一个 LLM 当评估函数，但不是简单的"打 0–100 分"，而是输出一个"混合价值"：

  • 数字分数：一个 0–100 的效用估计值，用于 UCT 公式计算；
  • 自然语言解释：一段话讲清楚"为什么这个状态好/不好"——比如"文件 X 的搜索还没覆盖到 issue 提到的关键函数"。

关键是这段人话解释不是装饰品，它会作为反馈喂给父节点，让父节点下一次展开时知道"该往哪边走"。这就是 SWE-Search 标题里那个 iterative refinement（迭代精化）的真意——价值函数不只为搜索打分，它本身是个会写笔记的"复盘员"，把每条岔路的经验写成语言，留给后续探索参考。

$$ v(s_{t,\tau}, a_{t,\tau}, \{s_i\}_{i=0}^{t-1}, \{a_i\}_{i=0}^{t-1}) = \big(\, \text{Score}_{\text{LLM}}(\cdot),\; \text{Explanation}_{\text{LLM}}(\cdot) \,\big) $$ (2)

价值函数的输入也很有讲究：不只看当前状态，还要看完整轨迹（之前搜过什么、改过什么）、文件上下文（当前能看到哪些代码片段）、以及已执行的测试结果。论文后面专门做了消融实验证明这三样缺一不可，缺了哪样打分都会糊掉。

第四步：MCTS + Discriminator——把搜索变成"棋手 + 评审团"

搜索算法用的是 AlphaZero 风格的 MCTS：四步循环——选择（Selection，按 UCT 公式挑最有潜力的子节点）、扩展（Expansion，让 Action Agent 走一步新动作）、评估（Evaluation，调 Value Agent 给数字 + 解释）、回传（Backpropagation，把分数往父节点传）。但作者做了两个关键改造：

  • 反馈循环：Value Agent 给出的"人话解释"会喂给父节点，让下一次扩展时 Action Agent 知道"上次那条岔路为什么不行"——这是标题里 iterative refinement 的实操。
  • 终选走辩论：MCTS 跑完一棵树会留下若干"叶子候选补丁"，传统做法是直接取价值函数最高那个。但 SWE-Search 不信这个——它搞了个 Discriminator Agent，让多个 agent 各自为不同的候选补丁辩护、互相挑刺，最后由一个 judge agent 拍板。这一步是借鉴多智能体辩论框架（Du et al. 2023、Khan et al. 2024）的产物。

05实验结果

实验在 SWE-bench-Lite（300 道真实 GitHub issue）上跑，跨五个模型：两个闭源（GPT-4o、GPT-4o-mini）+ 三个开源（Qwen2.5-72B-Instruct、Llama-3.1-70B-Instruct、DeepSeek-Coder-V2）。基线是 Moatless-Adapted——也就是论文自己改造的那套带树结构的 moatless-tools，但不接 MCTS、只走线性流程，这样能干净地分离出"搜索"本身的贡献。下面这张表把关键数字摆在一起。

模型Moatless-AdaptedSWE-Search相对提升
GPT-4o25.7%31.0%+20.6%
GPT-4o-mini14.0%17.0%+21.4%
Qwen2.5-72B-Instruct22.3%24.7%+10.8%
Llama-3.1-70B-Instruct14.7%17.7%+20.4%
DeepSeek-Coder-V217.3%21.0%+21.4%
五模型平均18.8%22.3%+23%（相对）

几个让人眼前一亮的发现：

开源小模型逼近 GPT-4o。装上 SWE-Search 的 Qwen2.5-72B 解掉 24.7%，已经摸到了 GPT-4o 单线 25.7% 的尾巴。论文标题里"smaller, open source models to approach GPT-4o"那句不是 PR 套话——这等于在说"用搜索换参数"，是个非常有诱惑力的方向。

搜索深度越深，效果越好。作者专门画了"搜索深度 vs 准确率"的曲线：随着推理时算力（迭代次数）增加，性能持续爬升，没有饱和迹象。这是 SWE-Search 最有分量的论据——它在为 SWE agent 这条路线画了一条"测试时算力扩展曲线"，呼应了第 021 篇 Scaling Test-Time Compute 那条通用推理曲线。

价值函数的三样输入缺一不可。消融实验里，把"轨迹历史"或"文件上下文"或"测试结果"任一项去掉，价值函数的判断质量都会显著下滑。这印证了那句话：SWE 任务里历史很重要，半路状态没有历史根本没法判。

Different Models 解的题"几乎不重叠"。这是 DEI 的多样性发现在 SWE-Search 里的回声——五个模型各自解掉的题集，重叠度仍然很低。这暗示着 SWE-Search 的天花板远没到顶：理论上你把五个模型 + 搜索的并集起来，覆盖面会远超 31%。

06影响与意义

SWE-Search 给 SWE agent 这条支线换了个心智模型：从"线性解题 + 事后集成"转向"事中搜索 + 迭代反馈"。它第一次把蒙特卡洛树搜索的完整范式（选择—扩展—评估—回传）成功搬进 SWE 场景，并解决了最棘手的"中间状态评估"难题——用一个 LLM 既给数字又写人话解释。这对工业界是个直接的诱惑：与其等一个更大的模型出现，不如用现有模型多搜几步。

更深一层的贡献是它把"测试时算力扩展"这条曲线画进了 SWE agent 领域。第 021 篇 Scaling Test-Time Compute 给通用推理画过一条，SWE-Search 给 SWE agent 也画了一条，而且曲线还没到饱和——这意味着"搜索深度"是 SWE agent 的另一个可扩展维度，跟"模型规模"、"训练数据"是并列的。论文里那句"pathway to improve software agents without requiring larger models or additional training data"，是在向整个圈子喊话：别只盯着模型大小卷，搜索也是一条路。

论文也直接催生了后续延伸。同一作者团队和紧邻的工作把"事中搜索"思路继续推：Satori-SWE、SWE-Replay 等都从不同角度改造 SWE-Search——前者用更精细的过程奖励，后者干脆绕开价值函数、改用"重放关键步"来降本。多个 SWE agent 排行榜系统也开始把"搜索 + 多候选"当作标配策略，SWE-Search 成了这条路线被反复引用的起跳点。

07局限性与未来方向

SWE-Search 的代价非常直白：贵。论文自己的成本分析里写得清清楚楚——在 GPT-4o 上，Moatless-Adapted 跑一遍 SWE-bench-Lite 花 40.86 美元，SWE-Search 要花 576 美元，是基线的 14 倍。Qwen2.5-72B 上是 8.5 美元 vs 42.5 美元，5 倍。这意味着 SWE-Search 在成本敏感的工业场景里不一定划算——你多花了 14 倍的钱，才换来 5 个百分点的提升。

第二，它押注"LLM 是合格的中途评审员"。Value Agent 用一个 LLM 给半路状态打分，这个 LLM 自己有偏差、有错判——论文后面专门做了"价值函数能否分辨成功轨迹"的实验（附录 F），结论是它能分辨，但远不是完美。这意味着 MCTS 的搜索方向有时候会被价值函数带偏，搜索树会往错误的方向深扎。

第三，Discriminator Agent 的辩论机制也有局限——多个 agent 辩论最终靠一个 judge 拍板，judge 自身的偏好会决定结果。论文承认这一点，但没给彻底的解法。作者点出的未来方向包括：用更便宜的小模型当 Value Agent + 强模型做关键节点复核来降本、把搜索从"事后选优"拓到"事中规划"、以及研究"如何主动构造互补的搜索分支"。这些后来都被一一接住了——尤其是 SWE-Replay，干脆绕过了价值函数这层。

08领域演进脉络

把视野从 SWE agent 支线放大到整条大模型搜索主线，能看清楚 SWE-Search 卡在哪一级台阶上。最早的"搜索式推理"是第 027 篇 Tree of Thoughts——把 CoT 升级成树形探索，让通用 LLM 在思维树上前瞻、回溯。第 028 篇 Graph of Thoughts 进一步把树拓成图。但这些都是"在思维空间里搜索"，没有真实环境反馈。

另一条线是"测试时算力扩展"——第 021 篇 Scaling Test-Time Compute 给通用推理画了扩展曲线，第 022 篇 Let's Verify Step by Step 用过程奖励模型给推理每步打分。这两条线在 SWE-Search 这里汇合：SWE-Search 把 ToT 的"树形探索"和 PRM 的"过程评估"同时搬进 SWE 场景，再叠加上真实 git 提交树作为环境反馈——这是 SWE agent 第一次同时拥有"树形探索 + 中途评估 + 真实反馈"。

同时，SWE agent 主线也在演进：SWE-agent 立"人机接口"标杆 → Agentless 质疑"要不要 agent" → OpenHands 做成平台 → MASAI 拆成模块化 → DEI 编排多 agent。SWE-Search 正是这条支线从"线性范式"转向"搜索范式"的那个拐点——它不再问"怎么让 agent 走得更好"，而是问"agent 能不能像棋手一样边走边回头"。这与主线上"动态编排"遥相呼应：一边是编排多个 agent，一边是搜索单 agent 的多条思路，本质都是"从单线走向多线"。

09趣味延伸

这篇论文最好玩的地方，藏在它的"血缘"里。第一作者位置上挂着两个名字——Antonis Antoniades（UC Santa Barbara）和 Albert Örwall（Moatless AI），两人共享一作（论文里那个 † 标记）。后者其实就是 moatless-tools 这个开源 SWE agent 框架的作者——一个瑞典人，把项目描述成"a hobby project where I experiment with some ideas I have about how LLMs can be used to edit code"（我业余搞着玩的小项目，试试 LLM 怎么改大代码库）。SWE-Search 这篇 ICLR 2025 论文，本质上就是把 Örwall 的"业余爱好"装上了 MCTS 引擎。

第三作者 Kexun Zhang 是 DEI 的第一作者——这意味着 DEI 和 SWE-Search 是同一个人主导的"姊妹篇"。一个实习生/学生，半年内连发两篇 SWE agent 方向的代表作：DEI 走"事后投票"路线，SWE-Search 走"事中树形搜索"路线。论文里那句"a new paradigm for autonomous software development"喊得响，但回头看，这俩姊妹篇合起来才是一条完整的演进叙事。

还有一个隐藏的彩蛋在 Demo 上——SWE-Search 提供了一个 Streamlit 在线演示（streamlit.moatless.ai）。你可以亲手喂一个 GitHub issue 进去看它怎么在树上来回切换状态、走 dead-end 回头、写人话解释。对一个学术论文配套 demo 来说，这种"能让人直观看到搜索过程"的可视化相当罕见——也暗示作者很清楚：SWE-Search 的卖点不是分数，是搜索过程本身。

10个人解读与延伸思考

读完整篇，我最大的感触是 SWE-Search 把"搜索"这条通用推理路线真正焊进了 SWE agent。在此之前，SWE agent 圈子的演进基本是沿着"接口设计 / 流水线 / 多 agent 编排"这三个轴走，每个轴都在优化"agent 怎么走"，但默认 agent 是线性走的。SWE-Search 是第一个把"边走边回头"这条腿接上的工作——它不卷模型、不卷接口，卷的是解题过程的形状。从一条线变成一棵树，是 SWE agent 范式的一次形态跃迁。

放到更大的图景里看，这其实呼应了整个大模型圈子过去两年的转向——从"训练时算力扩展"走向"测试时算力扩展"。第 020 篇 o1 用 RL 训思维链、第 021 篇画测试时扩展曲线、第 027 篇 ToT 把搜索塞进推理，都是同一种转向的不同侧面。SWE-Search 把这套思路搬进 SWE，是在说：SWE agent 不该只靠训练堆参数，也可以靠搜索堆深度。这是个很有想象力的方向——尤其当开源模型参数卷不动的时候。

当然，这条路也藏着隐忧。最直接的一条：SWE-Search 的"贵"是结构性的，不是工程优化能解决的——一棵搜索树的节点数随深度指数膨胀，再聪明的剪枝也压不住。如果搜索深度本身就是 SWE agent 的扩展维度，那成本曲线会不会爆炸？又或者，当价值函数自身的判断质量是天花板时，再深的搜索也只是把错误的方向走得更远？这些疑问，恰恰是 SWE-Search 留给下一篇的悬念。

留个问题给你 如果你是 SWE agent 团队的技术负责人，预算只够跑一次推理。你会选"用 SWE-Search 在一个 70B 开源模型上多搜几步"，还是"直接调用一次 GPT-4o 走线性流程"？换句话说：当搜索深度本身就是个可扩展维度时，"小模型 + 深搜索"和"大模型 + 浅搜索"哪个更划算？SWE-Search 的数据，更支持哪一种？

SWE-Replay: Efficient Test-Time Scaling for Software Engineering Agents

SWE-Search 把 MCTS 装进 SWE agent 的代价是 14 倍成本——而这 14 倍里很多是浪费在"价值函数判错方向、往死胡同深扎"上。下篇 SWE-Replay 干脆绕开价值函数：它不从头搜树，而是从历史轨迹里挑"关键中间步"在它之前重放、在那之后分叉——不靠 LLM 估分，靠"重用过去的经验"来扩展。它能比 SWE-Search 更省、更准吗？下期见。
