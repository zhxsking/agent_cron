大模型经典论文精读系列 #062

WikiSkill: Compiling Agent Experience into Persistent Knowledge for Skill Evolution WikiSkill：给 agent 一本永不回滚的"维基"——经验被编译成知识，知识再长出技能

作者：Liyan Tang, Cyrus Rashtchian, Chun-Sung Ferng, Andrew Tomkins, Da-Cheng Juan, Tu Vu 机构：Google Research · Virginia Tech 发表：2026-08 / arXiv 2608.27454
arXiv

先看一个让人坐直身体的消融实验。同一套技能进化框架、同一个模型、同样跑满全部迭代次数，只动一个开关——把"技能提案者"阅读一本笔记的权限拿掉——平均成绩就从 63.7% 掉到 48.7%。整整 15.0 个百分点，不来自更大的模型、不来自更多的数据、也不来自更强的算法，全部来自一本笔记本身。这本笔记，论文里叫 wiki（维基）。

为什么一本笔记值 15 个点？回顾"技能"这条支线：Voyager（第 36 篇）攒出了第一个可执行技能库，Anthropic 把 SKILL.md 推成事实标准，OpenSkill（第 59 篇）打通了开放世界的知识来源，SkillAlchemy（第 60 篇）给搜来的知识加了证据关卡，上一篇 MUSE-Autoskill（第 61 篇）更是把"技能的一生"从创建到传承打理得明明白白。但这条线上的几乎所有框架都有一个共同的盲区：进化过程本身会产生海量洞察——"这个改法为什么被拒""这个错误上一轮不是已经见过了吗"——它们去哪了？答案是：散落在优化历史的故纸堆里，下一轮从头考古，再踩一遍坑。就像一家公司只保存"最终发布的操作手册"，却把所有复盘会议的纪要都扔进了碎纸机。

这篇来自 Google Research 与 Virginia Tech 的论文，回应了一个看似朴素的问题：能不能给 agent 配一本只增不减的维基，让经验沉淀成知识、让知识长出技能？他们的答案是一个三层架构加一个四角色循环，核心设计哲学浓缩成一句话就是——技能可以回滚，知识永不回滚。就凭这一点，9B 小模型"带着技能"在测试中打败了 27B 大模型"裸奔"。

一句话总结 把 agent 的执行经验持续"编译"进一个永不回滚的持久知识库（wiki），让每一轮技能更新都站在沉淀知识的肩膀上——技能可回滚、知识永不丢。凭这个设计，WikiSkill 在 5 个基准、5 个模型上全面超越现有技能进化方法（EvoSkill、SkillOpt、Trace2Skill），甚至让 9B 小模型带着技能胜过 27B 大模型裸奔，而消融实验证明：那本"维基"本身就是 15 个百分点。

01领域定位

"技能"这条支线走到 2026 年，已经把"技能从哪来"（Voyager 的轨迹总结、OpenSkill 的开放世界经验蒸馏、SkillAlchemy 的证据准入）和"技能怎么活"（MUSE-Autoskill 的全生命周期管理）都回答了个遍。但有一个更底层的问题始终没人正面回答：进化过程中学到的东西，存在哪里？

现有框架的答案五花八门但都有共同缺陷：EvoSkill 把历次提案和评估结果累积成一份平铺的反馈历史；Trace2Skill 从执行轨迹里提炼教训后直接焊进技能文件；SkillOpt 靠被拒编辑的反馈和逐轮元指导来传递信息。它们的共同点是——知识没有自己独立的表示。洞察要么锁在技能文件里跟着技能一起被回滚，要么散落在优化日志里没人再看第二眼。用一个比喻：图书馆里只有"成书"（技能），既没有"原始档案库"（raw traces 的系统利用），更没有"百科全书"（沉淀的知识层）。

WikiSkill 补的正是这块拼图，而且来头有迹可循——论文开篇就致意了 Karpathy 在 2026 年 4 月那篇爆火的 LLM Wiki gist（我们在趣味延伸里细讲这段故事）。Karpathy 倡导"把经验编译成持久、可复利的知识"，WikiSkill 把这个理念从个人知识管理搬进了 agent 实验室，第一次让持久知识库成为技能进化流水线中的一等公民。它也是这条支线上第一篇正面回答"进化产出的知识如何组织与复用"的工作。

02研究背景

先把舞台搭好。所谓"技能进化"，如今已有一套相当标准的工作流：让 agent 在训练任务上跑一遍（rollout），分析成功与失败的轨迹，据此提出技能的新建或修改，再在验证集上把关——有效就保留，无效就回滚。三大 SOTA 基线各显神通：EvoSkill 把技能进化当作在候选程序前沿上的搜索，维护一份平铺的提案历史；Trace2Skill 用并行分析员拆解轨迹再层级合并补丁；SkillOpt 靠被拒编辑的反馈和逐轮元指导迭代。听起来都很合理，直到你问一个扎心的问题：

第 3 轮迭代里，提案者发现"模型总是把物品拿起来又放回原地，陷入死循环"，于是提议了一条规则，但验证集表现没涨，提案被拒。第 5 轮迭代里，同一个死循环又出现了——而此时，第 3 轮的根因分析、被拒提案的完整 diff、以及"这条规则为什么没用"的教训，分别躺在滚动覆盖的优化日志和被回滚的技能目录里。提案者两手空空，只能从零开始重新踩坑，甚至再提一次一模一样注定失败的方案。

类比 这就像维护一份代码：一种做法是每次改代码前，先从 git blame 里一行行考古出历史决策的蛛丝马迹；另一种做法是手边始终摊着一份持续更新的设计文档，为什么这么改、哪条路试过不行、下一步打算怎么办，全都白纸黑字写着。前者靠考古，后者靠积累。现有技能进化框架全是"考古派"，WikiSkill 要让 agent 当"积累派"。

更深一层的问题是"回滚"的副作用。验证门控为了防止技能越改越糟，把不达标的修改连同其背后的洞察一起扔掉——洗澡水和孩子一起倒掉了。一次失败的提案里往往埋着对错误模式的深刻理解，恰恰是最该沉淀的知识。另外，只存成功案例的"高光集锦"式记忆也不行：失败信号才是教 agent 最多的东西。这就把需求逼到了一个很具体的位置：需要一个独立于技能、独立于日志、只增不减、还能被后续每一轮迭代直接引用的知识载体。

03核心问题

把上面的痛点浓缩成一句话：如何把 agent 在交互中积累的执行经验，系统性地沉淀为可复用、可迁移的持久知识，从而支撑长期、跨迭代的技能进化？

这个问题可以拆成三小问：第一，沉淀什么——原始轨迹、提炼知识、可执行技能，哪些该分开存放、哪些该合并归一？第二，怎么组织——知识以什么结构存放，才能既装得下失败教训，又让后续提案者查得快、用得上？第三，怎么用——知识层和技能层谁在台前、谁在幕后，各自的访问权限怎么划？这第三问尤其微妙，因为它暗藏一个反直觉的设计决策。

思考一下 假设进化到第 4 轮，你手里有一本记录了三轮教训的维基。现在有两个人选可以读它：A. 正在跑任务、直接决定成败的推理 agent；B. 负责改写技能文件的提案 agent。直觉上，"给干活的人看笔记"似乎更有用——你会把维基的阅读权限给谁？还是干脆两个人都给？先记住你的答案，第 05 节的消融实验会给出一个让人意外的结论。

04方法详解

WikiSkill 的全貌可以概括为"三层架构、四个角色、一条铁律"。铁律你已经知道了：技能可回滚，wiki 永不回滚。下面从架构讲到循环。

第一步：把工作区切成三层——经验、知识、技能各回各家

WikiSkill 给 agent 的工作区划了三个互不越界的目录，对应三种性质完全不同的东西：

  • raw/（原始层）：存放每轮迭代产生的完整执行轨迹——推理过程、工具调用、调用结果、最终答案，一字不改。不可变、只增不减，相当于图书馆的原始档案库。
  • wiki/（维基层）：整个框架的心脏。里面是一本持续维护的"维基"：patterns/ 目录下是一个个模式页（pattern page），每页记录一种具体的失败模式或成功策略，附上可执行的解法；logs.md 是演化日志；skill-impact.md 是技能影响账本，程序化记录每次提案的 diff、验证分数和接受与否；index.md 是总目录。这一层跨迭代持久、跨迭代复利。
  • skills/（技能层）：真正被推理 agent 在运行时加载的技能集。每个技能目录两个文件：SKILL.md 是技能正文（指令、适用条件），PURPOSE.md 则是一张"出生证明"——回链到催生它的维基模式页，说明我为什么存在。

注意一个精妙的对称性：技能层是可逆的（验证不过就回滚），维基层是只进不退的（无论验证结果如何，新知识照单全收）。失败也留在账上——因为"知道哪条路不通"本身就是知识。

第二步：四个角色跑一轮循环

每一轮迭代，四个角色接力完成一次"经验 → 知识 → 技能"的转化：

  1. 推理 agent（Inference Agent）：带着当前技能集在训练任务上跑轨迹。技能全文直接注入系统提示词（沿用先前工作的全量注入设定，排除检索失败等干扰变量）。铁面无私的一条：训练 rollout 期间禁止阅读维基——为什么，第五节揭晓。
  2. 维基维护员（Wiki Maintainer）：拿到采样后的轨迹子集（每轮最多 8 条：至多 5 条失败的做根因分析 + 至多 3 条成功的做策略提取，单条日志截断在 15,000 字符以防撑爆上下文），在现有维基上做增量补丁式编辑——新建模式页、给旧模式页补充新证据、修订解法，同时更新目录、追加演化日志。
  3. 技能提案者（Skill Proposer）：一个多轮 ReAct 式的自主 agent。初始只拿到维基目录、技能影响账本和一份简洁的任务成败摘要，然后按需用 read_file 工具去深挖具体的模式页和原始轨迹，自己决定看什么、看多深。产出是一条原子提案：一次只新建一个技能，或只给一个已有技能打补丁。
  4. 门控与回滚（Gating and Rollback）：提案应用后得到候选技能集，在验证集上跑分。只有严格超过历史最佳才接受；否则回滚技能。但无论接受与否，这条提案的 diff、验证分数和结论都会被程序化地记进维基的影响账本——给未来的提案者留一份"此路不通"或"此路可通"的官方档案。
$$S_k \leftarrow \begin{cases}S'_k & \text{if } \mathcal{R}(\mathcal{T}_{\text{val},k}) > \mathcal{R}_{\text{best}}\\[2pt] S_{k-1} & \text{otherwise}\end{cases}$$ (1)

其中 $S'_k = \text{Apply}(S_{k-1}, P_k)$ 是应用提案 $P_k$ 后的候选技能集，$\mathcal{R}(\mathcal{T}_{\text{val},k})$ 是验证集得分，$\mathcal{R}_{\text{best}}$ 是历史最佳。接受则刷新 $\mathcal{R}_{\text{best}}$；拒绝则回滚到 $S_{k-1}$。但维基 $W_k$ 不出现在这个公式里——因为它从不参与回滚。每轮收尾，外层循环还会把提案结果写回维基，完成状态转移 $W_{k-1} \to W_k$。整个循环最多跑 8 轮；若验证集拿到满分则提前终止。

05实验结果

实验的铺面相当扎实：5 个基准覆盖五种能力——数学推理（LiveMath）、网络搜索（SealQA）、表格操作（SpreadSheet）、长文档问答（OfficeQA）、具身交互任务（ALFWorld）；5 个模型横跨开源与闭源——Qwen-3.5-4B/9B、Qwen-3.6-27B、Gemma-4-31B、Gemini-3.5-Flash；对手是三大 SOTA 基线加"无技能"对照。每个设置独立跑 3 次完整进化取平均，再用 1000 次配对 bootstrap 检验显著性（p<0.05）。

发现一：全面、且稳定地赢

五个模型上，WikiSkill 的平均分全部第一。比每个模型身后的最强竞品还分别高出 3.3、5.1、10.0、5.8、12.0 个点。更难得的是"稳"：对手们的发挥像坐过山车——EvoSkill 在 Qwen-9B 的 LiveMath 上大杀四方（28.2% → 58.1%），到 Gemma-4-31B 上同一基准却不升反降（33.9% → 29.8%）；SkillOpt 在 Gemini Flash 的 SealQA 上也倒退（29.4% → 28.2%）。WikiSkill 在几乎所有模型-基准组合上都是正增益。单点爆发靠运气，处处开花靠的是"每轮都站在知识肩膀上"的结构优势。

发现二：技能进化与模型缩放是"互补品"

一个漂亮的规律浮出水面：在 Qwen 家族内，WikiSkill 的平均增益随模型规模递增——4B +12.3、9B +17.5、27B +23.9 个点。在 SpreadSheet 上最夸张，27B 模型直接涨了 40.9 个点。越强的模型，从技能进化中获益越大——这不是一项只拯救弱模型的技术，而是与模型缩放并肩的另一条增长曲线。反过来也成立：小模型带技能可以越级挑战——Qwen-3.5-9B + WikiSkill 拿到 47.4%，把无技能的 Qwen-3.6-27B（39.4%）斩落马下；连 4B + 技能（38.5%）都几乎追平 27B 裸奔。如果你关心部署成本，这就是那句老话的新版本：与其买更大的脑子，不如给它一本更好的笔记本。

发现三：技能可以跨模型"移植"，而且别人家的可能更好

跨模型迁移实验的结果有两层意外。第一层：WikiSkill 进化出的技能跨模型、跨家族迁移都有效。第二层更反直觉：别的模型进化出的技能，常常比自己进化的还好用。

看第二行：4B 小模型进化出的数学技能，给 31B 的 Gemma 用，从 33.9% 拉到 73.1%——比自己进化的 56.7% 高出 16 个点。小模型进化的技能反而更牛，为什么？论文的解释是：小模型自身能力有限，被迫把每一步都写成明确、通用、不依赖模型内功的详细程序——而恰恰是这种"傻瓜式"的显式知识，放到大模型身上如虎添翼。这引出一个重要洞察：发现好知识和执行好知识是两种可以分离的能力。

但迁移也有翻车现场（第四行）：4B 进化的 SpreadSheet 技能把 Gemini Flash 从 50.5% 拖到 18.1%。错误分析找到两个原因：小模型的技能里塞满了"单行 Python 命令、字符串转换规则"这类低级 workaround，它们帮小模型避免执行失败，却捆住了强模型的手脚，让它不敢写端到端的完整脚本；碎片化的诊断流程还引入冗余工具调用，把强模型的交互预算提前耗尽。可见技能分两种：通用程序性知识（越迁移越香）和模型特异的补丁（一迁移就毒）。怎么让 wiki 多沉淀前者、少沉淀后者，是这条路线下一个值得挖的富矿。

消融：那本维基值 15 个点，而且不能给错人

回到开篇的悬念。消融实验在 Gemini-3.5-Flash 上做了 2×2 组合：推理 agent 和提案者各自有没有维基阅读权。结论有两个：

第一，维基本身就是增益的来源：提案者失去维基访问权（同时移除维护员，知识不再跨轮积累）后，均值从 63.7% 掉到 48.7%——正是开篇那 15 个点。没有沉淀下来的知识，提案者在疑难杂症面前就是无头苍蝇。

第二，回答第 03 节的思考题：给推理 agent 开维基阅读权，是帮倒忙。双开配置 60.9%，比默认的 63.7% 低了 2.8 个点，LiveMath 上更是从 72.6% 掉到 64.8%。论文的假设很精彩：推理 agent 如果能直接读维基，一些任务知识会"走捷径"直接从维基进入轨迹，轨迹本身反而变得没有信息量了——你观察不到 agent 在没有维基帮助时的真实挣扎，也就分析不出它到底哪里不会。这就像让学生开卷考试，你再也看不出他哪些知识点没掌握。知识的正确用法是"喂给教练"，而不是"塞给选手"。

案例解剖：一条技能的三轮进化史

ALFWorld（具身家务任务）上 Qwen-3.6-27B 的案例把整个机制讲活了。一个反复出现的错误是：agent 拿起物品、查看、放下、又挪走，陷入"拿起-放下"死循环。

注意这条时间线里的因果链：第 0 轮提案失败，但失败本身被维基留了档（提案 diff + 拒绝原因记入 skill-impact.md）；第 1 轮的提案者读过这份档案，知道"泛泛的目标导向规则没用"，于是提出了一条具体可执行的规则——"绝不把物品放回原位"——一击即中；此后新的死循环变体出现，维基同步累积新证据，到第 4 轮技能增补"每种操作对同一物品只做一次"，继续通过验证。技能在成长，而支撑它成长的每一步证据都查得到出处——PURPOSE.md 里写得明明白白。这已经不是"生成技能"，而是"栽培技能"。

06影响与意义

第一，它给"技能进化"补上了缺失的知识层，把此前隐式的问题显式化了：EvoSkill 们的优化历史是"副产品"，WikiSkill 的维基是"主资产"。论文的消融把这一点锤死了——15 个点的差距不是来自更聪明的提案者，而是来自把学过的东西留下来这件朴素的事。

第二，它分离了两种能力：发现知识（skill discovery）与执行知识（skill execution）。跨模型迁移实验表明，这两者可以由不同的模型分担——弱模型进化出的显式知识，强模型执行起来如虎添翼。工程含义直接写在脸上：一次进化，处处分发。与其给每个部署的模型各跑一条进化流水线，不如让"最会写技能的模型"维护一本公共维基，全团队共享。

第三，它把"部署后自提升"这条 2026 年的主线又向前推了一步：不碰模型权重，靠外部资产持续变强。与微软的 EvoLib（演进库）、Self-Harness（自改挽具）以及 Google 自家的 ReasoningBank（推理记忆）一起，WikiSkill 代表了一个正在合流的方向——agent 的经验不再是一次性消费品，而是可以复利的资产。参数缩放买的是"天赋"，测试时算力买的是"思考时间"，而持久知识库攒的是"资历"——三条曲线，可以叠加。

07局限性与未来方向

论文的 Limitations 一节写得相当坦诚，四条硬伤都指向未来的活儿：

  • 全量注入，未测检索：为隔离技能质量这一变量，所有技能全文塞进提示词。技能一多，检索与触发的开销和失败率就成了新问题——而这恰恰是真实系统绕不开的。
  • 严格门控的副作用：只有"立即涨分"的提案才被接受，那些"本轮持平、下轮发力"的中性提案会被一刀切掉。进化因此偏保守，可能错过需要多步铺垫的复杂改进。
  • 维基只增不减：论文自己承认，随着进化轮次拉长，模式页、日志、diff 会无限累积，缺一个自动修剪机制。人类维基靠编辑吵架来去重删减，agent 的维基还没长出这个器官。
  • 没有超长程任务：基准里最长的任务也就几十步交互。真正的软件工程任务动辄数百步、数小时，如何在单次超长 rollout 内在线更新知识，还是空白。

另外从迁移实验也能读出一个未解难题：wiki 会同时沉淀"通用程序"和"模型特异补丁"，前者是蜜、后者是毒，但目前的机制并不区分它们。为知识打上"通用性"标签，或许会成为这条路线的下一个关键发明。

08领域演进脉络

把镜头拉远，这个领域对"知识"的处理方式经历了几次搬家：预训练时代，知识搬进参数，一次训练终身受用，但更新昂贵且不透明；对齐与应用时代，指令跟随让参数里的知识能被"唤醒"，可新知识还是进不去；推理范式时代（第 20–23 篇），思维链把"思考过程"临时外化，用完即弃；agent 时代（第 35 篇起），工具与环境给了模型"动手"的能力；技能支线（第 36、59–61 篇），程序性知识终于搬进了文件系统——可复用、可审计、可分发。

WikiSkill 站在这个脉络的最新一格：在"技能"之外，又给陈述性知识与经验教训安了一个永久的家。至此，agent 的"外置知识栈"凑齐了三层——一次性思考（思维链）、程序性知识（技能）、复利型经验（维基）。它与 ReasoningBank 的"记忆路线"、EvoLib 的"库路线"正在从三个方向逼近同一件事：让经验不再蒸发。下一次范式的候选词，也许就是"经验复利"。

09趣味延伸

这篇论文的灵感源头值得单独讲一段。2026 年 4 月，Andrej Karpathy——就是那个Transformer 时代反复出现在我们系列里的 Karpathy——在 GitHub 上发了一份只有几页的 gist，标题就叫 LLM Wiki。核心主张一句话：别让 LLM 每次都从原始资料里重新发现知识，先让它把知识整理进一套持续维护的维基。他把个人知识库切成三层：raw 层放原始资料（PDF、笔记、书签，只读不改）；wiki 层是 LLM 亲手写的 markdown（摘要、概念页、交叉引用）；再加一份 schema 教 LLM 怎么维护这套维基。这份 gist 迅速拿下五千多星，"第二大脑"社区为之沸腾，因为分工设计实在优雅——你读，LLM 写（You read it; the LLM writes it）。

WikiSkill 的作者们读到这份 gist 后问了一个漂亮的问题：既然个人知识可以这么"编译"，agent 的经验为什么不行？于是 raw 层变成了执行轨迹，wiki 层变成了模式页，schema 变成了外层循环的调度代码，而"你"变成了跑任务的推理 agent。一篇顶会级别的系统论文，骨架竟来自一份工程师博客式的 gist——这大概是"研究品味"最好的注脚之一。

另一个耐人寻味的细节在作者名单里。本文的六位作者来自 Google Research 和 Virginia Tech，而被 WikiSkill 明确击败的基线之一 EvoSkill，正出自本文资深作者 Tu Vu 所在团队的先前工作——连 EvoSkill 用的 OfficeQA 基准和任务划分都被 WikiSkill 原封不动继承了下来。用自己的新框架打败自己的旧框架，这在大模型史上从来都是好故事的固定开头。顺带一提，第一作者 Liyan Tang 也是 agent 评测领域的老熟人，此前以 InfiAgent、DABStep 等工作为人所知。

10个人解读与延伸思考

读完这篇论文，我最强烈的感受是：它其实在讲一个经济学故事。参数缩放的边际成本越来越高——下一代大模型的训练费用以亿计；测试时算力按 token 收费，每一分"多想一会儿"都是真金白银。而维基式知识积累的边际成本几乎为零：反正轨迹已经跑出来了，多写几页 markdown 而已。15 个点买一叠 markdown 文件，这可能是 2026 年性价比最高的一笔交易。"经验复利"完全有资格成为继参数缩放、测试时算力之后的第三条增长曲线——而且是一条几乎免费、可以和前两条叠加的曲线。

对每天维护 prompt 库、技能库、SOP 文档的从业者，这篇论文还有一个扎心的镜像问题：你维护的那些库，是不是也只有"成书"没有"维基"？每次改 prompt 靠 git blame 考古、每次踩过的坑在下一个项目里重新踩一遍——我们人类自己，何尝不是那个没有持久知识库的 agent。

留个问题给你 维基只增不减，短期是复利，长期是膨胀——模式页越攒越多、影响账本越记越长，提案者的上下文窗口总有装不下的一天。人类维基靠"编辑互殴"来去重和删减条目，agent 的维基该靠什么？一个会"遗忘"的维基和一个"全记"的维基，哪个会让技能进化走得更快？如果让你设计一个维基修剪 agent，它的验收标准应该长什么样？
