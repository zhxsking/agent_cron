大模型经典论文精读系列 #051

Diversity Empowers Intelligence: Integrating Expertise of Software Engineering Agents DEI：多样即智慧——不同 SWE agent 解的题竟几乎不重叠，组队后 34.3% 反杀最强单 agent，ICLR 2025 的多样性集成范式

作者：Kexun Zhang, Weiran Yao, Zuxin Liu, Yihao Feng, Zhiwei Liu, Rithesh Murthy, Tian Lan, Lei Li, Renze Lou, Jiacheng Xu, Bo Pang, Yingbo Zhou, Shelby Heinecke, Silvio Savarese, Huan Wang, Caiming Xiong 机构：Salesforce AI Research / Carnegie Mellon University 发表：2024-08 / arXiv（ICLR 2025 录用）
arXiv GitHub Project

想象一家软件公司里有四位顶尖工程师，每人都能独立修好约 27% 的 GitHub bug。你也许会想：选最强的那位、把奖金全发给他就行。可当你把四人各自修好的 bug 清单摊在桌上一比，会看到一个反直觉的画面——他们修好的题，几乎不重叠。

换句话说，这不是"谁更强"的问题，而是"谁擅长哪一类题"。Aider 擅长改 diff、Moatless 擅长搜代码、Agentless 不让模型自己决策、OpenDevin 先复现 bug 再动手——四套手艺，四拨人马。本文要回答的问题是：能不能别再卷"单一最强 agent"，转而把这些各有所长的 agent 组成一个"评审委员会"，让它们合力？

一句话总结 不同 SWE agent 各有所长、解的题几乎不重叠；DEI 用一个挂在所有 agent 之上的"元模块 + 重排序"委员会，把开源组合的解决率从 27.3% 拉到 34.3%（+25%），最佳组合冲到 55%，登顶 SWE-Bench Lite。

01领域定位

把镜头拉远，这是大模型"软件工程 agent"这条支线连续第五篇。前四篇像在回答同一个问题的不同侧面：第 047 篇 SWE-agent 说"给 agent 一套对的人机接口比堆十个 agent 更管用"；第 048 篇 Agentless 反手一问"那连 agent 都不要行不行"；第 049 篇 OpenHands 把 agent 做成开放平台；第 050 篇 MASAI 把一个 agent 拆成五个子智能体分工。四篇都默认一个前提：要造一个"最强单体"。

DEI 换了个姿势。它不再问"谁是冠军"，而是问"组一支全明星队会怎样"。它承接了前面所有 agent 的成果——把 Aider、Moatless、Agentless、OpenDevin 当成现成的"队员"，自己只做一件事：当教练，挑哪份补丁该上场。这一步把 SWE agent 的研究重心从"单体设计"推向"集成与编排"，是这条支线从单打走向团战的转折点。

02研究背景

要理解 DEI 的动机，得先看它出生时 SWE agent 圈子的"内卷"长什么样。2024 年中，SWE-bench Lite 是公认主考场——300 道从真实 GitHub 仓库抠出来的 issue，模型得读懂 issue、在庞大代码库里找到相关文件、生成能通过隐藏单元测试的补丁。榜单上挤着一票开源 agent，成绩都在 27% 上下挤成一团：SWE-agent、Aider、Moatless Tools、Agentless、OpenDevin……彼此咬得很紧，谁也甩不开谁。

圈子默认的叙事是"刷分"：谁能在 300 道题上多对一两道，谁就是新王者。但作者们盯着榜单时发现了一件被所有人忽略的事——这些分数相近的 agent，对的具体题目几乎完全不一样。Agentless 会的那批，OpenDevin 未必会；Moatless 拿下的，Aider 可能压根没碰过。这背后是各自的设计哲学差异：OpenDevin 会先把 bug 复现一遍拿反馈，而 Agentless 干脆不让模型自主决策、走"定位→修复→验证"的固定流水线；Aider 用简单的 diff 格式提交，Moatless 则靠代码搜索 + 检索双管齐下。不同的工具、不同的工作流、不同的提示词，造就了不同的"拿手好戏"。

类比 把 SWE-bench Lite 想象成一家综合医院的 300 个病例。每个 agent 像一个专科医生：Agentless 是流程严谨的"全科流水线医生"，OpenDevin 是爱先做检查再下诊断的"实验派医生"，Moatless 是会翻病历索引的"检索派医生"，Aider 是手快利落的"手术派医生"。他们各自能治好的病人加起来，远超任何一个人单独看的病号数——但医院一直在评"谁是最佳主治医师"，从没人想过开个联合会诊。

作者算了一笔账：一组平均解决率只有 26.6% 的 agent，如果存在一个"全知评审员"能永远从候选补丁里挑出正确的那份，合力能解掉 54.3% 的题——几乎是单兵最优的两倍。这个数字像一根刺：它说明真正的瓶颈不在"哪个 agent 最强"，而在"我们根本没把这些各有所长的 agent 用在一起"。问题只剩一个：上哪儿去找这个"全知评审员"？

03核心问题

DEI 要回答的核心问题只有一句话：在没有"全知评审员"的情况下，能否用一个可学习的元策略，从一堆各有所长 agent 产出的候选补丁里，自动挑出最可能正确的那一份——让组合的表现逼近"理论上限"，并超过任何单个 agent。

思考一下 如果四份补丁摆在评审员面前，他凭什么判断哪份对？他既看不到隐藏的单元测试，也跑不动整套测试套件。先猜猜：一个强大的 LLM，只读 issue 描述和补丁前后的代码，能不能当好这个评审员？差多远？

04方法详解

DEI 的设计哲学是"不动队员，只加教练"。它把自己定位成一个挂在任何现有 agent 框架之上的元模块——你不改 Aider、不改 OpenDevin，只把它们产生的候选补丁收上来，交给 DEI 的评审委员会打分、重排、选最优。下面分三步拆解。

第一步：把 SWE agent 问题形式化成 CMDP

作者先把"修 GitHub issue"这件事，套进一个带上下文的马尔可夫决策过程（Contextual MDP）里，记作 $\mathcal{M}=(\mathcal{S},\mathcal{C},\mathcal{A},\mathcal{R},\mathcal{P},p_0,\rho)$。$\mathcal{S}$ 是状态（文件当前长什么样），$\mathcal{C}$ 是上下文（仓库信息 + issue 描述），$\mathcal{A}$ 是动作（搜索、编辑这类工具调用），$\mathcal{R}$ 是奖励（补丁对不对）。这套记号不是炫技，而是为了给后面的"元策略"留位置：每个 agent 是一条策略 $\pi_i$，DEI 要学的是一个站在它们之上的元策略 $\pi^*$。

$$\hat{a} \;=\; \arg\max_{a_i \in \mathcal{A}_{\text{cand}}(c)} \; \text{Score}_{\pi^*}\!\big(a_i,\; c\big)$$ (1)

翻译成人话：给定一个 issue 的上下文 $c$，多个 agent 各自交上一份候选补丁 $a_i$，元策略 $\pi^*$ 给每份打分，分数最高的 $\hat{a}$ 就是 DEI 的最终答案。整套框架要解决的就是"怎么把这个 $\text{Score}$ 学好"。

第二步：DEI 框架——一个"评审委员会"元模块

DEI 的元策略不靠训练大模型，而是用一个强大的 LLM 当评审员，对每份候选补丁走"输入构造 → 解释生成 → 打分重排"的多阶段流水线。它像在 agent 团队之上加了一层"评审委员会"：委员们不写代码，只读代码、挑毛病、投票。下图是这套元模块的整体结构。

第三步：DeiBase——一个简单却有效的实现

"元策略"听上去很玄，作者交出的第一版实现却朴素得可爱，取名 DeiBase。它分两个关键动作：先构造评审输入，再打分重排。

构造输入时，DeiBase 给每份补丁喂四样东西：① issue 的原始描述；② agent 自己定位出来的相关代码片段（说明它为什么改这里）；③ 改之前的代码；④ 改之后的代码。两个设计选择藏在里面：整个仓库太大塞不进上下文，所以只给 agent 认为相关的片段；前后代码都给，是为了让评审员像看 diff 一样直接对照"改了啥"。接着，评审员（实现里用 GPT-4o）会先为每份补丁生成一段"解释"，再给它打一个 1–10 的分，分数最高的候选就是 DEI 的提交。下图是这条流水线。

作者还设计了三档不同的"委员组合"来验证思路：DeiBase-1（仅榜单 top-2 的两个 agent，看小组合行不行）、DeiBase-2（五个高性能闭源 agent，看强强联手的上限）、DeiBase-Open（Aider + Moatless + Agentless + OpenDevin 四个全开源 agent，保证别人能复现整条流水线）。最关键的是最后这档——它用全开源的"平民阵容"去挑战榜单上那些闭源大块头。

05实验结果

实验在 SWE-Bench Lite 上跑，回答两个研究问题：agent 们到底有多"多样"？DEI 这套评审委员会到底能帮多少？两个答案都相当刺激。

多样性惊人。一组平均解决率只有 26.6% 的 agent，"全知评审员"上限（oracle）能解 54.3%——也就是说，把队员们的拿手题并集起来，覆盖面几乎翻倍。这直接坐实了"不同 agent 解的题几乎不重叠"的猜想，也说明集成路线的"天花板"远没到顶。

DeiBase 真的能逼近这个天花板。全开源的 DeiBase-Open 把组合解决率从单兵最优的 27.3% 拉到 34.3%，相对提升 25%，反超了榜单上一票闭源方案。最猛的一组直接干到 55%，登顶 SWE-Bench Lite 榜首。下面这张表把关键数字摆在一起。

配置单兵最优组合（DEI）相对提升
DeiBase-Open（4 个开源 agent）27.3%34.3%+25%
最佳组合（登顶 SWE-Bench Lite）—55.0%榜首
Oracle 上限（全知评审员）26.6% 均值54.3%理论上限

消融实验里还有几个有意思的发现：去掉"解释生成"这一步，打分质量会掉，说明让评审员先"说人话"再打分比直接打分更稳；只用两个 top agent 的 DeiBase-1 也能反超单兵最优，证明集成增益主要来自"多样性"而非"堆人数"；而且评审员用更强的 LLM，增益越明显——这等于在暗示：LLM 确实是个不错的代码评审员，模型越强，教练越称职。

06影响与意义

DEI 给 SWE agent 这条支线换了个心智模型：从"刷单一最强"转向"组合最优"。它第一次系统量化了 agent 之间的"解题多样性"，并给出一个开箱即用的集成范式——不重新造 agent，只加一层评审委员会。这对工业界尤其友好：企业手里往往已经攒了好几个内部 agent，与其推翻重来，不如用 DEI 思路把它们编成一支队伍。

更深一层的贡献是它实证了"LLM 是合格的代码评审员"。DeiBase 没训练任何模型，纯靠 GPT-4o 读补丁打分，就把组合解决率推到 34.3%、逼近 54.3% 的理论上限。这等于给后续工作指了路：与其苦练更强的"写代码 agent"，不如先把"读代码、判代码"的评审能力做大做强——因为评审员的天花板，就是整支队伍的天花板。

论文也直接催生了后续延伸。同一作者 Kexun Zhang 紧接着推出了 SWE-Search，把"委员会投票"升级成"蒙特卡洛树搜索"——把集成范式从"事后选优"推进到"事中探索"。多个 SWE agent 排行榜系统也开始把"多样性集成"当作标配策略，DEI 成了这条路线被反复引用的起跳点。

07局限性与未来方向

DEI 不是没代价。最直白的一条：贵。要让一组 agent 各跑一遍，再让一个强力 LLM 把所有候选补丁都读一遍打分，算力开销是单 agent 的好几倍——54.3% 的 oracle 上限，是用"跑 N 个 agent"换来的。在成本敏感的工业场景里，这套"全明星队"未必划算。

第二，它押注"现有 agent 之间真的够多样"。如果未来某天某个 agent 全面碾压同行、解题集合高度重叠，DEI 的增益就会塌掉——它的天花板是队友间的互补性，而不是无穷大。第三，评审员离"全知"还有距离：34.3% vs 54.3% 的 oracle，中间差了整整 20 个百分点，说明 DeiBase 那个朴素的 GPT-4o 评审员远没把多样性红利吃满，重排序策略还有大量改进空间。

作者自己点出的未来方向包括：把评审员从"事后打分"升级成"事中参与"（这也是 SWE-Search 走的路）、用更便宜的"小模型评审员 + 少量强模型复核"来降本、以及研究"怎样主动构造互补的 agent 组合"而不是被动挑现成的。这些后来都被一一接住了。

08领域演进脉络

把视野从 SWE agent 支线放大到整条大模型 agent 主线，能看清楚 DEI 卡在哪一级台阶上。最早的 agent 是"单兵循环"：ReAct 把"思考-行动"织成循环（第 035 篇），Reflexion 把失败写进语言记忆重试（第 031 篇）。接着是"多智能体协作"：MetaGPT、AutoGen、ChatDev（第 038–041 篇）让一群 agent 像团队一样分工。再到"动态编排"：MacNet、puppeteer、MAS-Orchestra（第 043–045 篇）把协作拓扑从静态图推向会学习的编排。

而 SWE agent 这条支线自成一体：SWE-agent 立"人机接口"标杆 → Agentless 质疑"要不要 agent" → OpenHands 做成平台 → MASAI 拆成模块化子智能体。DEI 正是这条支线从"单体设计"转向"集成编排"的那个拐点——它不再关心"怎么造一个更好的 agent"，而是关心"怎么把已有的好 agent 用到极致"。这与主线上"动态编排"的演进遥相呼应：一边是编排多智能体，一边是集成多 agent，本质都是"从单打走向团战"。

09趣味延伸

这篇论文最好玩的彩蛋，藏在缩写里。DEI 全称是 Diversity Empowered Intelligence，但这三个字母恰好撞上了企业界近年最热门的另一个缩写——DEI（Diversity, Equity & Inclusion，多元、公平与包容）。论文里那句题词"A garden's beauty never lies in one flower. Diversity in all its forms is the path to greatness"（一座花园的美从不只在一朵花上，多样性通向伟大），读起来简直像在企业 DEI 培训会上念的口号。

更逗的是系统图里真的有一个盒子，老老实实标着 "DEI committee review"（DEI 委员会评审）。ICLR 2025 的评审忍不住在 meta review 里吐槽了一句："Fun acronym, and having a box labeled 'DEI committee review' in your system diagram is hilarious :)"——好玩的缩写，而且系统图里放一个写着"DEI 委员会评审"的盒子，太搞笑了。能在严肃的顶会评审里被夸"好笑"，大概也是这篇论文独一份的待遇。

还有一条暗线：第一作者 Kexun Zhang 来自卡内基梅隆，在 Salesforce AI Research 实习期间做出 DEI，紧接着就和别人合作推出了 SWE-Search——把这篇"委员会投票"的思路升级成"树形探索"。一个实习生，半年内连发两篇 SWE agent 方向的代表作，这条研究脉络本身就挺"多样性"的。

10个人解读与延伸思考

读完整篇，我最大的感触是 DEI 用一种"反内卷"的姿态点破了一个行业执念。过去两年，所有人都在拼"单一最强 agent"——谁在 SWE-bench 多对一道题谁就是王者。可 DEI 的数据冷冰冰地指出：你卷出来的"最强"，也只覆盖了 27% 的题；而把几个 27% 的"非最强"组合起来，能覆盖 55%。这在管理学上有个现成的对应——全明星队常常打不过配合默契的平民队，因为前者每个位置都强但重叠，后者每个位置都不同但互补。

这个洞察放到更大的图景里更值得玩味。它其实在暗示一种"agent 时代的分工经济学"：与其追求一个无所不能的通用 agent，不如培育一批各有所长的专业 agent，再用一个强大的"评审/编排层"把它们编排起来。这和人类社会从"通才工匠"走向"分工流水线 + 管理层"的历史如出一辙。DEI 的评审员 GPT-4o，某种程度上就是这支 agent 团队的"项目经理"。

当然，这条路也藏着隐忧。如果"评审员"才是天花板，那会不会最终所有团队都用同一个最强的闭源评审员、所有差异化又被抹平？又或者，当某个 agent 真的强到解题集合全面覆盖时，"多样性"这个红利会不会像泡沫一样破掉？这些疑问，恰恰是 DEI 留给下一篇的悬念。

留个问题给你 如果你是这家"agent 医院"的院长，手里预算只够养两个 agent + 一个评审员。你会挑两个"风格迥异但都中等"的，还是挑一个"最强 + 一个互补"的？DEI 的数据，更支持哪一种组队哲学？
